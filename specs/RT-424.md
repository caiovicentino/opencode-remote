# RT-424 — `seq` malformado num quadro derruba o daemon (rejeição descartada por `void handleMessage`)

## Problem
Qualquer membro da sala (inclusive o relay, que o modelo de ameaça trata como não confiável) mata o
processo do daemon com um único quadro, sem decifrar nada:

1. `apps/relay/src/index.ts:1058-1063` repassa `seq: frame.seq` sem validar (é metadado em claro).
2. `handleSealedFrame` (`apps/daemon/src/index.ts:3361-3370`) faz `const seq = frame.seq ?? 0`. Para
   `1.5`, `"abc"`, `{}` ou `Infinity` (JSON `1e999`), o `seq <= session.lastSeq` dá `false` e segue para
   `seqAad(frame.from, seq)`. Lá, `BigInt(seq)` (`packages/protocol/src/crypto.ts:119-125`) lança
   `RangeError`/`SyntaxError` **antes** do `openSealed`, ou seja, antes de qualquer autenticação.
   Basta que `from` seja o id de uma sessão viva, que aparece em claro no envelope.
3. `handleMessage` (`index.ts:3411-3618`) só tem `try` em volta do parse e do ramo de controle. A
   chamada `await handleSealedFrame(...)` (3617) e o `frame.from` (3418) ficam fora dele: o texto
   `null` também quebra, com `TypeError` em `null.from`.
4. Os dois pontos de fiação (`index.ts:3698` relay, `index.ts:3800` `/ws` local) usam
   `void handleMessage(data, ws)`. O daemon não registra `unhandledRejection` e o Node 22 encerra o
   processo. Resultado: DoS remoto e não autenticado.
5. Efeito colateral do mesmo buraco: `seq` acima de 2^53 perde precisão e `setBigUint64` faz wrap
   módulo 2^64. Com `seq = 2^64+4096`, um quadro legítimo selado com `seq` 4096 abre normalmente e grava
   `lastSeq ≈ 1.8e19`. Daí em diante todo quadro vira "replay rejected" e a sessão congela em silêncio.
   O cliente web tem o mesmo padrão (`apps/web/src/lib/client.ts:930-937`). No navegador não há crash,
   só a rejeição solta e o risco de congelar.

## Approach
Padrão da casa (helloguard/pairwindow): **veredito puro na fronteira + fiação fina + backstop único**.
A lição P3-407 vale aqui: a validação é aplicada uma vez, no ponto único por onde passam os dois transportes.

1. **`packages/protocol/src/crypto.ts`**
   - Nova função `export function frameSeq(raw: unknown): number | null`. `undefined`/`null` → `0`,
     preservando a semântica atual do `?? 0`: o guarda de replay continua recusando. Inteiro com
     `Number.isSafeInteger(raw) && raw >= 0` → `raw`. Qualquer outra coisa → `null` (fail-closed), o que
     inclui string numérica, boolean, fração, `NaN`, `±Infinity`, negativo e `>= 2^53`.
   - `seqAad` passa a lançar `RangeError("seqAad: seq must be a non-negative safe integer")` quando
     `frameSeq(seq) !== seq`. Isso deixa o contrato explícito e elimina o wrap de 64 bits para qualquer
     chamador futuro. A assinatura não muda e a AAD dos valores válidos fica byte a byte idêntica.
   - Exportar `frameSeq` em `packages/protocol/src/index.ts`.
2. **`apps/daemon/src/frameguard.ts` (novo, puro: sem `node:*`, `ws`, `fetch`, relógio ou log)**
   - `frameVerdict(raw: unknown)` → `{ ok: true; frame: RelayFrame & { seq: number } }` ou
     `{ ok: false; reason: "not-object" | "bad-from" | "bad-payload" | "bad-seq" }`. Uma causa por retorno,
     avaliadas nesta ordem: `raw` não é objeto (ou é array/`null`) → `not-object`; `from` não é string →
     `bad-from`; `payload` não é string → `bad-payload`; `frameSeq(raw.seq) === null` → `bad-seq`.
   - Não valida `room`: o daemon não usa o campo no roteamento. Joins com `payload: ""` passam.
3. **`apps/daemon/src/index.ts`**
   - Em `handleMessage`, logo após o `JSON.parse` (3414): rodar `frameVerdict`. Se `!ok`:
     `metrics.inc("ocr_frames_malformed_total")` e `log("warn", "malformed frame dropped", { reason })`.
     O `from` só entra no log quando for string, cortado com `.slice(0, 16)`. Nunca logar `seq`, payload
     ou o valor bruto (Constituição #1). Depois, `return`. Daí em diante usar `verdict.frame`.
   - Em `handleSealedFrame` (3361): trocar `frame.seq ?? 0` por `frame.seq`, já normalizado pelo veredito.
     O quadro malformado **não** chama `attributeAuthFailure`/`authFailures.record`, porque metadado
     forjado não pode marcar um dispositivo pareado como falho.
   - Backstop único: `function onSocketMessage(data, ws)` chama `handleMessage(data, ws).catch((err) => { … })`.
     O catch faz `metrics.inc("ocr_frame_handler_errors_total")` e
     `log("error", "frame handler failed", { error: err instanceof Error ? err.name : "unknown" })`.
     Só o `name`, nunca `message`/stack, que podem carregar conteúdo do quadro. Os dois `ws.on("message")`
     (3698 e 3800) passam a chamar `onSocketMessage`. **Não** adicionar `process.on("unhandledRejection")`.
4. **`apps/web/src/lib/client.ts`**
   - Em `onMessage` (844-851): `if (!frame || typeof frame !== "object") return;` antes de `frame.from`.
   - Em 930: `const seq = frameSeq(frame.seq); if (seq === null || seq <= this.daemonLastSeq) return;`
   - Em 414: `void this.onMessage(...)` passa a `this.onMessage(...).catch(() => {})`, para não deixar
     rejeição solta. O comportamento continua sendo descartar o quadro.

## Edge cases
- **Controle sem `seq`** (hello/ping, `scripts/localws.test.ts:121-127,181-187`): `undefined` → `0`, passa.
- **`seq: 0`/ausente num quadro selado:** continua caindo em "replay rejected" (3362), sem mudança.
- **`seq` = `Number.MAX_SAFE_INTEGER`:** válido. `2^53` ou mais → `bad-seq`. Nenhum cliente real chega
  lá (`++sendSeq` em `index.ts:2798` e `client.ts:812,1001`).
- **String numérica `"5"`:** hoje passa e grava `lastSeq` como string, envenenando as comparações. Agora é `bad-seq`.
- **`from` forjado igual a uma sessão viva + `seq` inválido:** a sessão fica intacta (`lastSeq`, `sendSeq`,
  sem registro de auth failure) e uma op legítima seguinte com `seq` válido é respondida.
- **Enxurrada de lixo:** cada quadro gera um `warn`, no mesmo regime do "replay rejected". O volume já é
  limitado pelo token bucket do relay (`apps/relay/src/index.ts:993-1006`) e, no `/ws` local, pelo token da API.
- **Texto `5`, `"x"` ou `[]` na raiz do JSON:** `not-object`/`bad-from`, descartado sem exceção.
- **Erro futuro dentro de `proxy`/`sealAndSend`:** o backstop contém o erro e o processo sobrevive.

## Acceptance criteria
1. `npx tsx scripts/unit.test.ts` passa, com casos novos:
   - `frameSeq`: `undefined`→`0`, `null`→`0`, `0`→`0`, `1`→`1`, `MAX_SAFE_INTEGER`→ele mesmo.
     Retorna `null` para `1.5`, `NaN`, `Infinity`, `-1`, `"1"`, `"abc"`, `true`, `{}`, `[]`, `2**53`, `2**64`.
   - `seqAad("a", 1.5)` e `seqAad("a", 2**53)` lançam `RangeError`.
   - `seqAad("client", 1)` produz os mesmos bytes de antes: 6 bytes de `"client"` + `00…01`, 14 bytes no
     total. O roundtrip de `unit.test.ts:1101-1107` segue verde.
   - `frameVerdict`: `null`/`5`→`not-object`, `[]`/`{payload:"x"}`→`bad-from`, `{from:"a",payload:5}`→`bad-payload`,
     `{from:"a",payload:"x",seq:1.5}`→`bad-seq`, `{from:"a",payload:""}`→`ok` com `seq === 0`.
2. **Prova e2e** em `scripts/localws.test.ts`, com a sessão `localtest` já viva (após a fase 4), enviando
   pelo mesmo `ws` e em sequência: o texto cru `null`; `{"room":"localws","from":"localtest","seq":1.5,"payload":"AAAA"}`;
   o mesmo quadro com `"seq":"abc"`, com `"seq":1e999` (texto cru) e com `"seq":18446744073709555712`.
   Após 1000 ms: `daemon.exitCode === null && daemon.signalCode === null`, e uma op selada nova com
   `seq: 2` recebe `status === 200` em ≤8 s (o `lastSeq` não foi envenenado). No código de hoje o daemon
   morre no primeiro quadro, então o teste falha.
3. `grep -cE "node:|from \"ws\"|fetch\(|Date\.now|log\(" apps/daemon/src/frameguard.ts` → `0`.
4. `grep -n "void handleMessage" apps/daemon/src/index.ts` → nenhuma linha.
   `grep -c "unhandledRejection" apps/daemon/src/index.ts` → `0`.
5. `npm run typecheck`, `npm run lint`, `npm run test:unit` e `npm run test:e2e` verdes.
6. `npx tsx scripts/invariants.ts` continua verde **sem alteração no arquivo**: a checagem de
   `export function seqAad` + `additionalData` segue válida.
7. `docs/security.md` ganha um item em `## Threat notes` dizendo que envelope malformado (`seq` fora de
   inteiro seguro ≥ 0, `from`/`payload` não string) é descartado antes de qualquer cripto, sem afetar a
   sessão viva, e contado em `ocr_frames_malformed_total`. O mesmo item cita o backstop
   `ocr_frame_handler_errors_total`. `docs/architecture.md` diz que `seq` é validado como inteiro seguro
   não negativo antes de entrar na AAD.

## Out of scope
- Validar ou reescrever `seq` no relay (`apps/relay/src/`): o relay é não confiável, e a defesa precisa
  estar nas pontas. Mudar o relay não fecha o ataque.
- Handler global de `unhandledRejection`/`uncaughtException` no daemon (mascararia bugs reais).
- Mudar o guarda de replay (`seq <= lastSeq`), o formato da AAD para valores válidos, o handshake
  (RT-390/helloguard), a allowlist, o arquivo de estado 0600, `scripts/invariants.ts`, `deploy/`,
  `package.json` ou UI.
- Throttle dos logs de quadro malformado (fica para outra task, se aparecer volume real).
