# P2-114 — Ops fail-closed: deploy aborta com checkout de produção sujo + doctor testa o binário tier-B no boot e alerta em N falhas de spawn

## Problem
- `deploy()` (`apps/pilot/src/deploy.ts:343-365`) faz `git checkout -q main` + `git reset -q --hard <sha>` no checkout de produção (`cfg.repo`) sem olhar se a árvore está suja. Modificações rastreadas do operador (o repo de produção é também a árvore de trabalho humana) são descartadas em silêncio, ou o checkout falha de forma críptica. Não há guard antes da mutação, ao contrário do disk guard (P3-006) e do sha guard (P2-058).
- O tier-B (`runTierB`, `apps/pilot/src/runner.ts:420-463`) faz `spawn("claude", …)`; um binário ausente/quebrado gera `infra: "spawn"` e `runAgentForRole` (linha 484-505) apenas loga `tierB-fallback` (warn) e cai para tier A. Ninguém conta a sequência nem alerta: o pilot rodou ~18h com tier-B morto sem ninguém notar. O doctor de boot (`runDoctor`, `apps/pilot/src/doctor.ts:304-333`) não sonda o binário.

## Approach
Opção escolhida: **deploy aborta com árvore suja** (menor e shippável; separar o checkout de produção mexeria em `deploy/install-pilot.sh`, safety-critical — fora de escopo).

1. **Dirty guard no deploy** (`deployguard.ts` + `deploy.ts`):
   - Pure: `export function dirtyGuardDetail(porcelain: string | null): string | null` em `deployguard.ts`. `null` (sonda falhou) → `"prod checkout state unknown (git status failed) — deploy aborted before reset"` (fail-closed). Linhas `??` ignoradas; 0 linhas rastreadas → `null` (ok); senão `"prod checkout dirty: N tracked file(s) modified (a, b, c…) — deploy aborted before reset"` (até 3 paths, resto `+k more`).
   - Em `deploy()`, logo após o disk guard e ANTES do `git rev-parse HEAD`/`prev`: sonda `git status --porcelain --untracked-files=no` via `exec(..., { cwd: cfg.repo, allowFail: true })` (mesma flag que o tamper check de `pipeline.ts:1818`); `ok:false` → `null`. Injetável: `DeployOpts.probeDirty?: (repo: string) => string | null`. Se `dirtyGuardDetail` retornar texto: `log("warn")`, `emitEvent("deploy", { phase: "dirty-guard", ok: false, detail })`, `notify(meta?.task ?? "deploy", false, detail)`, `return { ok: false, rolledBack: false, detail }`. Sem quarentena (o SHA não tem culpa, igual ao disk guard).
2. **Doctor: sonda do binário tier-B no boot** (`doctor.ts`):
   - `export function doctorTierB(models: ModelsConfig | undefined, run: RunFn): DoctorResult`. Sem nenhum modelo em `models.tierB` → `{ ok: true, changed: false, detail: "no tier-B model configured — probe skipped" }`. Com modelo → `run("claude --version")`; `ok` → detail `"claude <primeira linha da saída>"`; falha → `{ ok: false, changed: false, detail: "tier-B binary unusable: claude --version failed — <tail 120 chars>" }`. `changed` é sempre `false` (diagnóstico, não reparo).
   - `runDoctor(cfg: Pick<PilotConfig, "repo" | "models">, workspaces, log, hooks?)` chama `doctorTierB(cfg.models, hooks?.runTierB ?? realRun(cfg.repo))`, loga `doctor: tierB` (warn quando `!ok`) e, quando `!ok`: `emit("phase", { task: "doctor", phase: "tierB-binary", ok: false, detail })` e `void notifySupervisor("doctor", false, detail).catch(() => {})` — ambos injetáveis via `hooks?: { runTierB?: RunFn; notify?: typeof notifySupervisor; emitEvent?: typeof emit }`. Resultado entra no `ok` de "doctor pass complete". Nunca bloqueia o boot.
   - CLI: novo subcommand `tierb` (usage/switch de `main()`, `doctor.ts:345-389`), exit 1 quando `!ok`.
3. **Alerta em N falhas de spawn consecutivas do tier-B** (`runner.ts`):
   - `export const TIERB_SPAWN_ALERT_EVERY = 3;` e pure `export function shouldAlertTierBSpawn(streak: number, every = TIERB_SPAWN_ALERT_EVERY): boolean` → `streak > 0 && streak % every === 0` (alerta na 3ª, 6ª… — sem spam por chamada).
   - Contador em memória do módulo `tierBSpawnStreak` (o boot é coberto pelo doctor; não persistir em state.json). `export function noteTierBOutcome(r: Pick<RunResult, "infra">): number` → `infra === "spawn"` incrementa, qualquer outro resultado zera; retorna a streak. `export function resetTierBSpawnStreak()` para testes.
   - Em `runAgentForRole`, após `runTierB`: `const streak = noteTierBOutcome(r); if (shouldAlertTierBSpawn(streak)) { logDispatch("error", "tierB-spawn-broken", { role, model, streak }); emit("phase", { task: "doctor", phase: "tierB-spawn", ok: false, detail: \`tier-B spawn failed ${streak}x in a row (claude binary?) — falling back to tier A\` }); void notifySupervisor("tierB", false, detail).catch(() => {}); }`. Fallback para tier A continua igual (P1-059).
4. **Docs** (`docs/PILOT.md`): item `0d.` na seção "Deploy staged + rollback" (após o `0c.` da linha 202) descrevendo o dirty guard (flag, evento `dirty-guard`, notify, sem quarentena, fail-closed em sonda indisponível); na seção "Doctor de reparo determinístico (P1-030)" (linha 636+) adicionar o bullet **`tierb`**, a linha de uso `npx tsx apps/pilot/src/doctor.ts tierb` e um parágrafo sobre o alerta `tierB-spawn` a cada 3 falhas consecutivas.

## Edge cases
- Só modificações **rastreadas** contam (`--untracked-files=no`): `opencode.json` untracked e `dist/`/`node_modules/` (gitignored) nunca abortam o deploy.
- Sonda `git status` falhando (repo corrompido, cwd inexistente) → aborta (fail-closed), diferente do disk guard (fail-open) — justificado no detail e nos docs.
- Deploy abortado pelo dirty guard não quarentena o SHA: o self-heal de pending deploy (`index.ts:317-333`) vai tentar de novo a cada ciclo idle até `maxDeploysPerDay`, cada vez com notify — mesmo comportamento do disk guard; documentar.
- `doctorTierB` sem modelo tier-B configurado nunca chama `run` (sem `claude` na máquina de quem só usa tier A, o doctor continua verde).
- `claude --version` que trava: `exec` já tem timeout padrão de 10min — passar `timeoutMin: 1` no `realRun` usado pela sonda (ou aceitar o RunFn e documentar). Não pode segurar o boot indefinidamente.
- Streak de spawn zera em qualquer resultado não-spawn (timeout, marker ausente, sucesso): só o binário quebrado dispara o alerta, não lentidão do modelo.
- Alerta só em múltiplos de 3 — 100 falhas seguidas geram ~33 notifies, não 100; o doctor de boot cobre o cenário "reiniciou e continua quebrado".
- `emit`/`notifySupervisor` falhando nunca derrubam `runAgentForRole` nem `runDoctor` (try/catch, `.catch(() => {})`).

- `npm run typecheck && npm run build --silent && npm run test:unit` verdes; `npm run lint` sem novos erros.
- `scripts/unit.test.ts` — checks novos, todos verdes:
  - `dirtyGuardDetail("")` → `null`; `dirtyGuardDetail("?? foo\n")` → `null`; `dirtyGuardDetail(" M a.ts\nM  b.ts\n")` contém `"2 tracked file(s)"`, `"a.ts"` e `"deploy aborted before reset"`; `dirtyGuardDetail(null)` contém `"state unknown"`.
  - Deploy real-git (P1-036 lesson, sem mock de git): `mkdtemp` + `git init` + commit de `f.txt`, depois modificar `f.txt`; `deploy(cfg, sha, { task: "P2-114" }, { verifiedMerges: [sha], quarantine: [], probeFreeBytes: async () => 100*GB, notify, emitEvent })` (sem `probeDirty` — sonda real) → `res.ok === false && res.rolledBack === false && res.detail.startsWith("prod checkout dirty")`; events `[start, dirty-guard]` com `ok:false`; 1 notify com task `P2-114`; `readFileSync(f.txt)` ainda contém a modificação (nada foi resetado) e `git rev-parse HEAD` não mudou.

  - `resetTierBSpawnStreak(); noteTierBOutcome({infra:"spawn"})` 3x → `3`; `noteTierBOutcome({})` → `0`; `noteTierBOutcome({infra:"spawn"})` → `1`.
- Manual: `npx tsx apps/pilot/src/doctor.ts tierb` com `PATH` sem `claude` e tier-B configurado → exit 1 e log `doctor: tierB` com `ok:false`; com `claude` no PATH → exit 0.

## Out of scope
- Separar o checkout de produção do worktree humano (mexeria em `deploy/install-pilot.sh`, safety-critical) e qualquer mudança em `deploy/` ou `scripts/invariants.ts`.
- Reparo automático do tier-B (reinstalar `claude`, trocar de modelo) — o doctor só diagnostica e alerta.
- Persistir a streak de spawn em `state.json` ou expor um chip novo no dashboard (o feed de eventos já mostra `phase` com `ok:false`).
- Auto-stash/auto-commit da árvore suja antes do deploy.
