# P1-059 — Cognição em tiers: modelos fortes planejam/julgam, flash executa

## Problem

Todo agente do pipeline roda no mesmo modelo flash via `opencode run`
(`runAgent`, apps/pilot/src/runner.ts:195). Evidência da semana: 20 merges
seguidos passaram por reviewers flash sem pegar a amnesia do IER (falha
semântica); specs fracas queimaram pipelines inteiros; e um modelo externo
(fable-5.1) achou em 1h o que o sistema não achou em 20 merges. Papéis de
julgamento (estratégia, planejamento, arbitragem de review) precisam de um tier
de modelo mais forte; papéis de execução (builder, review de rotina, scribe)
já são bem servidos pelo flash e continuam baratos.

## Approach

1. **Config** — `PilotConfig` (apps/pilot/src/state.ts) ganha `models?:`:
   ```json
   "models": {
     "tierA": { "builder": "glm-5.3-flash", "reviewer": "glm-5.3-flash", "scribe": "glm-5.3-flash" },
     "tierB": { "strategist": "fable-5.1", "planner": "opus", "forensic": "fable-5.1", "reviewerEscalation": "opus" }
   }
   ```
   Default (sem bloco): tudo tier A — comportamento atual intacto e deployável.
   Nomes tier A são registro/documentação (o `opencode run` segue usando o
   modelo configurado do opencode); só tier B muda o binário de dispatch.
2. **Dispatch por role** (apps/pilot/src/runner.ts): nova `runAgentForRole(role,
   prompt, opts)` — se `opts.models.tierB[role]` existir, roda tier B via
   `claude -p --model <m> --add-dir <cwd> --permission-mode acceptEdits`
   (prompt via **stdin**, stdin fechado após EOF; cwd = workspace; timeout
   SIGTERM→SIGKILL igual ao `runAgent`). Helpers puros exportados p/ bateria:
   `claudeArgs(model, ws)` e `shouldFallbackTierB(result, marker?)`.
   **Fallback**: `!ok || timedOut || output vazio || marker ausente` ⇒ reexecuta
   pelo `runAgent` (tier A) e loga `tierB-fallback`. Sem tier B configurado,
   `runAgentForRole` === `runAgent`. Log `agent-dispatch` com role/tier/model.
3. **Tier B nos papéis**:
   - **Planner** P0/P1 (pipeline.ts, fase planner): `runAgentForRole("planner", …)`.
     Valid determinístico (`validateSpec`/`commitSpec`) intocado.
   - **Strategist** (index.ts `runStrategist`): idem, marker `STRATEGIST:DONE`.
   - **Reviewer de escalada**: novo predicado puro `needsEscalation(round,
     secOk, qualOk, secAllDropped, qualAllDropped)` — true quando round 1 com
     vereditos divergentes ou findings todos unverificados (`allDropped`,
     pipeline.ts:1163). Se `tierB.reviewerEscalation` configurado, roda 1
     reviewer extra `runAgentForRole("reviewerEscalation", reviewerPrompt(
     "ESCALATION", …))`; o veredito + findings verificados dele decide.
     Máx. 1 escalada por round; emit `phase: "review-escalation"`.
   - **Forensic semanal**: novo apps/pilot/src/forensic.ts — `runForensic(cfg,
     st)` chamado na janela nightly 03:xx (`maybeNightly`), guardado por
     `state.forensicLast` (roda se ausente ou >7 dias). Contexto: até 100
     failure lessons (`readRecentFailureLessons(defaultLessonsFile(), 100)`),
     lista de `~/.opencode-remote/pilot/gate-fail/*.json`, `git log --oneline
     -50`. Saída: taxonomia de falhas (padrões, causa raiz, recomendações) →
     grava `~/.opencode-remote/pilot/forensic-latest.md`, loga resumo e envia
     `digest()`. `PilotState.forensicLast?: string`.
4. **Gate intocado** — lista de steps do gatekeeper (pipeline.ts:1331) e
   `verifyEvidence` não mudam: modelo forte planeja/julga, mas o merge continua
   passando pela mesma evidência determinística.

## Touched files

- `apps/pilot/src/state.ts` — `models?` no `PilotConfig` (parse tolerante, merge com DEFAULTS).
- `apps/pilot/src/runner.ts` — `runAgentForRole`, `runTierB`, `claudeArgs`, `shouldFallbackTierB`, logs dispatch/fallback.
- `apps/pilot/src/pipeline.ts` — planner via `runAgentForRole`; predicado `needsEscalation` + bloco de escalada no loop de review; propagar `cfg` p/ dispatch.
- `apps/pilot/src/index.ts` — strategist via `runAgentForRole`; chamada semanal `runForensic` em `maybeNightly`.
- `apps/pilot/src/forensic.ts` — novo (prompt do forensic + escrita do relatório + digest).
- `scripts/unit.test.ts` — bateria dos helpers puros (ver critérios).
- `docs/PILOT.md`, `AGENTS.md` — documentar o bloco `models`, tiers e fallback.

## Edge cases

- `claude` ausente no PATH / exit != 0 / timeout ⇒ fallback tier A automático
  (log `tierB-fallback`), pipeline nunca trava nem queima attempt.
- Tier B termina sem o marker de conclusão do papel (o "DONE" esperado pelo
  runner, citado nas seções acima) ⇒ fallback; o retry de planner
  (2 tentativas, pipeline.ts:971) continua valendo.
- Sem bloco `models` em pilot.json ⇒ zero mudança de comportamento.
- Escalada só existe com `reviewerEscalation` configurado; sem ele, divergência
  e `allDropped` seguem o fluxo atual (effective approve / findings).
- Forensic roda só com slots idle (mesma guard do `maybeNightly`); falha é
  best-effort e nunca bloqueia o loop.
- `--add-dir` limitado ao workspace clone; nada de `~/.opencode-remote` no
  tier B (regra anti-exfiltração do strategist já existente se mantém).
- Slots concorrentes: dispatch é por processo (claude), sem estado compartilhado.

## Acceptance criteria

1. `npm run typecheck --silent`, `npm run test:unit --silent` e
   `npm run build --silent` verdes.
2. Unit tests novos em scripts/unit.test.ts pinam: `claudeArgs("opus","/w")` =
   `["-p","--model","opus","--add-dir","/w","--permission-mode","acceptEdits"]`;
   `shouldFallbackTierB` true p/ `{ok:false}`, `{timedOut:true}`, output vazio
   e marker ausente, false p/ saída ok com marker; config sem `models` ⇒
   `runAgentForRole` resolve tier A p/ qualquer role; tabela do
   `needsEscalation` (divergente ⇒ true; ambos APPROVE ⇒ false; round>1 ⇒ false).
3. Com `"models": {"tierB": {"planner": "fable-5.1"}}` em pilot.json: a próxima
   task P0/P1 loga `agent-dispatch` com `tier:"B"` no pilot.log e o spec commitado
   passa no mesmo `validateSpec`/gate. Removendo o bloco, volta a logar `tier:"A"`.
4. Tier B indisponível (simulado: `PATH` sem `claude` numa run de teste):
   pilot.log mostra `tierB-fallback` e o pipeline completa via tier A sem
   intervenção humana.
5. Divergência de reviewers no round 1 (1× APPROVE, 1× REQUEST_CHANGES) com
   `reviewerEscalation` configurado emite `phase:"review-escalation"` e no máx.
   1 run extra de review por round.
6. `state.forensicLast` presente após a janela 03:xx e `forensic-latest.md`
   criado; segunda execução na mesma semana não roda de novo.
7. Critério de campo: com tier B no strategist ativo e ≥10 refills em 7 dias,
   taxa de `pipeline result ok:false` no pilot.log da semana < 40%.

## Out of scope

- Migrar builder/reviewers de rotina/scribe para tier B (ficam tier A sempre).
- Plumbar os nomes tier A no opencode (hoje o modelo vem do opencode.json).
- Mudar gatekeeper, `scripts/invariants.ts`, `deploy/`, cripto E2E, allowlist.
- Injetar a taxonomia do forensic no prompt do strategist (após validação).
- Contabilidade de custo por role/papel e dashboard de tiers no PWA.
- Re-rotear redteam/researcher/explorer.
