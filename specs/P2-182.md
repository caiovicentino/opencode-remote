## Problem

`apps/desktop/src/main.ts:611-620` só chama `session.defaultSession.setPermissionRequestHandler` e
`setPermissionCheckHandler` dentro do `if (process.env.OCR_DESKTOP_CAMERA_BLOCK === "1")` criado pela
P2-117. No app empacotado essa variável nunca existe, então **nenhum handler é registrado** e a sessão
default cai no default do Electron (que concede várias permissões sem perguntar).

O pane Browser (`README.md:136`, `README.md:591`) renderiza um `<webview>` que navega para qualquer
http/https e abre sozinho quando o agente cita uma URL de localhost — conteúdo de terceiros. Desde a
P2-169 o bundle é assinado/notarizado e carrega as usage descriptions de câmera e microfone
(`README.md:632`), então um pedido feito por uma página qualquer aparece para o SO como se fosse o
nosso produto pedindo.

Mesma classe de buraco que a P2-178 fechou no `shell.openExternal` (`apps/desktop/src/extlink.ts`), e
mesma correção: uma decisão pura única antes da chamada perigosa.

## Approach

1. **Novo módulo `apps/desktop/src/permissions.ts`** — puro, no espírito de `extlink.ts`/`deeplink.ts`/
   `sidecarexit.ts`: sem `import ... from "electron"`, sem `node:fs`, sem `node:path/os`, sem `fetch`.
   Exporta:
   ```ts
   export interface PermissionContext { devUrl?: string; cameraBlocked: boolean }
   export interface PermissionDecision { allow: boolean; reason: string }  // reason SEMPRE não-vazio
   export function permissionDecision(name: unknown, requestingUrl: unknown, ctx: PermissionContext): PermissionDecision
   ```
   Também exporte a lista de permissões liberadas (ex.: `SHELL_PERMISSIONS = ["media",
   "clipboard-sanitized-write", "fullscreen"]`) para o teste importar em vez de duplicar strings.
2. **Política** (allowlist, default deny):
   - Origem do shell = `file:` (bundle empacotado, `win.loadFile`) **ou** origem exatamente igual à de
     `ctx.devUrl` quando definida (`main.ts:1122-1128`, `OCR_WEB_URL`). Comparar `URL.origin`, e o
     scheme sempre em caixa baixa (motivo da P2-178: `FILE:` não pode passar).
   - Permissão liberada apenas se `name` ∈ `SHELL_PERMISSIONS` **e** quem pede é a origem do shell.
   - Negar explicitamente, mesmo vindo da origem do shell: `geolocation`, `notifications`, `midi`,
     `midiSysex`, `hid`, `serial`, `usb`, `openExternal`, `pointerLock`, `idle-detection`,
     `window-management`.
   - Qualquer nome desconhecido (inclusive `"unknown"` e permissões futuras do Chromium) → negar com
     reason próprio. Nada ganha acesso em silêncio numa bump de Electron.
   - `ctx.cameraBlocked === true` → `media` negada **inclusive** para a origem do shell. Esse é o
     único efeito que `OCR_DESKTOP_CAMERA_BLOCK` continua tendo (hatch da P2-117 preservado byte a byte).
3. **`main.ts`**: remover o `if (process.env.OCR_DESKTOP_CAMERA_BLOCK === "1")` e registrar os **dois**
   handlers sempre, fora de qualquer bloco condicional, ambos consultando `permissionDecision` com
   `{ devUrl: process.env.OCR_WEB_URL, cameraBlocked: process.env.OCR_DESKTOP_CAMERA_BLOCK === "1" }`:
   - `setPermissionRequestHandler((_wc, permission, callback, details) => { const d = permissionDecision(permission, details?.requestingUrl, ctx); if (!d.allow) logError(...); callback(d.allow); })`
   - `setPermissionCheckHandler((_wc, permission, requestingOrigin) => permissionDecision(permission, requestingOrigin, ctx).allow)`
   - Log da recusa: **só** nome da permissão + scheme de quem pediu + `reason` — nunca a URL inteira
     (navegação do usuário não pode vazar no `desktop.log`, mesmo motivo do `extlink`).
4. **Testes** em `scripts/unit.test.ts` (já na cadeia `test:unit`), no mesmo formato `check(...)` do
   bloco P2-178 (`scripts/unit.test.ts:562-610`), incluindo a leitura do `main.ts` real via
   `mainTsSource`.
5. **Docs**: uma frase em `README.md` e em `README.pt-BR.md`, junto do parágrafo do pane Browser
   (`README.md:136` / `README.pt-BR.md:116`) ou do parágrafo de câmera/microfone (`README.md:632` /
   `README.pt-BR.md:486`).

## Touched files

- `apps/desktop/src/permissions.ts` — **novo**, módulo puro com `permissionDecision`.
- `apps/desktop/src/main.ts` — import do novo módulo; substituir o bloco condicional das linhas 611-620
  pelo registro incondicional dos dois handlers.
- `scripts/unit.test.ts` — novo bloco de checks (padrão do bloco `externalOpenDecision`, linhas 562-610).

- `README.pt-BR.md` — mesma frase em pt-BR.

## Edge cases

- `name`/`requestingUrl` não-string, `""`, URL não parseável, URL sem origem (`origin === "null"` em
  URLs opacas) → negar, cada um com reason próprio e distinto (`not-a-string`, `empty`,
  `unparseable-url`, `missing-origin`).
- `ctx.devUrl` ausente, vazio ou não parseável → tratar como "sem dev URL"; só o `file:` passa.
- Scheme em caixa alta (`FILE:///…`, `HTTP://localhost:5173`) → mesma decisão do minúsculo.
- `media` da origem do shell com `cameraBlocked: true` → negado (reason específico, ex.:
  `camera-blocked`), sem alterar nenhuma outra permissão.
- `notifications` fica negada mesmo para o shell: no bundle o renderer roda em `file:` e
  `apps/web/src/lib/push.ts:25` já aborta nesse protocolo; as notificações do desktop saem do main
  (`notify.ts`), não da Notification API do renderer.
- `permissionDecision` nunca lança: qualquer `new URL()` fica dentro de try/catch.
- `reason` é sempre não-vazio, inclusive no caminho `allow: true`.

## Acceptance criteria

- `npx tsx scripts/unit.test.ts` verde com checks novos cobrindo, no mínimo:
  - `media` liberada para `file:///.../index.html`;
  - `media` liberada para a dev URL quando `ctx.devUrl = "http://localhost:5173"` (requesting
    `http://localhost:5173/index.html`);
  - `media` negada para `https://evil.example.com/page`;
  - `media` negada para a origem do shell quando `cameraBlocked: true`;
  - `geolocation`, `notifications`, `midi`, `midiSysex`, `usb`, `hid`, `serial` negadas mesmo vindas
    da origem do shell;
  - nome de permissão desconhecido (ex.: `"future-sensor-api"`) negado;
  - `""`, URL malformada e valor não-string negados;
  - todo caso negado com `decision.reason.length > 0`.
- Asserções lendo o `main.ts` real (via `mainTsSource`): o arquivo importa `./permissions`; chama
  `setPermissionRequestHandler` e `setPermissionCheckHandler` exatamente 1x cada; nenhuma dessas
  chamadas está dentro de um bloco condicionado a `OCR_DESKTOP_CAMERA_BLOCK` (a única ocorrência
  restante dessa env em `main.ts` é a que monta `cameraBlocked`); nenhum outro callback de permissão
  existe no arquivo.
- Asserção de pureza de `apps/desktop/src/permissions.ts` (source read): não contém `from "electron"`,
  `node:fs`, `node:path`, `node:os`, `node:child_process` nem `fetch(`.
- `npm run test:desktop-flow` verde — o boot 1 da P2-117 (`OCR_DESKTOP_CAMERA_BLOCK=1`,
  `scripts/desktop-flow.test.ts:852-885`) continua chegando ao estado `unavailable` do scanner com o
  CTA de colar código.
- `npm run typecheck`, `npm run build` e `npm run test:unit` verdes, com output real colado no EVIDENCE
  (nada de tail resumido — o gate re-executa e compara, cf. P2-099).
