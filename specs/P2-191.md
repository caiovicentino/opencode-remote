# P2-191 — mac Intel sem download + feed macOS apontando para o zip errado

## Problem
`apps/desktop/electron-builder.yml` declara `mac.target` como `dmg`/`dir`/`zip` sem `arch`, e o job
`desktop-dmg` de `.github/workflows/release.yml` roda em `macos-14` (arm64): a release só carrega
artefatos arm64 e um usuário de Mac Intel não acha instalador nenhum. O `release-verify`
(`scripts/release-assets.ts:73`) aprova assim mesmo, porque exige apenas *um* `.dmg` e *um* `.zip`
carregando a versão, sem olhar arquitetura. Pior: `apps/desktop/scripts/update-feed.mjs:76`
(`pickZipName`) escolhe o zip do feed pelo primeiro em ordem alfabética quando o yml não referencia
um caminho — no instante em que a segunda arquitetura existir, `update-mac.json` serviria o zip
errado e o Squirrel.Mac entregaria uma atualização que não roda na máquina do usuário
(`apps/desktop/src/update.ts:138` hoje aponta todo darwin para o mesmo `update-mac.json`).

## Approach
1. **electron-builder.yml (bloco `mac`)** — declarar arquitetura explícita nos alvos distribuíveis,
   mantendo `dir` sem `arch` (electron-builder usa a do host, `dist:smoke` da P3-010 segue rápido):
   ```yaml
   target:
     - target: dmg
       arch: [arm64, x64]
     - target: dir
     - target: zip
       arch: [arm64, x64]
   ```
   `artifactName: OpenCode-Remote-${version}-${arch}.${ext}` já rende `-arm64`/`-x64` em dmg e zip.
2. **update-feed.mjs — `macFeedPlan` (pura, exportada)**
   `macFeedPlan(fileNames, tag, repoSlug, meta = {})` → `{ feeds: { arm64, x64 } | null, problems: string[] }`.
   - `meta` opcional (`{ notes, pubDate }`) para o CLI injetar o que já lê do `latest-mac.yml`;
     defaults `""` e `new Date().toISOString()`, para os testes chamarem com 3 argumentos.
   - Arquitetura do nome por token com fronteira: `/(^|[-_.])arm64([-_.]|$)/` e `/(^|[-_.])x64([-_.]|$)/`
     sobre o nome sem a extensão — `OpenCode-Remote-0.3.0-mac.zip` nunca casa com nenhuma arquitetura.
   - Cada documento tem o mesmo formato de hoje: `{ url, name, notes, pub_date }`, `url` =
     `https://github.com/<repoSlug>/releases/download/<tag>/<encodeURIComponent(zip)>`,
     `name` = versão nua da tag (tag sem o `v`).
   - `problems` (strings, mesmo estilo de `buildSquirrelFeed`, TODOS reportados de uma vez, fail-closed
     → `feeds: null` quando houver qualquer um): tag vazia; nenhum `.zip` na lista (cobre lista vazia);
     por arquitetura declarada, zero zips casando (`missing file: *.zip carrying <arch> …`); mais de um
     zip da mesma arquitetura (`ambiguous …`, listando os nomes).
   - `pickZipName`/`buildSquirrelFeed` continuam existindo (a validação yml×tag do CLI depende deles).
3. **update-feed.mjs — modo CLI** — depois da validação atual (`buildSquirrelFeed`), chamar
   `macFeedPlan` e gravar três arquivos em `dist/`: `update-mac-arm64.json`, `update-mac-x64.json` e
   `update-mac.json` como **apelido byte a byte** do documento arm64 (`JSON.stringify(feed, null, 2) + "\n"`
   idêntico) — a base já instalada consulta o nome antigo e não pode perder o caminho de atualização.
   Qualquer problem de `macFeedPlan` → nada é escrito, exit 1 com todos os problems listados.
4. **apps/desktop/src/update.ts — `publicFeedUrl`** — novo parâmetro `arch: string = process.arch`
   (4º, depois de `platform`). Ordem: `OCR_PUBLIC_UPDATE_FEED` continua com prioridade absoluta →
   `packaged` → darwin escolhe `update-mac-arm64.json` (arm64), `update-mac-x64.json` (x64) e
   `update-mac.json` para qualquer outra arquitetura; win32 segue `latest.yml`; demais plataformas `null`.
   `updatesEnabled` chama com 3 argumentos e continua funcionando pelo default.
5. **scripts/release-assets.ts** — novo `AssetMatch` `{ kind: "extension+version+arch"; ext; version; arch }`
   (mesma checagem de fronteira da versão + token de arquitetura no nome). `expectedAssets(tag)` passa a
   ter **10** slots: dmg arm64, dmg x64, zip arm64, zip x64, exe, `latest-mac.yml`, `update-mac.json`,
   `update-mac-arm64.json`, `update-mac-x64.json`, `latest.yml`. Sem instalador Intel o `release-verify`
   reprova e a release fica rascunho pelo contrato da P2-179 (`scripts/release-publish.ts` reusa
   `missingAssets`, nada muda lá).
6. **release.yml (job `desktop-dmg`, passo de upload)** — o glob passa a subir
   `apps/desktop/dist/update-mac*.json` junto do dmg e do `latest-mac.yml`, senão a release real nunca
   satisfaria os dois slots de feed novos. Nenhum outro job é tocado; justificar no commit (regra #3
   não se aplica — não é `deploy/` nem `invariants.ts` — mas o passo é de release).
7. **Docs** — README.md (§ instalador DMG e a lista "What each release must carry"), README.pt-BR.md
   (seções espelhadas) e docs/troubleshooting.md: existem **dois** downloads, o usuário de Apple Silicon
   pega `-arm64`, o de Intel pega `-x64`, e um app arm64 já instalado continua se atualizando pelo nome
   antigo (`update-mac.json`, apelido do feed arm64).

## Touched files

- `apps/desktop/scripts/update-feed.mjs` (`macFeedPlan` + `main()`)
- `apps/desktop/src/update.ts` (`publicFeedUrl`)
- `scripts/release-assets.ts` (`AssetMatch`, `assetMatches`, `expectedAssets`)
- `.github/workflows/release.yml` (só o passo "Attach DMG + update metadata", job `desktop-dmg`)

- `README.md`, `README.pt-BR.md`, `docs/troubleshooting.md`

## Edge cases
- Zip sem arquitetura no nome (`…-mac.zip`, legado) nunca casa com arm64 nem com x64 → vira problem
  de arquitetura faltando, jamais um feed apontando para o artefato errado.
- Fronteira de token: `x64` não pode casar dentro de `arm64`/`x86_64`; `arm64` não pode casar em
  `arm64e` — use as regex com fronteira acima.
- `update-mac.json` precisa ser **byte a byte** igual ao arm64 (mesmo `pub_date`): gere o documento uma
  vez e escreva o mesmo texto nos dois arquivos.
- `publicFeedUrl` com `OCR_PUBLIC_UPDATE_FEED` ignora plataforma **e** arquitetura (override absoluto).
- Blocos existentes de `scripts/unit.test.ts` que quebram com `expectedAssets` de 6 → 10 e **precisam ser
  atualizados**: P2-153 ("expected assets are exactly 6", contagem de `missing` e o CLI que espera
  `6 problem(s) found`), P2-179 (`publishDecision`, lista `complete` e a contagem de feeds ausentes) e
  P2-186 (fixture de checksums, que passa por `missingAssets` em `scripts/release-checksums.ts:123`).
  As fixtures precisam ganhar os nomes `-x64` e os dois feeds novos.
- Falha do gate por artefato ausente é sempre fail-closed: nenhum feed parcial escrito em disco.

## Acceptance criteria
- `npx tsx scripts/unit.test.ts` verde, com blocos novos cobrindo:
  - `macFeedPlan` com os dois zips presentes → dois documentos, cada `url` terminando no zip da própria
    arquitetura, `problems.length === 0`;
  - zip x64 ausente → problem; zip arm64 ausente → problem; dois zips arm64 → problem (ambíguo);
    lista vazia → problem; `feeds === null` em todos esses casos;
  - nome sem arquitetura (`OpenCode-Remote-0.3.0-mac.zip`) não satisfaz nenhuma arquitetura;
  - documento apelido: `JSON.stringify(plan.feeds.arm64) === JSON.stringify(aliasDoc)` (byte a byte);
  - matriz `publicFeedUrl`: `("darwin","arm64") → …/update-mac-arm64.json`,
    `("darwin","x64") → …/update-mac-x64.json`, `("darwin","ppc64") → …/update-mac.json`,
    `("win32", …) → …/latest.yml`, `("linux", …) → null`, e `OCR_PUBLIC_UPDATE_FEED` vencendo os quatro;
  - matriz `release-assets`: release completa (10 nomes) sem nenhum problem; sem o dmg Intel → problem;
    sem o zip Intel → problem; sem `update-mac-arm64.json` → problem; sem `update-mac-x64.json` → problem;
  - asserção lendo o `apps/desktop/electron-builder.yml` real: o bloco `mac` declara `arm64` **e** `x64`
    em `dmg` e em `zip` (parse do bloco entre `\nmac:` e `\ndmg:`, como o teste P2-186 já faz).
- `npm run typecheck`, `npm run build` e `npm run test:unit` verdes, com output real colado no EVIDENCE.
- `npx tsx scripts/invariants.ts` verde (nenhuma mudança lá).
- Empacotar de fato segue fora do gate por design (docs/PILOT.md); nenhum screenshot é evidência.
