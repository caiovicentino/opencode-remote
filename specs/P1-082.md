# P1-082 — Cards de aprovação fantasma no modo auto — lifecycle de permissão

## Problem

No modo auto o daemon responde o ask em nome do usuário (`autoApprove`, `apps/daemon/src/index.ts:1226`)
e emite `ocr.permission.auto` via WS (:1250-1257), mas o ChatView constrói os cards de aprovação
direto do buffer de eventos (`apps/web/src/components/ChatView.tsx:874-882`, extração em
`extractPermission` :150-172): **todo** evento `permission.*` dos últimos 50 vira um card acionável,
sem consultar o estado atual. Resultado (print do operador):

- cards eternos de asks já resolvidos (ghost cards);
- o mesmo `permissionID` renderiza N cards (8 idênticos no print) — não há dedupe por evento;
- clicar num card stale faz `POST /session/:id/permissions/:pid` no opencode e o chat mostra o
  erro cru `approve failed (404): ...` (`respond`, ChatView.tsx:971-994).

## Approach

1. **Módulo puro novo** `apps/web/src/lib/permissionCards.ts` (testável sem DOM):
   - `collectPermissionAsks(events, sessionId): PermissionAsk[]` — reaproveita a lógica de
     `extractPermission` (ChatView.tsx:150) e **dedupe por `permissionID`** (Map, última ocorrência
     vence). N asks do mesmo request → 1 entrada.
   - `reconcilePermissionCards(asks, serverPending, responded, autoMode)` →
     `{ actionable, resolved }`. Regras: card é **acionável** somente se o `permissionID` consta na
     lista PENDING do daemon (GET `/permission`, filtrada por `sessionID`) E não está em `responded`
     E `autoMode === false`. Tudo que foi visto e não está pendente vira linha colapsada
     `resolved` com a origem (`"auto"` se veio de `ocr.permission.auto`, senão `"other"`).
2. **ChatView.tsx**:
   - Fonte de verdade dos cards acionáveis passa a ser a lista do servidor (`persistedAsks`,
     fetch `GET /permission` já existe em ChatView.tsx:465-480). Eventos de permissão servem só
     para semear as linhas `resolved` e disparar **re-fetch** do `/permission` (debounce ~300ms) —
     não renderizam card por si sós.
   - Em `ocr.permission.auto` (handler existente ChatView.tsx:719-730): em vez de só sumir com o
     card, movê-lo para linha colapsada "auto-aprovada" em tempo real (WS do daemon já emite o
     evento — nenhum change no daemon esperado; verificar e cobrir em teste).
   - **Modo auto**: obter `autoMode` via `GET /__ocr/settings` (shape em
     `apps/daemon/src/index.ts:465-467`; SettingsView.tsx:161 já consome). Com autoMode: nenhum
     card acionável — badge passivo e discreto no transcript ("AutoMode — ações aprovadas
     automaticamente", audit log no daemon é o registro) + toast `autoApproved` existente por evento.
   - `respond()` (:971-994): status **404** → tratar como "já resolvida": marcar responded, remover
     de `persistedAsks`, mostrar inline `t("alreadyResolved")` (nota amigável, não erro vermelho).
     Outros status mantêm o erro atual.
3. **i18n** `apps/web/src/lib/i18n.ts`: novas chaves en + pt-BR: `alreadyResolved`
   ("Permission already resolved" / "Permissão já resolvida"), `permResolvedLine`
   ("resolved" / "resolvida"), `permAutoLine` ("auto-approved" / "auto-aprovada"), `autoBadge`.
4. **Teste unitário** `scripts/permission-cards.test.ts` (padrão tsx de
   `scripts/pwa-watch.test.ts`: `check()` + exit code): dedupe (10 eventos, mesmo permissionID → 1),
   reconcile (pendente-only acionável; autoMode → 0 acionáveis; classificação auto/other;
   responded → resolved), 404→alreadyResolved (extraí o mapeamento p/ função pura se possível).
   Adicionar ao chain `test:unit` do `package.json` raiz.

## Touched files

- `apps/web/src/lib/permissionCards.ts` (novo — lógica pura de dedupe/lifecycle)
- `apps/web/src/components/ChatView.tsx` (render de cards, badge auto, respond 404, re-fetch /permission)
- `apps/web/src/lib/i18n.ts` (chaves novas en/pt-BR)
- `scripts/permission-cards.test.ts` (novo)
- `package.json` (chain `test:unit` += novo teste)

## Edge cases

- `GET /permission` falha ou daemon legacy sem endpoint: nunca bloquear o chat — manter lista
  anterior e re-tentar no próximo evento `permission.*` (comportamento atual como fallback
  explícito, sem cards fantasma novos).
- Eventos com `id` em vez de `permissionID` (extractPermission já normaliza :162) — dedupe pela
  chave normalizada.
- Asks pendentes anteriores ao abrir a view continuam cobertos por `persistedAsks` (fetch no
  mount, ChatView.tsx:461-495); troca de sessão reseta estado (`:450-495` já limpa — não vazar
  `resolved` entre sessões; keyar resolved por `sessionID`).
- autoMode ligado no meio da sessão: re-checar settings quando chegar `ocr.permission.auto` sem
  card correspondente; badge some/aparece sem reload.
- Card resolvido por **reject** humano → linha "resolvida" (não "auto-aprovada").
- Diff tocando `apps/web/` ativa `npm run test:desktop-flow` no gate — não quebrar seletores/fluxo
  do chat (P1-080 repro de overflow continua passando).

## Acceptance criteria

- `npm run typecheck` (raiz, workspaces) → 0 erros; `npm run build` → web builda; `npm run test:unit`
  → verde incluindo `scripts/permission-cards.test.ts` (todas as checks OK).
- Teste unitário cobre: (a) 10 eventos com o mesmo `permissionID` → 1 card; (b) `autoMode=true` →
  0 cards acionáveis mesmo com asks pendentes; (c) ID ausente do pending do servidor → linha
  `resolved`, nunca card acionável; (d) 404 mapeia para mensagem amigável.
- Comportamento observável: sessão em modo auto com 10 asks seguidos → **nenhum** card acionável,
  apenas badge passivo + toasts; cards de asks já resolvidos viram linha colapsada; clicar em card
  stale mostra "Permissão já resolvida" inline (sem `approve failed (404)` cru); card aberto vira
  "auto-aprovada" em tempo real ao receber `ocr.permission.auto` (WS), sem reload.
- Nenhuma mudança em `apps/relay/`, `scripts/invariants.ts` ou `deploy/`.

## Out of scope

- Novos endpoints no daemon ou mudança no fluxo de autoApprove (WS event já existe).
- Botões "always allow"/politicas por ferramenta; histórico de permissões persistido.
- Perguntas (`question.asked`) — mesmo padrão de bug existe, mas fica para task própria.
