# P1-035 — Watchdog não deve matar o pilot durante aux agents

## Problem

`startWatchdog(3)` (apps/pilot/src/state.ts:263-275) roda a cada 60s e faz `process.exit(1)`
se o arquivo `~/.opencode-remote/pilot/heartbeat` envelhecer >3min. O loop principal toca
o heartbeat no topo de cada ciclo (apps/pilot/src/index.ts:75, ciclo ~5s), mas durante
`await runStrategist` (index.ts:189, timeout 25min), `await runResearcher`
(researcher.ts:69-74, 20min) e o redteam (index.ts:380-393, 30min) o loop está bloqueado.
Quem alimenta o watchdog hoje:

- `runTierB` (runner.ts:344): timer próprio `setInterval(touchHeartbeat, 60_000)` — seguro.
- Pipeline de tasks: callback `stream` toca o heartbeat (pipeline.ts:1054-1055) — seguro enquanto streama.
- Explorer: toca no próprio callback (explorer.ts:148, lição P3-052).
- `runAgent` tier A (runner.ts:196-253): NÃO toca heartbeat. Seu `onStdout` é
  `agentStream(role)` (runner.ts:174-186), que só loga (throttle 10s) — e num agent
  silencioso (ex. strategist lento) nenhum chunk chega.

Resultado: um strategist tier A (fallback do P1-059 ou ausência de tierB), researcher ou
redteam que fique >3min sem stdout derruba o processo inteiro via watchdog — matando
slots com pipeline em voo (`running` map) e forçando restart pelo KeepAlive.

## Approach

1. **Helper único** — em state.ts (junto de `touchHeartbeat`, linha 256), exportar:
   ```ts
   export function startHeartbeat(everyMs = 60_000, touch: () => void = touchHeartbeat): () => void
   ```
   Faz `setInterval(touch, everyMs)` e devolve função de stop (clearInterval).
2. **runAgent alimenta o watchdog** — em runner.ts, após o spawn bem-sucedido
   (depois da linha 217), agendar `const stopHb = startHeartbeat(opts.heartbeatMs ?? 60_000, opts.heartbeatTouch ?? touchHeartbeat)`
   e pará-lo nos handlers `exit` e `error` (junto do `clearTimeout(timer)` existente).
   O timer cobre também o caso "agent sem stdout nenhum" — exatamente o cenário do critério.
3. **runTierB usa o helper** — trocar o `setInterval(touchHeartbeat, 60_000)` inline
   (runner.ts:344) por `startHeartbeat()`; `finish` chama o stop retornado. Sem mudança de
   comportamento.
4. **Injetáveis de teste em runAgent** (todos opcionais, default = comportamento atual):
   `preflight?: () => Promise<boolean>` (default `waitForApi`), `spawnImpl?: typeof spawn`,
   `heartbeatMs?: number`, `heartbeatTouch?: () => void`. Nenhuma dependência nova.
5. **Docs** — atualizar a menção em docs/PILOT.md (~linha 750): todos os aux agents agora
   alimentam o watchdog via timer interno do runAgent/runTierB (não só o explorer).

Alternativa rejeitada: pausar o watchdog durante os awaits — cega a proteção global
(um event loop travado com slots em voo deixaria de ser detectado). Alimentar o heartbeat
mantém o watchdog armado e elimina só o falso positivo.

## Touched files

- `apps/pilot/src/state.ts` — exportar `startHeartbeat` (novo, ~6 linhas).
- `apps/pilot/src/runner.ts` — `runAgent`: timer + stop nos handlers exit/error; opts
  ganham os 4 injectables; `runTierB`: refatorar para `startHeartbeat`.
- `scripts/unit.test.ts` — novos checks (critérios 1-2).
- `docs/PILOT.md` — uma linha atualizando a referência ao P1-035 (~linha 750).

## Edge cases

- Agent silencioso do início ao fim: timer cobre (não depende de stdout).
- `waitForApi` false ou spawn error: retorno antes/agenda nada ou para o timer — sem
  intervalo vazando (stop idempotente nos dois handlers, padrão `done` do runTierB).
- Timeout do próprio runAgent (SIGTERM→SIGKILL): segue resolvendo `ok:false` pelo handler
  `exit`; o watchdog continua armado para travadas reais do processo (ex. exec síncrono —
  deploy já toca o heartbeat dos dois lados, lição P1-044).
- Slots concorrentes: cada `runAgent` tem seu próprio intervalo (sem estado global novo);
  escritas no arquivo são as mesmas de hoje (`writeFileSync` de um timestamp).
- Semântica do watchdog intocada: `maxSilenceMin`, checagem de 60s e `process.exit(1)`
  permanecem (state.ts:263-275).
- Unit tests escrevem heartbeat real? Não — usam `heartbeatTouch`/`touch` injetados,
  herméticos mesmo com pilot de produção rodando na mesma máquina.

## Acceptance criteria

1. `npm run test:unit --silent` verde com os novos checks:
   - `startHeartbeat(20, spy)`: spy chamado ≥2x em ~70ms; após `stop()`, zero chamadas
     novas em ~70ms.
   - **Critério do backlog (estrategista silencioso)**: `runAgent("x", { preflight: async () => true,
     spawnImpl: () => spawn(process.execPath, ["-e","setTimeout(()=>process.exit(0),300)"]),
     heartbeatMs: 20, heartbeatTouch: spy, timeoutMin: 5, cwd: tmp, label: "t" })` —
     resolve `{ok: true}` com stdout vazio e `spy` chamado ≥2x durante o silêncio;
     o processo do test não morre (silêncio de 300ms com refresh a cada 20ms escala
     1:1 com strategist de 6min silencioso a cada 60s vs watchdog de 3min).
   - runTierB continua usando `startHeartbeat` (checks p1-059 existentes seguem verdes).
2. `npm run typecheck --silent` e `npm run build --silent` verdes.
3. Em produção (observável): durante um await de strategist/redteam real, o mtime de
   `~/.opencode-remote/pilot/heartbeat` avança no máx. ~60s entre toques e
   `GET /api/pilot-events` reporta `heartbeatMs` < 120000 mesmo com o agent mudo;
   nenhuma linha `watchdog: heartbeat stale` no pilot.log atribuível a awaits de aux agents.

## Out of scope

- Mudar `startWatchdog` (intervalo, `maxSilenceMin`, exit) ou o KeepAlive do daemon.
- Pausar o watchdog durante awaits (abordagem rejeitada — ver Approach).
- Heartbeat em `deploy.ts` (já resolvido, P1-044) e no stream do pipeline (pipeline.ts:1055).
- `scripts/invariants.ts`, `deploy/`, cripto E2E, allowlist, replay protection — intocados.
- Novas dependências ou mudança no formato do arquivo de heartbeat (dashboard lê número cru).
