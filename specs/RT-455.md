# RT-455 — relay: crash remoto não autenticado com um único frame (envelope malformado)

## Problem
`socket.on("message")` em `apps/relay/src/index.ts:996-1078` faz `JSON.parse` do frame e só
confere `typeof room/payload === "string"` (linha 1003). `from` e `seq` passam sem validação
até o `JSON.stringify({room, from: frame.from ?? socket.id, seq: frame.seq, payload})`
(linhas 1073-1078). O `JSON.parse` do V8 é iterativo, mas o `JSON.stringify` é recursivo:
um `from` ou `seq` com aninhamento profundo (ex.: `"["×400k + "]"×400k`, cabe no `maxPayload`
de 1 MB) lança `RangeError: Maximum call stack size exceeded` dentro do listener do `ws`.
Não há `try/catch` nem handler de `uncaughtException` no relay → o processo inteiro morre,
derrubando todas as salas de todos os tenants. Basta abrir um socket (sem auth) e mandar um
frame com `room` válido. Variante do mesmo bug: o frame literal `null` (`JSON.parse("null")`)
faz `frame.room` lançar `TypeError` na linha 1003 — também fatal. (`String(frame.from)` nos
logs das linhas 1015/1057 também custa O(n) em arrays gigantes; a validação de forma resolve isso.)

## Approach
1. Novo módulo puro `apps/relay/src/envelope.ts` (sem imports, sem I/O, sem relógio, sem log —
   padrão de `roomid.ts`/`apps/daemon/src/frameguard.ts`):
   - `export const FROM_MAX = 128` (mesmo teto de `ROOM_ID_MAX`; o daemon usa o room como `from`,
     o PWA usa 8 chars base36 — `apps/web/src/lib/client.ts:1090`).
   - `export function envelopeVerdict(raw: unknown): { ok: true; frame: { room: string; from: string | undefined; seq: number | null | undefined; payload: string } } | { ok: false; reason: "not-object" | "bad-room" | "bad-payload" | "bad-from" | "bad-seq" }`.
   - Regras: `raw` objeto não-nulo e não-array; `room` string; `payload` string;
     `from` ausente/`null` (→ `undefined`, o chamador aplica `socket.id`) OU string com
     `length <= FROM_MAX`; `seq` `undefined`/`null` (preservado como veio) OU número
     `Number.isSafeInteger && >= 0` — mesma regra de `frameSeq` em
     `packages/protocol/src/crypto.ts:125` (inline, sem importar; o teste prova paridade).
   - A grammar do room continua em `isValidRoomId` (não duplicar aqui; `bad-room` é só tipo).
2. Em `index.ts`, substituir a linha 1003 por `const v = envelopeVerdict(parsed); if (!v.ok) return;`
   e usar `v.frame` no resto do handler (drop silencioso, igual ao parse inválido de hoje —
   nada logado, nunca conteúdo do payload; constituição #1). O rebuild vira
   `JSON.stringify({ room, from: frame.from ?? socket.id, seq: frame.seq, payload })` — bytes
   idênticos para todo frame legítimo (`seq` ausente continua omitido, `null` continua `null`).
3. Defesa em profundidade: envolver o corpo do listener `message` num `try/catch` que, em
   exceção inesperada, loga uma linha `ev("warn", "frame dropped: handler error", { id: socket.id })`
   (sem mensagem de erro com dados do frame) e fecha SÓ esse socket com `1011` — o processo
   nunca cai por causa de um frame. Não adicionar `process.on("uncaughtException")`.
4. Docs: um parágrafo curto em `docs/RELAY-HOSTING.md` (perto da seção de validação de room
   id P2-019) descrevendo a validação de forma do envelope (RT-455).
5. Teste `scripts/relay-envelope.test.ts` + registrar em `test:unit` no `package.json` (ao lado
   de `relay-rooms.test.ts`).

## Edge cases
- Frame `null`, `5`, `"x"`, `[]`, `true` → drop, socket aberto, relay vivo.
- `from` aninhado profundo (400k níveis) e `seq` aninhado profundo → drop antes do stringify.
- `from` objeto/array/número/booleano, `from` string de 129 chars → drop. `from` ausente → `socket.id` (comportamento atual).
- `from: ""` continua aceito (hoje é repassado como `""` por causa do `??`); não mudar.
- `seq`: `1.5`, `-1`, `NaN` (não existe em JSON), `1e300`, `2**53`, `"3"`, `{}` → drop; `0`, `7`, `2**53-1`, ausente, `null` → passam.
- Join (`payload: ""`) sem `seq` e com `from` curto continua juntando à sala.
- A validação roda ANTES do token bucket (como o check atual da linha 1003): frame malformado não consome budget, mesmo comportamento de JSON inválido hoje.
- Probe do healthz / testes existentes mandam `{room, from: "b1", payload: ""}` → continuam válidos.

## Acceptance criteria
- `npx tsx scripts/relay-envelope.test.ts` passa e cobre:
  (a) unidade: cada caso de Edge cases acima dá o veredito esperado; paridade
  `envelopeVerdict({room:"r",payload:"",seq:x}).ok === (frameSeq(x) !== null)` para
  `x ∈ {undefined,null,0,1,1.5,-1,2**53,2**53-1,"1",{},[]}` (import de `frameSeq` só no teste);
  o módulo `envelope.ts` não tem nenhuma linha `import`.
  (b) integração com relay real: listener + sender na mesma sala; sender manda, em sequência,
  `null`, `[]`, frame com `from` = array aninhado 400k níveis, frame com `seq` aninhado 400k
  níveis, `from` de 129 chars, `seq: 1.5`; depois um frame válido. Asserções: o processo do
  relay NÃO saiu (`proc.exitCode === null` e sem evento `exit`), o listener recebe exatamente
  1 frame (o válido), o socket do sender continua `OPEN`, e `/healthz` responde 200.
  (c) o frame válido roteado chega byte-idêntico ao formato atual:
  `{"room":…,"from":"owner","seq":3,"payload":"hello"}` e, sem `seq`, sem a chave `seq`.
- `npm run test:unit` verde (inclui `relay-rooms`, `relay-ratelimit`, `relay-healthz` inalterados).
- `npm run typecheck` verde.
- `npx tsx scripts/invariants.ts` verde.
- Reproduzir o ataque contra `main` sem o fix derruba o relay (o builder cita isso no EVIDENCE
  como prova de que o teste (b) falha sem o patch).

## Out of scope
- Validação de `seq`/`from`/replay no daemon (já coberta por RT-424, `apps/daemon/src/frameguard.ts`) e no PWA.
- Controle de frames clear `reconnect`/`pong` no PWA, hello-replay, SSRF do proxy, injeção no handoff (outros achados do red team).
- Novas métricas/contadores em `/metrics`/`/healthz` (evita mexer em consumidores do payload — lição P2-332).
- Qualquer mudança em crypto, allowlist, replay protection, `deploy/` ou `scripts/invariants.ts`.
- Handler global de `uncaughtException`/`unhandledRejection`.
