# P2-155 — recheck periódico de update

## Problem
`apps/desktop/src/main.ts:288` (`runUpdateCheck`) só é chamado em dois lugares: no boot
(`onReady`, linha 329) e no item **Check for updates** do tray (linha ~1145). Desde a P2-152 fechar
a janela mantém o app vivo indefinidamente, então um usuário que abre o app uma vez e nunca mais
toca no menu da bandeja fica preso na versão instalada para sempre — o que esvazia a P2-146 (feed
público `update-mac.json` com download em background) e a P2-131 (`update-available-manual`).
Falta um recheck periódico, com backoff quando o feed está morto, sem tocar no consentimento da
P1-050 nem no caminho do boot/tray.

## Approach
1. **Novo módulo puro `apps/desktop/src/updateschedule.ts`** — sem importar `electron` (mesmo padrão
   de `tray.ts`, `badge.ts`, `closehint.ts`; pode importar apenas o `type UpdateStatus` de `./update`).
   Exporta as constantes e a decisão:
   - `UPDATE_RECHECK_BASE_MS = 6 * 60 * 60_000` (6 h)
   - `UPDATE_RECHECK_MIN_MS = 5 * 60_000` (piso duro de 5 min)
   - `UPDATE_RECHECK_BACKOFF_START_MS = 15 * 60_000`
   - `UPDATE_RECHECK_JITTER = 0.1` (±10 %)
   - `nextCheckDelayMs(status: UpdateStatus, consecutiveFailures: number, random: () => number): number | null`
   Regras:
   - `disabled` → `null` (não há superfície de update; zero rede).
   - `update-downloaded` → `null`: o consentimento da P1-050 já foi oferecido e só o restart aplica —
     re-checar aqui só re-ofereceria o que o usuário já decidiu.
   - `update-not-available` | `update-available` | `update-available-manual` → base com jitter:
     `BASE * (1 - JITTER + random() * 2 * JITTER)`, ou seja 5,4 h … 6,6 h.
   - `feed-unreachable` | `unrecognized-feed` → backoff exponencial, **sem chamar `random`**:
     `min(BASE, BACKOFF_START * 2 ** max(0, f - 1))` com `f` = falhas normalizadas. `f<=1` → 15 min,
     `2` → 30 min, `3` → 1 h, …, satura em 6 h (`f >= 10` já está no teto). `2 ** n` infinito satura
     igual pelo `Math.min`.
   - Normalização do contador: `Number.isInteger(f) && f > 0 ? f : 0` (negativo, fracionário, `NaN`,
     `Infinity` → `0`).
   - Clamp final em todos os ramos numéricos: `Math.max(UPDATE_RECHECK_MIN_MS, Math.round(delay))` —
     nenhuma combinação de `random` e contador pode devolver menos de 5 min, e o retorno é sempre
     inteiro finito.
2. **`apps/desktop/src/main.ts`** (só isso; boot e tray intactos):
   - módulo-level `let updateRecheckTimer: NodeJS.Timeout | null = null;` e `let updateFeedFailures = 0;`
   - `runUpdateCheck(source)`: encadear `.then((status) => scheduleNextUpdateCheck(status))` no
     `checkForUpdatesOnBoot(...)` (o valor de retorno cobre também `disabled`, que não passa por
     `onStatus`) e, no `.catch` já existente, tratar o erro inesperado como
     `scheduleNextUpdateCheck("feed-unreachable")` depois do `logError` — um throw não pode matar o
     recheck para sempre.
   - `scheduleNextUpdateCheck(status)`: se `!updatesEnabled()` → limpa o handle e retorna (nunca
     agenda); `clearTimeout` do handle anterior antes de qualquer coisa (reagendamento é idempotente);
     falhas (`feed-unreachable`, `unrecognized-feed`) incrementam `updateFeedFailures`, qualquer outro
     status resolvido (`update-not-available`, `update-available`, `update-available-manual`,
     `update-downloaded`) zera o contador; `const delay = nextCheckDelayMs(status, updateFeedFailures, Math.random)`;
     `delay == null` → não agenda; senão `updateRecheckTimer = setTimeout(() => runUpdateCheck("scheduled"), delay)`
     (pode `.unref()`), com uma linha de log opcional do atraso escolhido.
   - `app.on("will-quit")` (linha 568): limpar `updateRecheckTimer` (`clearTimeout` + `= null`)
     **antes** do `if (daemonStopped) return;`, junto do `pairingTimer`.
3. **Docs**: uma linha em `README.md` (seção de auto-update, ~linha 537) e em `README.pt-BR.md`
   (~linha 401) dizendo que o app reconfere sozinho a cada ~6 h enquanto está aberto (mesmo com a
   janela fechada na bandeja) e recua para 15 min→6 h quando o feed está fora do ar.
4. **Testes** em `scripts/unit.test.ts` (já na cadeia `test:unit`), num bloco novo
   `// --- desktop update recheck schedule (P2-155) ---`, seguindo o estilo dos blocos existentes
   (`check(...)`, import no topo a partir de `../apps/desktop/src/updateschedule`, `readFileSync`
   do `main.ts` como em `scripts/unit.test.ts:3948`).

## Edge cases
- `random()` = 0 → exatamente `0.9 * BASE` (5,4 h); `random()` = 0.999999 → `< 1.1 * BASE` e nunca
  `>= 6,6 h + 1 ms`; `random()` fora de [0,1) não pode furar o piso de 5 min (clamp).
- `consecutiveFailures` negativo, `0.5`, `NaN`, `Infinity` → tratado como `0` (15 min no ramo de falha).
- 10 falhas consecutivas → exatamente `UPDATE_RECHECK_BASE_MS`, nunca acima.
- `updatesEnabled()` falso (dev sem `OCR_UPDATE_FEED`, plataforma sem feed) → nenhum `setTimeout`,
  nenhuma requisição de rede: a P1-071 (local sem cerimônia) e a regra "zero rede quando desabilitado"
  continuam valendo.
- Reagendamento não pode empilhar timers: um check manual pelo tray durante um recheck agendado
  substitui o handle (clear antes de setTimeout).
- `update-downloaded` disparado pelo listener do `autoUpdater` (via `onStatus`) não agenda nada — o
  agendamento é derivado do valor de retorno de `checkForUpdatesOnBoot`, não de `onStatus`.
- Nada de plaintext/segredo em log novo: só status, origem e atraso em ms.

## Acceptance criteria
- `npx tsc -p apps/desktop --noEmit` (ou `npm run typecheck`) verde; `npm run build` verde;
  `npm run test:unit` verde — output real colado no EVIDENCE.
- `grep -c "electron" apps/desktop/src/updateschedule.ts` = 0 (módulo puro).
- Blocos novos em `scripts/unit.test.ts` cobrindo, com `check(...)` nomeados por `P2-155`:
  1. os 7 status: `disabled` → `null`, `update-downloaded` → `null`, os 3 de sucesso → número no
     intervalo `[19_440_000, 23_760_000]`, os 2 de falha → número.
  2. `random = () => 0` → `19_440_000` exato para `update-not-available`, `update-available` e
     `update-available-manual`; `random = () => 0.999999` → `< 23_760_001` e `> 23_759_000`.
  3. backoff crescente com 1/2/3 falhas: `900_000`, `1_800_000`, `3_600_000` para `feed-unreachable`
     e `unrecognized-feed`.
  4. 10 falhas consecutivas → `21_600_000` (teto = intervalo base), e 50 falhas idem.
  5. piso: para todo status e para `random` devolvendo `0`, `-1`, `1`, `NaN`, o resultado não-nulo é
     `>= 300_000`.
  6. contador `-1`, `-99`, `0.5`, `NaN`, `Infinity` → mesmo resultado de `0` (`900_000`).
  7. asserção lendo o `apps/desktop/src/main.ts` real (`readFileSync`) confirmando que a fonte contém
     `nextCheckDelayMs`, `runUpdateCheck("scheduled")`, um `setTimeout` guardado em
     `updateRecheckTimer` e um `clearTimeout(updateRecheckTimer)` dentro do handler de `will-quit`.
- `README.md` e `README.pt-BR.md` mencionam o intervalo de recheck (grep por `6 h`/`6h` na seção de
  auto-update retorna a linha nova).
- `git diff --stat` não toca `package.json`, `deploy/`, `scripts/invariants.ts` nem nenhum arquivo de
  crypto/handshake.

## Out of scope
- Nenhuma mudança visual: sem screenshot como evidência.
- Não alterar `package.json` (nem a cadeia `test:unit`), `deploy/`, `scripts/invariants.ts`.
- Não mexer no fluxo de consentimento da P1-050, no `attachUpdateListeners`, no `openReleasePage` da
  P2-131 nem nos caminhos de boot e de tray de `runUpdateCheck`.
- Sem novas portas, listeners de rede, IPC, preferência de usuário ou UI para configurar o intervalo.
- Sem persistir o contador de falhas em disco (é estado de sessão do processo main).
