# P1-093 — AutoMode não pode falhar em silêncio (evento WS + card acionável)

## Problem

Com AutoMode ligado, `autoApprove` (`apps/daemon/src/index.ts:1267-1308`) responde o ask no
lugar do usuário; no sucesso emite `ocr.permission.auto` (:1291-1298). No **insucesso** (POST
não-ok :1284-1288 ou exceção :1304-1307) só faz `log("warn", ...)` — nenhum evento sai.
Do lado do cliente, `reconcilePermissionCards` suprime cards quando `autoMode=true`
(`apps/web/src/lib/permissionCards.ts:101`), então o ask fica pendente e **invisível**: o agente
para esperando aprovação e o operador não tem affordance nenhuma.

## Approach

1. **Daemon** (`apps/daemon/src/index.ts`, só `autoApprove`): trocar o POST único por um loop
   de **2 tentativas** (retry 1x, delay ~500ms — manter o gate rápido). Sucesso em qualquer
   tentativa segue o fluxo atual (log, audit, broadcast `ocr.permission.auto`, push).
   Se a 2ª tentativa também falhar: `autoApproved.delete(permissionID)` (comportamento atual),
   `audit("permission.auto.failed", { sessionID, permissionID, action, error })` e **broadcast**
   do evento novo `ocr.permission.autoFailed` com `{ sessionID, permissionID, action, error }`
   (`error` = status HTTP ou message). Não emitir `autoFailed` no meio do retry — só no falha
   final. Relay intocado: segue no envelope selado, igual `ocr.permission.auto`.
2. **Módulo puro** (`apps/web/src/lib/permissionCards.ts`):
   - `CollectedAsk` ganha `autoFailed: boolean`; `collectPermissionAsks` seta
     `autoFailed: type === "ocr.permission.autoFailed"` (última ocorrência vence: um
     `ocr.permission.auto` posterior reseta o flag).
   - `reconcilePermissionCards` (:99-108): card acionável se pendente E não respondido E
     (`!autoMode` **ou** `ask.autoFailed`). Entrada acionável carrega `autoFailed?: boolean`
     para o estilo vermelho. Sem falha registrada, supressão do AutoMode continua igual
     (regressão P1-082 preservada).
3. **ChatView** (`apps/web/src/components/ChatView.tsx`):
   - Efeito irmão do handler de `ocr.permission.auto` (:873-893) para `ocr.permission.autoFailed`
     (mesmo filtro `sessionID === sessionId`): registrar o id num `Set` (ref) e setar nota
     persistente `autoFailNote` com `t("autoFailed", { action })`.
   - Render no composer, junto do badge do AutoMode (:1982-1986): nota vermelha
     (`color: var(--danger)`, `role="alert"`) enquanto houver id falhado ainda pendente; limpar
     quando o card for respondido/sair do pending. O card acionável aparece sozinho via
     `reconcilePermissionCards` (:1040-1045) — estilizá-lo com borda/detalhe `--danger`.
   - O re-fetch debounced de `/permission` já dispara (tipo contém "permission", :622-639).
4. **i18n** (`apps/web/src/lib/i18n.ts`): chave `autoFailed` en + pt-BR, ex. "AutoMode couldn't
   approve: {action} — manual review needed" / "AutoMode não conseguiu aprovar: {action} —
   aprove manualmente".
5. **Desktop-flow** (`scripts/desktop-flow.test.ts`): nova fase no boot-2 hermético (fake
   backend do P1-089, :1102-1141):
   - Fake: `POST /session/ses-autofail/permissions/perm-fail` → **500 sempre**; `GET /permission`
     → `[{ id: "perm-fail", sessionID: "ses-autofail", permission: "bash" }]` (sessão dedicada,
     não colide com os beats existentes).
   - Ligar AutoMode pela UI real (Settings → toggle `autoModeLabel`, SettingsView.tsx:394) —
     fluxo de usuário, nada de editar state file na mão.
   - Abrir `#/session/ses-autofail`, emitir via `/__emit` um
     `{ type: "permission.updated", properties: { sessionID: "ses-autofail", permissionID: "perm-fail", type: "bash" } }`.
   - Asserções (`waitProbe`/ipc): nota vermelha visível no composer; card acionável com botões
     approve/deny **apesar** do AutoMode; `/__hits` registra **exatamente 2** POSTs na
     permission (retry 1x, não loop); shot de evidência 1440x900 (+390 se barato).
   - Subir `DEADLINE_MS` (165_000 → ~180_000) e atualizar a menção "<165s" no AGENTS.md.

## Edge cases

- Sucesso no retry (1ª falha, 2ª ok): só o evento de sucesso, nota vermelha nunca aparece.
- `autoFailed` de outra sessão: filtrado por `sessionID`, não vaza pra view atual.
- Usuário responde o card: id sai do pending → nota e card somem; mapa `autoApproved` foi
  limpo na falha, então ask novo do mesmo id re-tenta auto-aprovar.
- Evento `ocr.permission.auto` depois do `autoFailed` (ask re-emitido): última ocorrência vence,
  estado volta a "auto" — sem nota presa.
- 404 do opencode (resolvido em outro lugar durante o retry): treated as failure → evento;
  clique em card stale segue mapeado por `isPermissionResolvedElsewhere` (P1-082).
- Não quebrar checks existentes do permission-cards (`autoMode=true → 0 actionable` vale só
  para asks **sem** falha registrada).

## Acceptance criteria

- `npm run typecheck` → 0 erros; `npm run build` → ok; `npm run test:unit` → verde, com os
  novos checks em `scripts/permission-cards.test.ts`: (a) autoMode + pendente + `autoFailed`
  → 1 acionável com `autoFailed=true`; (b) autoMode + pendente sem falha → 0 acionáveis;
  (c) `autoFailed` seguido de `ocr.permission.auto` → linha resolved "auto", não acionável;
  (d) `autoFailed` de outra sessão ignorado.
- `npm run test:desktop-flow` → verde: nova fase prova (1) sinal vermelho visível no composer,
  (2) card acionável renderizado com AutoMode on, (3) exatamente 2 POSTs no fake, (4) shot de
  evidência salvo.
- Comportamento: com AutoMode on e opencode rejeitando o approve, o operador vê nota vermelha
  + card de aprovação em ≤ ~2s após o ask — nunca mais falha em silêncio.
- Sem mudanças em `apps/relay/`, `scripts/invariants.ts`, `deploy/`; nenhum listener novo;
  relay continua roteador cego.

## Out of scope

- Backoff maior, N retries ou fila de reprocessamento (retry fixo 1x).
- Políticas por ferramenta / allowlist de permissões; histórico persistido de falhas.
- `question.asked` sem affordance análoga (mesma classe de bug, task própria).
- Mudanças no fluxo de criptografia/handshake (evento novo só herda o envelope selado).
