# P2-218 — abertura no login ligada no primeiro boot empacotado, reversível e anunciada

## Problem
A abertura no login só existe como checkbox do menu da bandeja (`apps/desktop/src/main.ts:1713-1724`,
suportada em macOS/Windows via `loginItemSupported` em `apps/desktop/src/tray.ts:13`). O padrão é o do
sistema operacional — desligado — e nenhum arquivo de `apps/desktop/src` liga isso sozinho. O usuário
leigo do estágio 3 de `docs/VISION.md` instala, pareia pelo QR e perde a máquina inteira no primeiro
reboot, corte de energia ou logout: do telefone isso aparece como máquina sumida, sem causa. A P2-209
(`wakeplan.ts`) só reage ao retorno de suspensão e o respawn do sidecar (`daemon.ts`) só cobre o daemon
morto — nenhum dos dois alcança o caso do aplicativo simplesmente não estar rodando.

## Approach
1. **`apps/desktop/src/loginitem.ts`** (novo, puro — sem `electron`, sem `node:fs`, sem `fetch`, mesma
   higiene de `wakeplan.ts` / `installloc.ts` / `closehint.ts`): `loginItemPlan({ packaged, platform,
   alreadyEnabled, ownerDecided })` → `{ action: "enable" | "leave", reason }`, regras NESTA ordem:
   (1) `!packaged` → leave (máquina de desenvolvimento nunca tem o ajuste mexido); (2) plataforma fora
   de `darwin`/`win32` → leave (documentado no cabeçalho: a API é no-op fora dessas duas); (3)
   `ownerDecided` → leave, inclusive com o ajuste desligado (escolha do dono vence o padrão e nunca é
   revertida em boot nenhum); (4) `alreadyEnabled` → leave; (5) só o primeiro boot empacotado sem
   decisão → enable. Exporta também `loginItemMessage(action)` — a frase calma do overlay — e mantém
   toda string em pt-BR curto, sem caminho, sem esquema de URL e sem segredo (barra P2-140).
2. **`apps/desktop/src/startupstore.ts`** (novo, mesmo padrão de `relaystore.ts`): `startupSettingFile(userData)`
   → `<userData>/startup.json`; `writeStartupDecided(file, decided)` escreve `{ "decided": true }` em
   `<file>.tmp` com `mode: 0o600` + `renameSync` (tmp removido em qualquer falha, log-only, retorna
   boolean); `readStartupDecided(file)` é tolerante — arquivo ausente, ilegível, JSON corrompido ou
   campo de tipo errado devolvem `false`, jamais exceção; ENOENT permanece silencioso. Guarda SOMENTE
   o booleano — nunca nome de usuário, caminho ou credencial.
3. **`apps/desktop/src/main.ts`**: novo `let bootStartup: LoginItemVerdict | null = null;` ao lado de
   `bootInstallLocation` (linha 100) e um helper compartilhado `setLoginItemEnabled(enabled: boolean)`
   que é o ÚNICO chamador de `app.setLoginItemSettings({ openAtLogin })` e sempre grava
   `writeStartupDecided(startupSettingFile(app.getPath("userData")), true)`. Em `onReady()`, logo após
   o bloco de install-location e ANTES de `runUpdateCheck("boot")`, o plano é consultado UMA única vez
   com `app.isPackaged`, `process.platform`, `app.getLoginItemSettings().openAtLogin` e
   `readStartupDecided(...)`; em `action === "enable"` chama `setLoginItemEnabled(true)` e loga uma
   linha `[desktop] login item: <action> (<reason>)`. O clique do item de bandeja passa a ser
   `click: (item) => setLoginItemEnabled(item.checked)`, então desligar na bandeja registra a decisão e
   é definitivo. Nenhuma sonda periódica nova, nenhuma requisição nova, nenhum intervalo existente alterado.
4. **Payload + UI**: `PairingState` em `apps/desktop/src/pairing.ts` ganha `startup?: { state: string;
   message: string }` DEPOIS de `clock` (linha 102), e o objeto de `setPairingState({...})` em
   `main.ts:1255-1289` acrescenta `startup:` como ÚLTIMO campo, depois de `clock` — nenhum campo
   existente removido ou renomeado, para as asserções de fonte real da P2-189/P2-193/P2-197/P2-199/
   P2-211/P2-214 continuarem casando. `apps/web/src/App.tsx` espelha o campo no tipo (junto de `clock`,
   linha 116) e passa `startup={pairingState?.startup ?? null}` (linha 783). `PairingOverlay.tsx`
   renderiza `<p className="pair-startup">{startup.message}</p>` logo ABAIXO da linha de relógio,
   somente quando `startup.state === "enable"`; ausente ou qualquer outro estado = desconhecido =
   nada renderizado. Comentário obrigatório no JSX afirmando que a linha NUNCA esconde o QR nem
   bloqueia o pareamento (é anúncio, não erro). `apps/web/src/index.css`: `.pair-startup` copiando os
   tokens de `.pair-clock` (2039-2078), tom `--muted` (sem `--warn`, sem badge, sem gradiente, sem
   emoji, sem raio novo). `apps/desktop/src/diagnostics.ts`: campo aditivo `startup?: { state: string;
   reason: string } | null` e UMA linha nova `login item: <state> (<reason>)` — estado e motivo apenas,
   jamais caminho, mantendo o contrato de privacidade do cabeçalho.
5. **Hatch de teste + docs**: `OCR_DESKTOP_FORCE_LOGIN_ITEM=1` (mesma política OCR_* de
   `OCR_DESKTOP_FORCE_DMG_VOLUME` / `OCR_DESKTOP_CAMERA_BLOCK`) força o veredito `enable` para o
   payload, o diagnóstico e o screenshot. Sob o hatch a ação NÃO chama `setLoginItemEnabled` e NÃO
   grava decisão — a máquina de desenvolvimento continua intocada (constituição do próprio módulo).
   README.md (perto de 617/1171), README.pt-BR.md (perto de 639) e docs/troubleshooting.md (linha da
   tabela + nova seção curta no padrão da "After sleep and wake (P2-209)") documentam: o app empacotado
   passa a abrir no login no primeiro boot, por que isso é necessário para o telefone achar a máquina, e
   que desligar em **Start at login** na bandeja é definitivo (nenhum boot futuro religa).

## Edge cases
- Build de desenvolvimento (`app.isPackaged === false`): leave mesmo sem decisão registrada — o ajuste
  do dev nunca é tocado.
- Linux e qualquer outra plataforma: leave; a API é no-op e o item de bandeja já é escondido por
  `loginItemSupported`.
- Decisão registrada + ajuste desligado: leave (o dono desligou na bandeja; nenhum boot futuro religa).
- `startup.json` ausente/corrompido/`decided: "sim"`: lê como "sem decisão" — no primeiro boot
  empacotado o pior caso é religar uma vez, nunca uma exceção no boot.
- `setLoginItemSettings` lançando (disco cheio, permissão): try/catch log-only, o shell não cai.
- Payload legado sem `startup` (daemon/shell antigo): renderer trata como desconhecido e não renderiza nada.
- Overlay: `enable` aparece somente no boot em que a ação foi enable (o veredito é do boot, não é
  recomputado por tick), e nunca esconde/dim o QR.

## Acceptance criteria
- `npm run typecheck`, `npm run build`, `npm run test:unit` e `npm run test:desktop-flow` verdes, com
  output real colado no EVIDENCE.
- Bloco novo em `scripts/unit.test.ts` (já na cadeia `test:unit`) cobrindo a tabela completa de
  `loginItemPlan`: dev sem decisão → leave; plataforma fora de darwin/win32 → leave; decisão registrada
  com ajuste desligado → leave; decisão registrada com ajuste ligado → leave; ajuste já ligado sem
  decisão → leave; primeiro boot empacotado sem decisão → enable; e toda mensagem/`reason` gerada
  não-vazia, sem `/`, `\`, `http:`, `https:` nem `file:`.
- Tabela do store em `mkdtempSync(join(tmpdir(), ...))`: arquivo ausente → `false`; JSON corrompido →
  `false`; `{"decided":"sim"}` → `false`; ida e volta `writeStartupDecided` → `readStartupDecided` →
  `true`; e `statSync(file).mode & 0o777 === 0o600`.
- Asserções lendo o `main.ts` real: `(mainSrc.match(/loginItemPlan\(/g) ?? []).length === 1`;
  `indexOf("bootStartup = ") < indexOf('runUpdateCheck("boot")')`; a fatia do boot até

## Out of scope
Não instala serviço de sistema, não cria launch agent próprio, não mexe em nenhum ajuste do sistema
além do próprio item de login do aplicativo. Não altera a janela, o fechar-para-bandeja nem o lock de
instância única. Não altera o respawn do sidecar nem a política de backoff. Não altera `apps/daemon`
nem `apps/relay`. Não toca crypto E2E, allowlist de dispositivos nem proteção de replay. Não altera
`scripts/invariants.ts` nem `deploy/`. Nenhuma dependência nova; `package.json` intocado.
