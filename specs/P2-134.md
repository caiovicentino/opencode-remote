# P2-134 — Merge bloqueado por conflito com main vira rebase, não attempt queimado

## Problem
`mergePrForTask` (`apps/pilot/src/pipeline.ts:2378`) confirma o merge lendo só
`gh pr view <n> --json state,headRefOid`. Um PR que o GitHub já marcou como
`mergeable: CONFLICTING` / `mergeStateStatus: DIRTY` nunca vai para `MERGED`:
o loop queima os 60 polls × 5s (`PR_MERGE_CONFIRM_POLLS`) e devolve
`infra: "timeout"` com detail genérico "merge unconfirmed after ~5min". O ciclo
seguinte reabre o mesmo PR com o mesmo conflito, e como o branch preservado
(`setupTaskBranch`, `apps/pilot/src/pipeline.ts:255`) nunca é rebaseado em
`origin/main`, o conflito é permanente. Foi assim que P2-117, P2-123 e P2-126
morreram em 4 attempts com o gate verde — o mérito estava certo, a base é que
estava velha. Conflito com main causado pelo merge de outro slot é infra, não
mérito: hoje ele custa 5 min de poll por ciclo e attempts que não deveriam ser
debitados.

## Approach
1. **Poll enxerga o bloqueio** — a query do poll passa a ser
   `gh pr view <n> --json state,headRefOid,mergeable,mergeStateStatus`. Nova
   função pura exportada `mergeBlockReason(snap: { mergeable?: unknown;
   mergeStateStatus?: unknown }): string | null` em `pipeline.ts`, ao lado de
   `mergePrForTask`: devolve o motivo (`"mergeable=CONFLICTING"` /
   `"mergeStateStatus=DIRTY"`, ambos quando os dois batem) quando
   `mergeable === "CONFLICTING"` **ou** `mergeStateStatus === "DIRTY"`, e `null`
   em qualquer outro caso — inclusive campos ausentes, `MERGEABLE`, `UNKNOWN`,
   `BLOCKED`, `BEHIND` (o poll continua exatamente como hoje).
   Ordem dentro do loop, sem alterar a semântica atual: (a) head diferente do
   nosso sha → mérito; (b) `state === "MERGED"` → sucesso/anomalia; (c) só
   então `mergeBlockReason(snap)` — se não for `null`, **sai do loop no poll
   corrente** com `{ ok: false, infra: "conflict", detail: \`PR #<n> blocked:
   <reason> — merge exec: <mergeTail>\` }`. O `ghTail`/`mergeTail` de 300 chars
   continua carregando a razão real do `gh` (lição P2-125).
2. **Novo kind infra** — `"conflict"` entra em `InfraFailureKind`
   (`apps/pilot/src/audit.ts:60`). Nada mais muda em `audit.ts`:
   `resultInfraKind` já roteia por campo estruturado, então o caminho de
   `apps/pilot/src/index.ts:480` poupa attempt e janela de febre sozinho, e a
   linha `infra: merged.infra` de `pipeline.ts:1919` já propaga.
3. **Rebase no resume** — em `setupTaskBranch`, depois do
   `git checkout -q <branch>` que setou `resumed = true` e antes do log
   "branch preserved", roda `exec("git rebase origin/main", { cwd: ws,
   allowFail: true })`. Nova função pura exportada `rebaseOutcome(r: { ok:
   boolean; output: string }): "clean" | "conflict"` interpreta o resultado
   (`r.ok` ⇒ `"clean"`, senão `"conflict"`). No caminho `"conflict"`, fail-closed
   no espírito da P2-114: `git rebase --abort` (allowFail), branch permanece
   intacta na base antiga, log `warn` com `task`, `attempt` e a cauda (≤300
   chars) do output do rebase, e `setupTaskBranch` continua devolvendo `true`
   — o builder resolve no round seguinte. **Nunca** `git reset --hard
   origin/main` sobre histórico preservado (lição P1-060). O caminho fresh
   (attempt 0 / branch ausente) não roda rebase: já nasce em `origin/main`.
4. **Gate re-executa** — o rebase limpo reescreve os commits, o sha muda, e o
   gate determinístico do ciclo seguinte roda sobre o novo HEAD como qualquer
   attempt. Nenhum merge acontece sobre certificação velha; nenhuma mudança é
   necessária no gate para isso.
5. **Docs** — parágrafo curto em `docs/PILOT.md`, logo após o bloco "Merge de PR
   que falha é infra, não mérito (P2-125)" (linha ~634), documentando o kind
   `conflict` e o rebase do branch preservado.

- `apps/pilot/src/audit.ts` — `InfraFailureKind` ganha `"conflict"`.
- `scripts/unit.test.ts` — novos blocos P2-134 (imports de `mergeBlockReason` e

- `package.json` — **não é alterado** (`test:unit` já roda `scripts/unit.test.ts`).

## Edge cases
- Snapshot sem `mergeable`/`mergeStateStatus` (gh antigo, JSON parcial) ⇒
  `mergeBlockReason` devolve `null` e o poll segue o comportamento de hoje até
  o budget — nunca aborta por campo ausente.
- `mergeable: "UNKNOWN"` (GitHub ainda calculando) não é bloqueio: continua
  polando; o cálculo vira `CONFLICTING` ou `MERGEABLE` em polls seguintes.
- `state === "MERGED"` com `mergeable` residual `CONFLICTING`/`UNKNOWN` ⇒
  sucesso: a checagem de MERGED vem antes da de conflito.
- Head diferente do nosso sha continua mérito (`infra` indefinido), mesmo com
  o PR conflitante — a ordem das checagens preserva isso.
- Rebase conflitante deixa a árvore de rebase pela metade: o `--abort` é
  obrigatório, e o worktree tem de voltar limpo na ponta da branch preservada.
- Rebase sem identidade de git configurada / `origin/main` inexistente ⇒
  `allowFail` + `rebaseOutcome === "conflict"` ⇒ abort + log; nunca lança.
- Branch preservada já em cima de `origin/main` ⇒ rebase é no-op `ok`, sha não
  muda, nada a fazer.
- `clearCheckpoint` continua exclusivo do caminho fresh; o checkpoint é salvo
  depois de `setupTaskBranch`, então o rebase não o invalida.
- `mergeBlockReason` recebe `unknown` (JSON externo): trate valores não-string
  como ausentes, sem lançar.

## Acceptance criteria
Novos blocos em `scripts/unit.test.ts` (já na cadeia `npm run test:unit`),
com io falso zero-rede no molde do bloco P2-125 e git real no molde do bloco
P1-036:
1. `mergeBlockReason`: `CONFLICTING` ⇒ string não vazia citando `CONFLICTING`;
   `DIRTY` ⇒ string citando `DIRTY`; `{}`, `MERGEABLE`, `UNKNOWN`, `BLOCKED`,
   `BEHIND` e valores não-string ⇒ `null`.
2. PR conflitante: io falso cujo `gh pr view` devolve
   `{state:"OPEN",headRefOid:<nosso sha>,mergeable:"CONFLICTING",mergeStateStatus:"DIRTY"}`
   ⇒ `ok === false`, `infra === "conflict"`, `detail` cita `CONFLICTING`,
   **exatamente 1** chamada `gh pr view` e **0** sleeps.
3. PR mergeável: `{state:"MERGED",headRefOid:<nosso sha>,mergeable:"UNKNOWN"}`
   ⇒ `ok === true` (MERGED vence a checagem de conflito).
4. Snapshot sem `mergeable`: `{state:"OPEN",headRefOid:<nosso sha>}` ⇒
   `infra === "timeout"` e `PR_MERGE_CONFIRM_POLLS` chamadas de `gh pr view`
   (comportamento de hoje intacto).
5. Query pinada: alguma chamada casa
   `gh pr view <n> --json state,headRefOid,mergeable,mergeStateStatus`.
6. `resultInfraKind({ ok:false, infra:"conflict" }) === "conflict"` e, aplicando
   o caminho de `index.ts`, `Object.keys(st.taskAttempts).length === 0` e
   `feverReason(st) === null`.
7. `rebaseOutcome({ok:true,output:""}) === "clean"` e
   `rebaseOutcome({ok:false,output:"CONFLICT (content)"}) === "conflict"`.
8. Rebase limpo (git real): origin/main avança em `a.txt`, branch preservada
   commita `b.txt`; `setupTaskBranch(ws,"P2-134T",1) === true`, HEAD é
   `pilot/P2-134T`, `git merge-base --is-ancestor origin/main HEAD` passa,
   `b.txt` e `a.txt` existem no worktree.
9. Rebase conflitante (git real): ambos os lados editam o mesmo arquivo;
   `setupTaskBranch(...,1) === true`, `git rebase --abort` deixou a branch no
   sha preservado original, `git status --porcelain` vazio, sem diretório
   `.git/rebase-merge`/`.git/rebase-apply`, e o conteúdo da branch (não o de
   main) está no worktree.
10. Primeira attempt: `setupTaskBranch(ws,"P2-134U",0) === false` e a branch
    aponta para `origin/main` — nenhum rebase rodou.
11. `npm run typecheck`, `npm run build` e `npm run test:unit` verdes, com
    output real colado no EVIDENCE.
12. `git diff --name-only` não inclui `package.json`.

## Out of scope
- Alterar o orçamento de polls (`PR_MERGE_CONFIRM_POLLS`/`_DELAY_MS`).
- Qualquer fallback de merge local ou push direto em main (P1-076).
- Resolver conflitos automaticamente (merge/rebase com estratégia, `-X ours`)
  ou dar `reset --hard` na branch preservada.
- Mudar `scripts/invariants.ts`, `deploy/` ou a cadeia do gate.
- Mudar classificação de qualquer outro kind infra existente.
