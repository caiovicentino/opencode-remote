# P1-071 — First-boot explorer: journey review with clean state

## Problem

The pipeline reviews diffs against specs, but nobody reviews the *product premise*.
40+ tasks passed adversarial review without anyone asking "why would a local desktop
app ask for pairing?" (the P1-070 blind spot). The nightly explorer (P3-052) explores
like a first-time user but reuses the long-lived `explorer` session and starts its
prompt mid-journey ("pairing screen"), never freezing a true first-boot observation
as evidence.

## Approach

1. **Fresh-state explorer pass** (`apps/pilot/src/explorer.ts`):
   - Add exported `explorerSessionName(today: string): string` → `explorer-fresh-YYYYMMDD`
     (digits, no spaces — safe as a `OCR_DESKTOP_SESSION` key). Each run gets a session
     never used before, so `tools/desktop.mjs`'s keeper spawns fresh → `hermeticEnv()`
     mints a brand-new temp userData (true first install).
   - `runExplorer` computes the session once and passes it to `explorerPrompt(shotsDir, session)`;
     `explorerPrompt` becomes exported (pure, for tests) and uses `OCR_DESKTOP_SESSION=<session>`.
   - Rewrite the prompt to a first-boot journey review with the SAME budget constants
     (`EXPLORER_MAX_STEPS`, 25min, 5 findings) and output format (`EXPLORER: FINDING` /
     `EXPLORER: DONE`). New mandatory structure:
     a. First harness command: `shot <shotsDir>/first-boot-<YYYYMMDD>.png 1440 900` —
        untouched first screen, before any interaction.
     b. Answer premise questions in findings: why does a local app show an auth/pairing
        ceremony? Is every flow reachable from first boot? What are the empty states?
     c. Second boot (best-effort, same session) with `OCR_DAEMON_FORCE_RECONNECTING=1`
        — the hermetic "daemon detected, first contact" state (existing P1-053 knob,
        no harness changes). `close` between boots; `close` at the end.
   - Parser, backlog insertion and push flow (`parseExplorerFindings`, `explorerSpec`,
     `commitAndPushFindings`) stay untouched — findings still require a real shot on disk.
2. **Reviewer premise line** (`apps/pilot/src/pipeline.ts`, `reviewerPrompt` ~line 473):
   add one rule bullet for all roles: "Product premise: if the diff presupposes a user
   flow (auth, onboarding, connection), question the premise, not just the implementation."
3. **Constitution gains a product invariant**: append to `CONSTITUTION` (pipeline.ts:15)
   item 7: "Product premise: local = no auth ceremony; every flow must be reachable from
   first boot." Reviewers/red team read it via `${CONSTITUTION}` automatically.
   **Constitution-change flag:** commit message must carry `constitution-change:` in the
   body (docs/CONSTITUTION.md rule) — this adds a rule, removes none; `scripts/invariants.ts`
   is NOT touched (this invariant is judgment-enforced, not machine-checked).
4. **Docs**: docs/CONSTITUTION.md gets a short "Product invariants (judgment)" section
   (explicitly NOT verified by invariants.ts); docs/PILOT.md's P3-052 section (~line 841)
   documents the fresh-state first-boot pass; AGENTS.md explorer sentence gains "fresh-state
   first-boot pass (clean userData)".

## Edge cases

- Stale keeper of a previous same-named session would be *reused* (state not fresh):
  per-run date suffix makes collision impossible; if `open` returns `reused:true`, the
  prompt says to `close` then `open` once more (counts toward the 24-command budget).
- P1-070 already merged → fresh boot lands in local mode with no QR: the explorer must
  report only what the shot actually shows (no invented pairing findings; evidence-exists
  rule already enforces shots, not truth).
- Explorer crashes mid-run / never prints `EXPLORER: DONE`: existing non-blocking path
  (log-only, no findings filed, no throw).
- First-boot shot missing or wrong size: findings citing it are dropped by
  `parseExplorerFindings` (file-exists check); the run can file other valid findings.
- Two boots must fit `EXPLORER_MAX_STEPS=24`: prompt instructs ≤10 commands per boot phase.
- Constitution item 7 must not weaken items 1–2 (no auth-surface relaxation) — it only adds
  a product premise; text must not touch handshake/replay/0600 wording.

## Acceptance criteria

- `npm run typecheck` and `npm run test:unit` pass, including new checks:
  - `explorerSessionName("2026-09-02") === "explorer-fresh-20260902"`.
  - `explorerPrompt(dir, session)` contains `OCR_DESKTOP_SESSION=explorer-fresh-`,
    `first-boot-`, `1440 900` and the premise question text; still ends with
    `Your LAST line of output must be exactly: EXPLORER: DONE`.
  - `reviewerPrompt("SECURITY", …)` and `("QUALITY", …)` both contain "question the premise".
  - `CONSTITUTION` contains "first boot" and item 7.
- Nightly behavior (evidence in pilot log, non-blocking): during the 03:00 window
  `runExplorer` logs start with session `explorer-fresh-<date>`; afterwards
  `~/.opencode-remote/pilot/shots/explorer/first-boot-<date>.png` exists with 1440x900
  dimensions, and ≥1 journey finding is filed in `## Ready` whose spec cites that shot
  (`(severity: …, evidence: …first-boot…)`) — the P1-070 premise violation is expected to
  be rediscovered while pairing is still the first screen.
- `node tools/desktop.mjs` CLI/protocol unchanged; `grep -c "desktop.mjs" docs/PILOT.md`
  still documents the harness (no new ports, no listeners added).

## Out of scope

- Any change to `tools/desktop.mjs` commands, socket protocol or security model.
- `scripts/invariants.ts` / `deploy/` (constitution stays judgment-enforced here).
- Fixing the journey findings themselves (they become backlog tasks, incl. possibly P1-070
  re-verification — not this task's work).
- Explorer parser/budget/push semantics, escalation-reviewer mechanics, red-team pass.
- Mobile/web (non-desktop) first-boot journeys.
