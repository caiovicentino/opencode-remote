# P1-064 — Troca de sessão lenta: fetch duplo + histórico integral sem paginação

## Problem

Abrir uma sessão grande trava o app com skeleton eterno. Causas reais verificadas:

1. **Fetch duplo do histórico integral**: `loadHistory` (apps/web/src/components/ChatView.tsx:457)
   e `loadToolHistory` (ChatView.tsx:317, disparada ao abrir o drawer de atividade
   ChatView.tsx:1329) fazem ambos `GET /session/<id>/message` SEM paginação — o
   segundo é redundante: `loadHistory` já popula `historyTools` com
   `toolsFromRows(rows)` (ChatView.tsx:480).
2. **Daemon proxya sem cortar**: o passthrough genérico (apps/daemon/src/index.ts:714)
   repassa a resposta integral do opencode (MBs de tool output em sessões do pilot).
3. **Quadro de 1MB do relay**: `MAX_FRAME = 1_000_000` (apps/relay/src/index.ts:23) —
   resposta que estoura 1MB derruba o WS: a op nunca resolve e o skeleton fica
   eterno até o timeout default de 60s (client.ts:628). É a causa provável do
   relato "skeleton eterno ao alternar chats".
4. O render já é janelado (MSG_WINDOW=200, ChatView.tsx:214), mas o JSON integral
   ainda cruza relay+parse. Não há cache: voltar pra sessão recente refetcha tudo.

## Approach

1. **Fetch único** (ChatView.tsx): `loadHistory` é a única fonte. O botão do
   drawer (linha ~1329) NÃO refetcha se `historyTools.size > 0`; só refetcha
   quando vazio (sessão recém-aberta com fetch falho). Assinar `loadHistory` com
   `timeoutMs = 10_000` (4º arg de `request`, já suportado, client.ts:628).
2. **Paginação leve no daemon** (apps/daemon/src/index.ts): interceptar
   `GET /session/<id>/message` com `?limit=N&before=<messageID>` ANTES do
   passthrough. O daemon busca as rows no opencode (loopback, rápido), fatia a
   cauda e responde envelope `{ rows, hasMore, oldest, total }`; sem os params,
   passthrough byte-a-byte igual hoje (compat: export index.ts:519, handoff
   index.ts:1860, syncs internos index.ts:906/926/2135). Guarda de tamanho: se o
   JSON da página passar ~800KB (< MAX_FRAME do relay com folga), reduz `limit`
   até caber. `limit` máx. 200.
3. **Client paginado** (ChatView.tsx): abertura pede `?limit=50` (últimas 50);
   `winStart`/`pageOlder` continuam servindo o render local, e quando a janela
   chega na borda do que foi fetchado (`hasMore`), botão "carregar mais"
   busca `?limit=100&before=<oldest>` e faz prepend nas bubbles (manter o
   restore de scroll de `prePagingHeight`). `toolsFromRows` roda sobre o array
   acumulado.
4. **Cache das últimas 3 sessões**: novo `apps/web/src/lib/sessionCache.ts` —
   LRU Map<sessionId, { bubbles, historyTools, hasMore, oldest, savedAt }> em
   escopo de módulo (máx. 3, evict FIFO do mais antigo). No mount/troca de
   sessionId, ChatView hidrata sincronamente do cache (render imediato, sem
   skeleton) e refetcha a cauda em background; resposta nova substitui o estado.
5. **Timeout + erro explícito**: falha/timeout do fetch de histórico seta
   `loadingHistory=false`, mostra mensagem de erro humanizada (lib/errors) e
   botão **Retry** que re-dispara `loadHistory` — nunca skeleton infinito.
6. **Bônus — agrupar sessões do pilot** (SessionsView.tsx): títulos que casam
   `/\bP\d-\d{3}\b/` viram grupo "Pilot" colapsado no fim da lista (botão
   chevron, contagem; aberto via clique). Busca/keydown normal não muda.
   Estilo chips/typography existentes (design bar: Linear/Raycast — nada de
   emoji/gradiente).

## Edge cases

- Sessão vazia: `hasMore=false`, botão "carregar mais" não renderiza.
- `before` de messageID inexistente (rewind/unrevert): daemon responde página a
  partir da cauda disponível; client substitui as bubbles (nunca concatena duplicado).
- `revertTo`/`unrevert` (ChatView.tsx:840/855) e resync pós-reconexão
  (ChatView.tsx:600) chamam `loadHistory()` — devem refetchar a cauda e
  RESETAR o acumulado (evitar overlap/duplicação de IDs).
- Bolhas novas durante o fetch: watermark `lastEventId` e merge do stream
  continuam valendo; prepend de página antiga não mexe no tail.
- Cache hidrata estado obsoleto: refetch background sempre roda; se a sessão
  mudou no meio, `alive`/`sessionIdRef` descartam a resposta atrasada.
- Frame >1MB mesmo com guard: guard do daemon corta antes (800KB), unit cobre.
- Lista de sessões: sessões pilot renomeadas pelo usuário seguem no grupo
  (heurística por título) — documentar limitação.

## Acceptance criteria

1. `npm run typecheck --silent`, `npm run build --silent`, `npm run test:unit
   --silent` e `npm run test:desktop-flow --silent` verdes.
2. Unit (scripts/unit.test.ts) contra os helpers reais:
   a. 500 rows sintéticas → slice `limit=50` retorna exatamente as 50 finais,
      `hasMore=true`, `oldest` = id da 451ª; `before=<id da 451ª>` retorna as
      100 anteriores.
   b. Página cujo JSON exceda 800KB é fatiada até caber (teste com tool output
      de 200KB/row).
   c. Sem `limit`/`before` → passthrough: corpo idêntico ao de hoje (array puro).
   d. LRU do cache: mantém 3, evicta o mais antigo, `get` de ID desconhecido = null.
3. Network: abrir sessão dispara exatamente UM `GET /session/<id>/message`
   com `limit=50` (assert via desktop-flow ou log de audit do daemon); toggle do
   drawer de atividades não gera segundo fetch quando `historyTools` já tem dados.
4. Performance (unit, daemon real via scripts/integration.ts-style): resposta
   de cauda de 50 rows para sessão de 500 mensagens < 500ms e < 100KB.
5. Comportamento: timeout simulado (fetch que não resolve) → erro visível +
   botão Retry em ≤10s, sem skeleton remanescente; Retry refaz o request.
6. Alternar A→B→A com cache morno pinta A imediatamente (sem skeleton) —
   coberto por unit do hydrate do sessionCache + build.
7. Grupo "Pilot" colapsado visível na lista quando ≥1 título casa a heurística;
   screenshots 1440x900 e 390px no EVIDENCE (shots/builder/).

## Out of scope

- Virtualização real de DOM (react-window etc.) — o windowing atual basta.
- Mudar a API do opencode server (OPENCODE_URL) ou o formato do envelope E2E.
- Cripto E2E, allowlist, replay guard, `deploy/`, `scripts/invariants.ts` — intocados.
- Path de export (`/__ocr/export`) e syncs internos do daemon continuam full-history.
- Prefetch proativo de sessões, TTL do cache além de memória, persistência em disk.
- Deletar/arquivar sessões do pilot na lista (só agrupar).
