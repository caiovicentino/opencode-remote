# P3-344 — Rejeitar um cliente não pode derrubar o socket do relay inteiro

## Problem
No handler de `hello` (`apps/daemon/src/index.ts:3040-3052`), o caminho de rejeição envia o
`rejectPayload` e chama `setTimeout(() => ws.close(), 500)`. Mas `ws` ali é o **único socket
compartilhado com o relay** (`relaySocket`, `apps/daemon/src/index.ts:3167`): fechá-lo derruba a
sessão de **todos** os clientes pareados (o handler de `close` apaga toda sessão com
`s.socket === ws`, `index.ts:3205-3207`). Um único client zumbi — aba antiga da PWA com identidade
revogada, auto-reconnect a cada ~8s — vira um loop: `paired` → `rejected` → `relay connection lost`
→ backoff → todos reconectam (evidência: daemon.log 19:29-19:31; o "Telefone 1" recém-pareado morre
junto).

O mesmo defeito existe na revogação pelo app (`index.ts:1037-1041`): `s.socket.close()` fecha o
socket do relay quando o device revogado estava conectado via relay — revogar um telefone derruba
todos os outros.

Segundo problema (observabilidade): todo log/audit usa `pub.slice(0, 16)`. Os 16 primeiros chars do
base64 do SPKI são o header ASN.1 constante de **qualquer** chave P-256 — a string é idêntica para
todos os devices e não identifica nada. O mesmo vale para o `…${pub.slice(-6)}` da linha de audit em
`apps/web/src/components/SettingsView.tsx:1368`.

## Approach
1. **Módulo puro novo** `apps/daemon/src/clientfp.ts` (sem `node:fs`/`node:http`/`ws` — mesmo padrão
   de `pairwindow.ts`/`devicetouch.ts`, porque `index.ts` roda `main()` no import):
   - `pubFingerprint(pub: unknown): string` — sha-256 (`node:crypto` `createHash`, sem I/O) sobre os
     **bytes DER decodificados** do base64, primeiros 16 chars hex minúsculos. Entrada não-string,
     vazia ou que decodifica para 0 bytes → `"unknown"`.
   - `REJECT_WARN_INTERVAL_MS = 60_000` e
     `rejectLogDecision(lastWarnAt: number | undefined, now: number): "warn" | "silent"` — puro,
     `now` injetado. Ordem de regras fixa e documentada: (a) `lastWarnAt` ausente/não-numérico →
     `warn`; (b) `lastWarnAt > now` (relógio voltou) → `silent`; (c) `now - lastWarnAt >= intervalo`
     → `warn`; (d) resto → `silent`.
   - `noteRejectWarn(state: Map<string, number>, fp: string, now: number, max = 64): void` — grava e
     evicta as entradas mais antigas acima de `max`, para que um estranho ciclando pubs não faça o
     mapa crescer sem limite.
2. **Caminho de rejeição** (`index.ts:3040-3052`): continuar enviando o `rejectPayload` (o client
   precisa do feedback "identidade revogada"), **remover o `setTimeout(() => ws.close(), 500)`** e
   apenas `return` — drop silencioso daquele pub. O `log("warn", "client rejected: not in
   allowlist")` **e** o `audit("client.rejected")` passam a rodar só quando `rejectLogDecision` diz
   `warn` (audit.log tem cap de ~1 MB e rotaciona: um zumbi a cada 8s apagaria o histórico de
   segurança do dono). Contador `metrics.inc("ocr_client_rejected_total")` continua em toda rejeição.
   O caminho de rejeição não pode tocar em `sessions` — uma sessão já pareada com o mesmo `frame.from`
   permanece intacta.
3. **Revogação** (`index.ts:1037-1041`): fechar o socket **só** quando ele for um socket local
   (`localSockets.has(s.socket)`); no relay basta `sessions.delete(from)` — a sessão lógica morre, o
   socket compartilhado fica de pé.
4. **Fingerprint nos logs**: trocar todos os `pub.slice(0, 16)` de `index.ts` (linhas 1047, 1048,
   2334, 3017, 3021, 3037, 3038, 3041, 3043, 3075, 3078) por `fp: pubFingerprint(pub)` — chave nova
   `fp`, o campo `pub` some desses eventos. Em `SettingsView.tsx:1368`, renderizar `e.data?.fp`
   quando presente e manter o fallback `…${pub.slice(-6)}` para linhas de audit escritas antes da
   atualização (audit.log sobrevive ao upgrade). Sem componente novo, sem mudança de tipografia.
5. **Docs**: `docs/security.md` item 8 (trilha de auditoria) — fingerprint sha-256 do SPKI + warn/audit
   com throttle de 60s; e uma nota de que rejeição/revogação nunca fecham o socket do relay.
   `docs/troubleshooting.md` — sintoma "relay connection lost em loop / todos os aparelhos caem
   juntos" e a causa (device revogado reconectando), agora inofensiva.

## Edge cases
- Hello desconhecido chegando com o mesmo `frame.from` de uma sessão pareada: a sessão existente não
  pode ser apagada nem sobrescrita.
- Zumbi ciclando pubs diferentes: o mapa de throttle fica limitado a 64 entradas (LRU por
  `noteRejectWarn`).
- Relógio para trás entre dois rejeitos do mesmo pub → `silent` (nunca vira spam).
- `pub` malformado/base64 inválido → `"unknown"`, nunca exceção dentro do handler.
- Socket local (P1-061) rejeitando: também não fecha nada; cada client local tem seu próprio socket e
  simplesmente é ignorado.
- `relaySocket` reconectando enquanto o zumbi insiste: o mapa de throttle é in-memory e reinicia com o
  processo — aceitável, no pior caso um warn extra por boot.
- Audit rows antigas (`data.pub`) continuam renderizando na Security log.
- `scripts/invariants.ts` e `deploy/` não são tocados.

## Acceptance criteria
1. `npm run typecheck` verde.
2. `npx tsx scripts/unit.test.ts` verde, incluindo a bateria nova:
   - duas chaves P-256 distintas (`newIdentity()` do `@ocr/protocol`) produzem fingerprints
     diferentes, enquanto `pub.slice(0, 16)` das duas é **igual** (assert explícito da premissa);
   - a mesma chave produz o mesmo fingerprint em chamadas repetidas; formato `/^[0-9a-f]{16}$/`;
   - entradas inválidas (`""`, `null`, `"!!!"`) → `"unknown"`;
   - tabela de `rejectLogDecision` cobrindo as 4 regras na ordem documentada;
   - `noteRejectWarn` mantém no máximo 64 entradas após 200 pubs distintos.
3. `npx tsx scripts/e2e-orphans.ts && npx tsx scripts/reject-isolation.test.ts` sai 0 em < 90s
   (timeout global no próprio script, portas efêmeras, como `reconnect.test.ts`):
   - client A pareia via bootstrap e faz 1 op com sucesso;
   - client B (identidade nova, `from: "zombie"`) manda 3 hellos com ~200ms de intervalo e recebe 3
     frames de reject;
   - depois disso client A faz 3 ops que **todas** respondem (retry limitado a 3 tentativas com `id`
     novo por tentativa, conforme P3-337);
   - o stderr do daemon (capturado via `stdio: pipe`, `OCR_LOG_LEVEL=warn`) **não** contém
     `relay connection lost` nem `connected to relay` depois do pareamento de A;
   - o stderr contém no máximo **1** linha `client rejected` para os 3 hellos, e essa linha traz
     `"fp"` com 16 hex.
4. `grep -n "slice(0, 16)" apps/daemon/src/index.ts` não retorna nada.
5. `npx tsx scripts/invariants.ts` imprime `INVARIANTS OK`.
6. `npm run lint` verde.

## Out of scope
- Qualquer mudança no relay (`apps/relay/`), no allowlist/handshake, no `seq` em AAD ou no state file
  0600 — a superfície de auth não muda, só o efeito colateral do rejeito.
- Mostrar fingerprint na lista de dispositivos pareados (`SettingsView.tsx:1346`) ou qualquer redesign
  da Security log.
- Fazer o client parar de reconectar após um reject (comportamento da PWA).
- Backoff/reconexão do relay (`relayretry.ts`, `relayclose.ts`) e novas métricas além do contador
  `ocr_client_rejected_total`.
- Mudar `scripts/invariants.ts` ou `deploy/`.
