## Problem

`apps/daemon/src/index.ts:106` define `const RELAY_URL = process.env.RELAY_URL ?? "ws://127.0.0.1:8787"` e
`apps/desktop/src/daemon.ts:476-492` (`spawnChild`, único ponto de spawn do sidecar) monta o env com
`ELECTRON_RUN_AS_NODE` + `OCR_METRICS_PORT` e **nunca** `RELAY_URL`. No app empacotado o pareamento remoto
da P1-070 (`main.ts:496` `app:pairUrl`, `getPairUrl()` em `daemon.ts:372`) gera então um QR cujo endereço de
relay é `ws://127.0.0.1:8787` — o loopback do próprio Mac. O celular lê o QR, disca 127.0.0.1 e chega em si
mesmo.

A única forma de apontar o app para um relay hospedado (estágio 4, `docs/RELAY-HOSTING.md`,
`README.md:409`) é exportar `RELAY_URL` antes de abrir o app — coisa que quem instala um DMG nunca fará.
Não existe nenhuma superfície de configuração no shell.

## Approach

1. **Novo módulo `apps/desktop/src/relaysetting.ts`** — puro, no espírito de `extlink.ts` /
   `permissions.ts` / `webviewguard.ts`: sem `electron`, sem `node:fs`, sem `node:path/os`, sem `fetch`.
   Exporta:
   ```ts
   export const DEFAULT_RELAY_URL = "ws://127.0.0.1:8787"; // byte a byte o default de index.ts:106
   export const RELAY_URL_MAX_LEN = 512;                   // teto documentado
   export type RelayUrlOrigin = "env" | "stored" | "default" | "stored-invalid";
   export interface RelayUrlResolution { url: string; origin: RelayUrlOrigin; problems: string[] }
   export function relayUrlProblems(raw: unknown): string[];
   export function resolveRelayUrl(env: { RELAY_URL?: string }, stored: unknown): RelayUrlResolution;
   ```
   `relayUrlProblems` devolve `string[]` no mesmo formato dos preflights da P2-141/P2-171
   (`apps/relay/src/knobs.ts`): array vazio = válido. É problema: valor não-`string`; string vazia (após
   `trim()`); URL não parseável (`new URL` lança); esquema diferente de `ws:`/`wss:`; `ws:` apontando para
   host não-loopback; `url.username`/`url.password` não vazios; `raw.length > RELAY_URL_MAX_LEN`.
   O esquema é comparado em **caixa baixa** (`url.protocol` já normaliza, mas o teste cobre `WSS://`
   explicitamente — motivo da P2-178). Mensagens em inglês, log-safe, sem userinfo.
2. **Regra de loopback idêntica à autoridade de boot**: reproduzir a regra estrita de
   `isLoopbackHost` (`apps/daemon/src/relayurl.ts:32-39`) — `localhost`, `::1` (colchetes removidos) e
   `127.x.y.z` casado como **dotted-quad estrito** com octetos ≤ 255. Nada de prefixo (`127.0.0.1.evil.com`
   é público). Não importar de `apps/daemon` (workspace diferente, `index.ts` roda `main()` no import,
   lição P2-149/P2-161): duplicar com comentário citando `relayurl.ts` como autoridade final, e provar a
   paridade num check dedicado que roda a mesma tabela de hosts nos dois módulos.
3. **`resolveRelayUrl(env, stored)`** — precedência e fail-closed:
   - `env.RELAY_URL` presente e não vazio → `{ url: env.RELAY_URL, origin: "env", problems: relayUrlProblems(env.RELAY_URL) }`.
     O env **sempre vence** (caminho do operador/dev preservado byte a byte); os problems são só superfície
     de UI — quem recusa a discagem continua sendo `relayurl.ts` no boot do daemon.
   - senão, `stored` válido → `{ url: stored.trim(), origin: "stored", problems: [] }`.
   - senão, `stored` presente mas inválido → `{ url: typeof stored === "string" ? stored : "", origin: "stored-invalid", problems: relayUrlProblems(stored) }`.
     **Nunca** cai no default em silêncio: `url` jamais é `DEFAULT_RELAY_URL` nesse ramo.
   - senão (`stored` ausente/`null`/`undefined`) → `{ url: DEFAULT_RELAY_URL, origin: "default", problems: [] }`.
4. **Persistência — `apps/desktop/src/relaystore.ts`** (novo, fino; o módulo puro não pode importar
   `node:fs`, e `window-state.ts` é o precedente de I/O do shell): `relaySettingFile(userDataDir)` →
   `join(userDataDir, "relay.json")`; `readStoredRelayUrl(file): string | null` (arquivo ausente,
   ilegível, JSON corrompido ou campo não-string → `null` = não configurado, log-only);
   `writeStoredRelayUrl(file, url: string | null)` — grava `{"url":…}` em `<file>.tmp` com `{ mode: 0o600 }`
   e `renameSync` por cima, removendo o `.tmp` em caso de falha (mesmo contrato do `writeStateAtomic`,
   `apps/daemon/src/statefile.ts:37-49`); `url === null` limpa o ajuste (grava `{}`).
5. **`apps/desktop/src/daemon.ts`**: `let relayUrlForSpawn = DEFAULT_RELAY_URL;` + export
   `setSidecarRelayUrl(url: string): void`. `spawnChild` (único `spawn(` do arquivo, usado pelo start
   inicial, pelos respawns com backoff e pelo `restartDaemon`) passa a incluir `RELAY_URL: relayUrlForSpawn`
   no literal de `env`. Nenhuma outra variável muda; a adoção de daemon externo (`reuse`,
   `startReconnectWatchdog`) fica intocada.
6. **IPC em `main.ts`** (junto dos outros `ipcMain.handle`, `main.ts:397-565`), validando **sempre** no
   processo principal:
   - `app:relaySetting` → `resolveRelayUrl(process.env, readStoredRelayUrl(relaySettingFile(app.getPath("userData"))))`,
     devolvendo `{ url, origin, problems }`.
   - `app:setRelayUrl` (payload `unknown`): `null`/`""` → limpa o ajuste (ação "voltar ao relay local");
     senão `relayUrlProblems(payload)` — com problems **não persiste** e devolve `{ ok: false, problems }`.
     Válido → `writeStoredRelayUrl`, `setSidecarRelayUrl(resolvido)`, `void restartDaemon()` (para o daemon
     reemitir o URI de pareamento) e devolve `{ ok: true, url, origin, problems: [] }`.
   - No boot, antes de `startDaemonSidecar`, chamar `setSidecarRelayUrl(resolveRelayUrl(...).url)`.
7. **`preload.ts`**: `export interface RelaySetting { url: string; origin: "env"|"stored"|"default"|"stored-invalid"; problems: string[] }`
   e no `contextBridge`: `getRelaySetting: () => ipcRenderer.invoke("app:relaySetting")`,
   `setRelayUrl: (url: string | null) => ipcRenderer.invoke("app:setRelayUrl", url)`.
   `DesktopBridge` em `apps/web/src/App.tsx:96-123` ganha os dois campos opcionais e os repassa a
   `SettingsView`.
8. **`SettingsView.tsx`**: novo `<div className="card">` na faixa exclusiva do shell (ao lado do bloco
   `onPairRemote`, linhas 285-294), renderizado só quando `getRelaySetting` existe. Mostra: título
   `t("relayTitle")` ("Relay do celular"), `<input>` com o valor atual, linha `.muted` com a origem
   (env / salvo / padrão local), mensagem de erro em pt-BR quando `problems.length > 0` ou
   `origin === "stored-invalid"`, botão `Salvar` e botão secundário `Usar relay local`. Com `origin === "env"`
   o input é `readOnly` e o hint explica que a variável de ambiente manda. Reusar `card`/`input`/`.muted`/
   `button.primary` existentes — sem gradiente, sem emoji, sem novo token de spacing (constituição §6).
   Chaves novas em `apps/web/src/lib/i18n.ts` nos dois idiomas.
9. **Docs**: `README.md`, `README.pt-BR.md` (junto do parágrafo de relay hospedado, `README.md:409` /
   `README.pt-BR.md:389`) e `docs/troubleshooting.md` — como apontar o app para um relay hospedado pela
   tela de Settings e por que o relay local (`ws://127.0.0.1:8787`) só serve para a própria máquina
   (o QR gerado com ele não funciona em outro dispositivo).

## Edge cases

- `stored-invalid` com `stored` string: o spawn recebe `RELAY_URL` = a string inválida; o preflight de
  `relayurl.ts` recusa a discagem e retém o URI de pareamento — fail-closed, sem QR mentiroso.
- `stored-invalid` com `stored` não-string: `url === ""`; `process.env.RELAY_URL ?? default` usa `??`, então
  string vazia **não** cai no default — `parseRelayUrl("")` falha e o daemon segue fail-closed.
- Daemon adotado (externo/launchd): o env de spawn não alcança um processo que não é nosso filho; documentar
  em `docs/troubleshooting.md` que nesse caso o `RELAY_URL` tem de vir do serviço externo.
- `wss://` em host público é válido (TLS); `ws://localhost`, `ws://127.0.0.1:8787`, `ws://[::1]:8787` válidos;
  `ws://127.0.0.1.evil.com` é problema.
- `WSS://relay.exemplo.com` (maiúsculas) é aceito; `HTTP://…` e `file://…` são problema.
- `relay.json` inexistente na primeira execução: `origin === "default"`, zero problems, zero log de erro.
- Renderer hostil: o main revalida todo payload; nada persiste sem passar por `relayUrlProblems`.
