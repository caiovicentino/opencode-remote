# P3-341 — PR CONFLICTING não pode matar a task

## Problem
`mergeReadiness` (`apps/pilot/src/pipeline.ts:2142-2180`) decide `skip/conflict` assim que o
snapshot traz `mergeable=CONFLICTING` ou `mergeStateStatus=DIRTY`, e `mergePrForTask`
(`pipeline.ts:2270-2282`) devolve `{ ok:false, infra:"conflict" }` sem tentar nada. O único
reparo existente é indireto: `setupTaskBranch` (`pipeline.ts:310-345`) rebasa a branch no ciclo
seguinte e `mergeConflictBlock` (`pipeline.ts:472-475`) injeta um bloco no prompt do builder no
round seguinte. Foi exatamente o que matou P3-328: gate verde, PR #877 bloqueado por um parágrafo
novo no README que main ganhou enquanto a branch estava em review — a task ficou com PR órfão
aberto e o merge só saiu com intervenção do operador (`BACKLOG.md:16`). Três skips iguais viram
bloqueio duro pelo streak breaker (`apps/pilot/src/audit.ts:116-134`). Um conflito puramente
textual em doc não tem por que consumir ciclo, attempt nem operador.

## Approach
1. **Módulo puro novo** `apps/pilot/src/mergerepair.ts` — sem `node:fs`, sem `node:child_process`,
   sem `fetch`, sem `process` (padrão dos módulos puros já auditados por fonte no battery, ex.
   `permissions.ts`/`micaccess.ts`). Exporta, nesta ordem:
   - `classifyConflictPath(path: string): "protected" | "docs" | "code"` —
     `protected`: `deploy/`, `scripts/invariants.ts`, `.github/`, `BACKLOG.md` (constituição 3 e
     ledger do pilot: nunca auto-resolvidos, nem sendo `.md`); `docs`: qualquer `*.md` restante
     (README.md, README.pt-BR.md, AGENTS.md, `docs/**`, `specs/**`); `code`: o resto.
   - `parseConflictedFile(content: string): Segment[] | null` — `Segment = string | { ours: string[];
     theirs: string[] }`. Aceita marcadores `<<<<<<<`, `|||||||` (diff3, base descartada),
     `=======`, `>>>>>>>` em início de linha. Marcador aninhado, sem par ou fora de ordem ⇒ `null`
     (o chamador escala; nunca exceção).
   - `isCommentOnlyHunk(h): boolean` — verdadeiro só quando **todas** as linhas dos dois lados são
     vazias ou começam (após trim) com `//`, `/*`, `*`, `*/` ou `#`.
   - `resolveConflictedFile(path, content)` — `docs` e `code` comment-only ⇒ união determinística:
     ours e depois theirs, na ordem original, sem linha separadora, mantendo um único lado quando
     `ours` e `theirs` são idênticos; qualquer outro caso ⇒ `{ ok:false, reason }` com o motivo
     (`protected path`, `malformed conflict markers`, `code hunk changes semantics`).
   - `repairPlan(files: { path: string; content: string }[])` — avalia **todos** os arquivos em
     ordem de path, sem short-circuit, e devolve `{ verdict:"resolve"; files }` ou
     `{ verdict:"escalate"; paths; reason }` com **todos** os motivos concatenados (um por causa,
     ordem fixa — lição P2-322). Lista vazia ⇒ `escalate` com `"no conflicted paths reported"`.
2. **Runner fino** em `pipeline.ts` (I/O só aqui), `repairConflictedBranch(io, { branch, taskId })`,
   plano fechado e ordenado, executado no máximo **uma vez** por chamada de `mergePrForTask`:
   `git fetch -q origin` → `git merge --no-edit origin/main` → se falhou:
   `git diff --name-only --diff-filter=U` → `io.readFile` de cada path → `repairPlan` →
   `escalate` ⇒ `git merge --abort` e retorno `{ status:"escalate", detail }` (branch intacta,
   nada de push) → `resolve` ⇒ `io.writeFile` de cada arquivo, `git add -- <paths>` (paths
   passados por `JSON.stringify`), `git commit --no-edit`,
   `git push -q --force-with-lease origin <branch>` (mesmo precedente do `metapush`/`mergeTask`),
   `git rev-parse HEAD`. Retornos: `{ status:"repaired"|"clean"; sha }` (sha validado 40-hex),
   `{ status:"escalate"|"failed"; detail }`. `clean` = o merge não conflitou (main só tinha andado).
3. **Sinks opcionais e aditivos** em `PrMergeIo` (`pipeline.ts:2075-2078`):
   `readFile?: (p: string) => string | null` e `writeFile?: (p: string, c: string) => boolean`.
   Ausentes ⇒ o reparo é pulado e o comportamento é byte-a-byte o de hoje (todos os testes atuais
   de `mergePrForTask` continuam valendo sem edição). `mergeTask` (`pipeline.ts:2351-2362`) passa
   as implementações reais resolvidas contra `ws` com `join(ws, p)`, recusando path absoluto ou
   contendo `..`.
4. **Fio em `mergePrForTask`**: `let expectedSha = args.pushedSha`. Quando
   `ready.verdict==="skip" && ready.infra==="conflict"` e os sinks existem, roda o reparo;
   `repaired`/`clean` ⇒ `expectedSha = repair.sha` e **uma** nova
   `awaitMergeReadiness(io, prNumber, PR_READINESS_POLLS, expectedSha)`; `escalate`/`failed` ⇒
   retorna `{ ok:false, infra:"conflict", detail:\`PR #<n> ${CONFLICT_OPERATOR_MARKER}: …\` }`
   (marcador exportado, ex. `"needs operator"`, para o detail chegar ao evento de fase, ao log e
   ao `notifySupervisor` do fim de ciclo). O poll de confirmação passa a comparar `headRefOid`
   com `expectedSha` (não mais com `args.pushedSha`) — a garantia fail-closed continua idêntica.
5. **`awaitMergeReadiness` ganha 4º parâmetro opcional `expectSha`** e pede `headRefOid` no
   `--json`: com `expectSha` setado, snapshot cujo `headRefOid` difere vira `pending`
   (`"PR head not yet updated"`), então o segundo probe espera o CI **do head novo** antes de
   qualquer merge — nada de veredito verde herdado do head velho. Sem `expectSha`, comportamento
   inalterado. `mergeReadiness` continua pura e com a mesma assinatura.
6. **Docs**: parágrafo novo em `docs/PILOT.md` logo após o bloco P2-134 (linhas 935-949), em
   pt-BR e no mesmo tom, explicando o reparo automático, o que é trivial (docs/`.md` e hunks
   só de comentário), o que escala (código com semântica, `deploy/`, `scripts/invariants.ts`,
   `.github/`, `BACKLOG.md`, marcadores malformados) e que o head novo é re-checado antes do
   merge. `mergeConflictBlock` e o caminho do builder permanecem — são a rota do conflito
   semântico.

## Edge cases
- `git merge` limpo (main só andou): `status:"clean"`, push mesmo assim e re-probe com o sha novo.
- `git merge` já up-to-date e sem commit novo: `rev-parse HEAD` igual ao anterior ⇒ segue como
  `clean`, sem push redundante falhar o fluxo.
- `git push --force-with-lease` rejeitado (peer push): `status:"failed"` ⇒ infra `conflict`, ciclo
  seguinte tenta de novo; nunca `--force` puro, nunca push em `main`.
- `io.readFile` devolve `null` (arquivo deletado num dos lados, conflito delete/modify): escala.
- Conflito misto (um `.md` trivial + um `.ts` semântico): escala **tudo**, nada é escrito.
- Conteúdo binário / arquivo sem marcador em `--diff-filter=U`: `parseConflictedFile` ⇒ `null` ⇒ escala.
- Segundo probe volta `pending` até o teto: infra `timeout` (retry grátis), nunca merge otimista.
- Reparo roda no máximo 1× por chamada: um segundo `CONFLICTING` depois do push escala.

## Acceptance criteria
1. `npx tsx scripts/unit.test.ts` verde, com blocos novos cobrindo:
   - **conflito de docs resolvido sem intervenção**: io falso cujo `gh pr view` devolve
     `mergeable:"CONFLICTING"` no 1º probe e `MERGEABLE` + `headRefOid` novo depois do push;
     `git diff --diff-filter=U` devolve `README.md`; `mergePrForTask` retorna `ok===true`, a
     sequência de `exec` contém `git merge --no-edit origin/main`, `git commit --no-edit` e
     `git push -q --force-with-lease origin pilot/P3-341`, **não** contém `git merge --abort`, e
     o conteúdo escrito preserva os dois parágrafos (ours e theirs).
   - **conflito de código escalado**: mesmo io com `apps/pilot/src/pipeline.ts` conflitado em
     hunk não-comentário ⇒ `ok===false`, `infra==="conflict"`, `detail` contém o marcador de
     operador e o path; `exec` contém `git merge --abort` e **zero** `git push`.
   - `classifyConflictPath` para `README.md`/`docs/PILOT.md`/`specs/X.md` = `docs`;
     `deploy/x.sh`/`scripts/invariants.ts`/`.github/workflows/ci.yml`/`BACKLOG.md` = `protected`;
     `apps/pilot/src/pipeline.ts` = `code`.
   - `parseConflictedFile` de marcador aninhado/sem `>>>>>>>`/`=======` órfão ⇒ `null`;
     `isCommentOnlyHunk` verdadeiro para `//`/`*`/`#`/linha vazia e falso com uma linha de código.
   - `repairPlan` mistura docs+código ⇒ `escalate` com os dois paths, ordem fixa, sem short-circuit.
   - retrocompatibilidade: `mergePrForTask` com io **sem** `readFile`/`writeFile` e PR
     `CONFLICTING` devolve exatamente o de hoje (`ok:false`, `infra:"conflict"`, zero `git `).
   - `awaitMergeReadiness(io, n, polls, sha)` com `headRefOid` divergente ⇒ `pending`; igual ⇒
     verdito normal; sem `expectSha` ⇒ inalterado.
2. Asserção de fonte: `readFileSync(".../mergerepair.ts")` não contém `node:`, `require(`,
   `fetch(`, `child_process` nem `process.` (pureza — lição P2-324).
3. Asserção de fonte em `pipeline.ts`: o poll de confirmação compara com `expectedSha` e não
   existe mais `head !== args.pushedSha`; `isTaskMergeSha`/`recordVerifiedMerge` intactos.
4. `npm run typecheck` e `npm run build` verdes; `npm run test:unit` verde com output real colado
   no EVIDENCE (deve bater num re-run).
5. `git diff --stat` não toca `deploy/`, `scripts/invariants.ts`, `package.json`,
   `package-lock.json`, `apps/relay`, `apps/daemon`, `apps/desktop`, `apps/web`.

## Out of scope
Resolver conflito semântico de código automaticamente; alterar `mergeConflictBlock` ou o prompt do
builder; mudar `setupTaskBranch`/`rebaseOutcome`; qualquer merge local em `main` ou push direto em
`main` (P1-076); mudar `mergeReadiness` (assinatura e regras), o streak breaker de
`audit.ts`, o `notifySupervisor` ou canal novo de notificação; UI, crypto E2E, allowlist de
handshake, replay/seq no AAD, arquivo de estado 0600, portas novas e qualquer dependência nova.
