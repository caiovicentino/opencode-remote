# P1-060 — Tarefas long-horizon: destravar o flash para trabalho grande

## Problem

O pipeline só é lucrativo em tasks pequenas: `PilotConfig` fixa `maxReviewRounds: 3`,
`taskTimeoutMin: 45`, `maxAttemptsPerTask: 4` (apps/pilot/src/state.ts:23-39) para
qualquer task, e o strategist é instruído a gerar só trabalho "small and shippable in
one pipeline cycle" (apps/pilot/src/index.ts:429). Tudo grande é fatiado à mão (ex.:
P1-046 shell v2). Pior: cada attempt destrói o trabalho anterior — `runPipeline` roda
`git branch -qD pilot/<ID>` + `checkout -B` no início de TODO run
(apps/pilot/src/pipeline.ts:735-736), e os reviewers sempre recebem o diff TOTAL da
branch truncado a 60.000 chars (`diff.slice(0, 60_000)`, pipeline.ts:368) — em task
grande o review vira ruído truncado. P1-051 provou que o flash executa trabalho
complexo quando o scaffolding apoia; faltam scaffolds para horizonte longo.

## Approach

1. **Campo size na linha do BACKLOG** — `backlog.ts`: novo tag opcional `(size: L)`
   (mesma mecânica do `(area: ...)`: regex de fim de linha, `Task.size?: "S"|"M"|"L"`,
   default `"S"` quando ausente/desconhecido; `parseBacklog` nunca quebra).
2. **Budgets por size** — função pura `budgetsFor(size)` (exportada, testável):
   S/M ⇒ `{ rounds: 3, timeoutMin: 45, attempts: 4 }`; L ⇒ `{ rounds: 6, timeoutMin: 90,
   attempts: 6 }`. `index.ts` (`runSlot`) passa um cfg clonado com os budgets efetivos
   para `runPipeline`, e `overCap` usa o `attempts` do size da task.
3. **Checkpoint review (só L)** — no início de cada builder round gravar o SHA da
   branch em `~/.opencode-remote/pilot/checkpoints/<ID>.json` (mesmo padrão do
   `gateFailFile`). Reviewers de rounds > 1 recebem o diff INCREMENTAL
   `git diff <shaAnterior> pilot/<ID>` (prompts com nota "rounds anteriores já foram
   revisados; julgue só o incremental") em vez do diff total truncado. Round 1 e tasks
   S/M mantêm o diff total. Findings continuam alimentando o round seguinte pela
   variável `findings` existente; `verifyFindings` roga contra o diff incremental.
4. **Branch preservada entre attempts (implementa o pré-requisito P1-036)** — só
   deletar/recriar `pilot/<ID>` quando `state.taskAttempts[t.id]` for 0/undefined;
   caso contrário `git checkout -q pilot/<ID>` (sem `-B`) e o builder prompt recebe
   bloco "attempt N: a branch já existe, continue do histórico, não recomece".
   Diff dos reviewers por range de commits (`git diff <base> <branch>`) quando houver
   checkpoint anterior; sem checkpoint, base = origin/main.
5. **Planner com marcos para L** — `plannerPrompt` ganha bloco: task L exige a
   `## Approach` numerada em marcos (M1..Mn) com critério de aceite por marcos; o
   builder executa marcos em ordem, 1+ por round. (A dispatch tier B em si é P1-059 —
   aqui só o prompt muda; `validateSpec`/`SPEC_SECTIONS` intocáveis.)
6. **Strategist gera épicos L** — prompt em `index.ts` passa a permitir no máximo 1
   task `(size: L)` por batch, apenas quando o trabalho for genuinamente indivisível,
   com marcos listados no spec da linha.

## Touched files

- `apps/pilot/src/backlog.ts` — parse do tag `(size: S|M|L)` (espelho de `AREA_RE`, linha 17).
- `apps/pilot/src/pipeline.ts` — `budgetsFor`; preservação de branch (linhas 735-736);
  checkpoint sha por task; diff incremental no `reviewerPrompt`/chamada dos reviewers;
  blocos L no `plannerPrompt` e no `builderPrompt`.
- `apps/pilot/src/index.ts` — `runSlot` clona cfg com budgets do size; `overCap`
  task-aware; prompt do strategist com regra de épico L.
- `scripts/unit.test.ts` — testes das fases puras (parse size, budgetsFor, overCap,
  decisão de preservar branch, marker incremental no prompt de review).
- `docs/PILOT.md` + `AGENTS.md` — documentar campo size, budgets L e checkpoint review.

## Edge cases

- Linha sem `(size: ...)` ou com valor inválido ⇒ `"S"` (comportamento atual intacto).
- `checkout -B` no pipeline start destruiria a branch preservada — o `-B` só ocorre
  no caminho "attempts==0"; no caminho preservado usar checkout sem reset.
- `commitSpec` faz `reset --hard origin/main` antes do builder — OK: roda antes do
  primeiro round; nos attempts seguintes a branch preservada já tem o spec commitado.
- Diff incremental vazio num round aprovado (ex.: só re-evidência) — reviewers caem
  no fallback do diff total da branch; empty-diff self-heal continua olhando a
  branch inteira (`codeChanges`), não o incremental.
- Task L bloqueada após 6 attempts: `blockAndPush` zera o contador ⇒ re-queue humano
  recomeça limpo (branch antiga é deletada, sem código podre ressuscitando).
- Slots concorrentes: checkpoint sha é por task (`checkpoints/<ID>.json`), sem colisão;
  timeout de 90min não afeta o watchdog (heartbeat via `stream`).

## Acceptance criteria

1. `npm run test:unit --silent` verde com novos checks: `parseBacklog` extrai
   `size === "L"` de linha com `(size: L) (area: ui)` e `"S"` quando ausente;
   `budgetsFor("L")` = `{rounds:6, timeoutMin:90, attempts:6}` e `budgetsFor("S")` =
   `{rounds:3, timeoutMin:45, attempts:4}`; task L com 5 attempts não é overCap (cap 6)
   e task S com 4 é.
2. `npm run typecheck --silent` e `npm run build --silent` verdes.
3. Preservação de branch: em unit test da decisão pura, attempts=0 ⇒ deletar/recriar;
   attempts≥1 ⇒ preservar; e o prompt do builder de attempt>1 contém instrução de
   continuar da branch existente.
4. Checkpoint: prompt de review de round>1 L cita o range incremental e NÃO contém
   diff > 60k de rounds anteriores; `checkpoints/<ID>.json` gravado com sha após cada
   review (observável no FS durante pipeline real).
5. Critério de campo: a próxima task real size L (ex.: P1-046 shell v2 inteira) mergea
   com menos attempts registrados em `state.taskAttempts` que a média das versões
   fatiadas equivalentes; registrar o número no merge.

## Out of scope

- Dispatch tier B por modelo (P1-059) — aqui só o prompt do planner ganha marcos.
- Paralelizar rounds de um épico L ou quebrar épicos automaticamente em subtasks.
- Mudar `scripts/invariants.ts`, `deploy/`, cripto E2E, allowlist, replay protection.
- Novos tamanhos (XL), budgets configuráveis em pilot.json ou alteração de
  `maxTasksPerDay`/`maxDeploysPerDay`.
