# P1-099 — Scheduler com eager-fill dos 2 slots

## Problem

Evidence in `~/.opencode-remote/logs/pilot.log`: from 15:27 on 2026-09-02, 9+ consecutive
`pipeline start` entries all carry `"slot":1` (P1-072 → P1-089). Two mechanisms cause this:

1. **No eager-fill at pipeline end.** The dispatcher in `apps/pilot/src/index.ts:83-249`
   only schedules in its polling cycle (5s sleep plus long awaits: pending deploy,
   strategist, researcher). When a pipeline ends, the freed slot sits idle until the next
   cycle, and the pick only targets `free.length` slots as computed at the top of that
   cycle — a pipeline end never immediately backfills the *other* free slot.
2. **Area rule starves slot 2.** `pickTasks` (`apps/pilot/src/scheduler.ts:18-29`) gives
   every untagged task the `solo` key (`areaKey`, scheduler.ts:9-11). With slot 1 busy on an
   untagged task, all other untagged tasks are skipped, so slot 2 never fills; when both
   slots are idle the single pick always lands on the lowest slot number (slot 1). The
   Ready queue in that window was 100% untagged, hence 9 serial pipelines in slot 1.

Additionally, `runGateExclusive` (`apps/pilot/src/pipeline.ts:698-704`, used at :1439)
serializes the two slots' gatekeepers behind one global promise lock. That was needed while
the eval battery bound fixed ports; since P1-081 the relay/daemon in the e2e bind ephemeral
ports (`scripts/integration.ts:83`) and desktop-flow uses a unique `OCR_DESKTOP_SESSION`
per run (`scripts/desktop-flow.test.ts:104`), so parallel gates are safe.

## Approach

1. **Eager-fill (`apps/pilot/src/index.ts`)** — extract the scheduling block
   (index.ts:213-242) into a synchronous `fillFreeSlots(reason)` closure inside `main()`:
   - Guards, all checked before any pick: `frozen()`, `state.auditMode`,
     daily budget (`state.tasks + running.size < cfg.maxTasksPerDay`), `--once` mode caps
     free slots at 1 (eval battery behavior unchanged).
   - Re-reads the queue fresh (`git fetch` + `git show origin/main:BACKLOG.md` +
     `parseBacklog`), filters over-cap tasks exactly like index.ts:234.
   - Computes `free` slots, `busyAreas` and `remainingBudget` as today, calls
     `pickBatch(...)` and starts one `runSlot` per picked task in the lowest free slot,
     inserting into `running` immediately.
   - MUST be synchronous start-to-finish (`exec` is sync; no `await`) — atomicity on the
     event loop is what prevents double-picking between the main loop and slot workers.
   - Call sites: the main loop (replacing the inline block) and `runSlot`'s `finally`,
     right after `running.delete(slot)` (index.ts:347-349) — so every pipeline end
     immediately fills ALL free slots (the freed one AND any other idle one), which is the
     eager-fill the task demands. Log each eager start with
     `msg:"pipeline start", data:{..., reason:"eager-fill"|"loop"}` (greppable criterion).
2. **Parallel gate (`apps/pilot/src/pipeline.ts`)** — remove the global `runGateExclusive`
   lock; call `gatekeeper(...)` directly at pipeline.ts:1439. Deploy stays serialized:
   `deployBusy` (index.ts:48, launchDeploy index.ts:360-396) is untouched. If the builder
   finds one remaining truly-shared resource inside the gate, serialize ONLY that resource
   and justify in the commit message.
3. **Docs** — document eager-fill + parallel gate + serialized deploy in `docs/PILOT.md`
   (constitution rule 5).

## Edge cases

- Queue with only same-area/untagged tasks: eager-fill picks nothing extra — P1-006 rule
  preserved (unit-pinned at scripts/unit.test.ts:1074 "untagged tasks never run in
  parallel"); slot 2 legitimately waits for a distinct-area task.
- Two pipelines finish back-to-back: synchronous fill guarantees each task is picked once;
  the second `finally` sees the first's picks in `running`.
- Budget exhausted mid-fill: `pickBatch` already caps by `remainingBudget` (unit-pinned,
  scripts/unit.test.ts:1077-1078); over-cap tasks are skipped, main loop still blocks them.
- `git show origin/main:BACKLOG.md` fails during eager-fill: skip the fill (main loop
  retries in its next cycle). Never throw out of `runSlot.finally`.
- Concurrent gatekeepers: safe post-P1-081 (ephemeral ports, per-run `OCR_DESKTOP_SESSION`,
  `e2e-orphans` only kills processes with test markers + hermetic env). Each gate runs in
  its own slot workspace; `state` mutations stay event-loop atomic.
- Deploys: a merge landing while a deploy is in flight keeps logging
  "deploy in flight — merge queued on main" (launchDeploy, index.ts:361-364).

## Acceptance criteria

1. `npm run test:unit --silent` green, including a new "P1-099 eager-fill" block in
   `scripts/unit.test.ts` with a 3-task queue and 2 slots asserting:
   - both slots fill when the 3 tasks span >= 2 distinct area keys;
   - with 1 slot busy on area X, the freed slot picks the next distinct-key task and the
     same-key task is left queued;
   - all-same-area queue → nothing extra picked; budget 0 → nothing picked.
2. `npm run typecheck --silent` and `npm run build --silent` green.
3. Log criterion (post-merge, production pilot.log): when Ready >= 2 schedulable tasks
   (distinct area keys), overlapping `pipeline start` entries on `"slot":1` and `"slot":2`
   appear — slot B's start precedes slot A's `pipeline result`.
4. Deploy serialization: no two `deploy result` entries interleave without the
   "deploy in flight — merge queued on main" line between them (`deployBusy` invariant).
5. `--once` mode unchanged: exactly 1 pipeline total (eval battery relies on this).

## Out of scope

- `deploy/` and `scripts/invariants.ts` (constitution rule 3) — untouched.
- The P1-006 area-exclusivity rule, the `solo` default for untagged tasks, BACKLOG format
  or any task-dependency graph.
- Deploy concurrency (`deployBusy` stays the single global deploy lock), budgets,
  fever/audit mode logic, and P1-078 cache-affinity scheduling.
