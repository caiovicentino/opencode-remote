# P2-115 — Alerta de guard repetido: rejeições fail-closed sobre saída de LLM (validateSpec, verifyFindings) escalam motivo pro operador

## Problem
- `commitSpec` (`apps/pilot/src/pipeline.ts:1029-1056`) e `validateSpec` (`pipeline.ts:166-178`) só devolvem `boolean`. O loop do planner (`pipeline.ts:1451-1480`) loga `planner attempt produced no valid spec` sem dizer POR QUÊ (seção faltando? marker de controle? diff não spec-only? arquivo ausente?) e devolve `planner did not produce a valid specs/<ID>.md after 2 attempt(s)`. P1-073/P1-102/P1-103 queimaram 4 attempts cada com esse detail opaco (ver FAILURE LESSONS).
- `verifyFindings` (`pipeline.ts:1936-1953`) devolve `reasons` por finding, mas o caminho fail-closed "todos os findings unverificáveis" (`pipeline.ts:1749-1764`) só emite um `console.log` info por round; as razões de drop vão pro `pilot.log` via `logHallucination` (`pipeline.ts:2093`) e nunca chegam ao feed/notify.
- Não existe contador por (task, guard): o mesmo guard pode rejeitar a mesma task N vezes seguidas sem nenhum sinal de alerta ao operador. Modelo a seguir: P2-114 (`runner.ts:527-539`), streak em memória + `emit` + `notifySupervisor`.

## Approach
1. **Módulo novo `apps/pilot/src/guardalert.ts`** (pure + contador em memória do módulo, como `noteTierBOutcome` de P2-114):
   - `export type GuardName = "validateSpec" | "verifyFindings"; export const GUARD_ALERT_THRESHOLD = 2;`
   - `export function noteGuardRejection(task: string, guard: GuardName, reason: string): { count: number; alert: boolean }` — incrementa `Map<"${task}|${guard}", number>`; `alert = count >= GUARD_ALERT_THRESHOLD` (dispara na 2ª, 3ª, 4ª… rejeição consecutiva; bounded pelos attempts).
   - `export function clearGuardRejections(task: string, guard?: GuardName): void` (sem `guard` limpa a task inteira); `export function resetGuardAlerts(): void` (testes).
   - `export function guardAlertDetail(guard: GuardName, count: number, reason: string): string` → `` `${guard} rejected ${count}x in a row: ${reason}` `` com `reason` cortado em 160 chars (o `emit` corta detail em 220).
   - `export function raiseGuardAlert(task, guard, reason, hooks?: { emitEvent?: typeof emit; notify?: typeof notifySupervisor }): { count: number; alert: boolean }` — chama `noteGuardRejection`; quando `alert`: log JSONL `level:"error", msg:"guard-repeat"` com `{ task, guard, count, reason }`, `emitEvent("alert", { task, phase: guard, ok: false, detail })` dentro de try/catch e `void notify(task, false, detail).catch(() => {})`. Hooks default = `emit` de `./events` e `notifySupervisor` de `./notify` (nenhum dos dois importa `pipeline`/`guardalert` → sem ciclo).
2. **Razão do guard de spec** (`pipeline.ts`):
   - `export function specRejectReason(content: string): string | null` — mesma lógica de `validateSpec`, devolvendo `"spec too large (N lines / M chars)"`, `"control marker at line k: <marker>"` ou `"missing section(s): a, b"`; `validateSpec(c)` passa a ser `specRejectReason(c) === null` (comportamento idêntico; testes de `validateSpec` existentes seguem verdes).
   - `export function commitSpecWithReason(ws, id): { ok: true } | { ok: false; reason: string }` com as razões `"invalid task id"`, `"specs/<ID>.md missing on disk"`, `"spec unreadable"`, o texto de `specRejectReason`, `"spec write failed"`, `"branch diff not spec-only: <names ou vazio>"`. `commitSpec(ws, id)` vira wrapper que devolve `.ok` (assinatura e testes atuais intactos).
   - Loop do planner (`pipeline.ts:1470-1475`): `const res = commitSpecWithReason(ws, t.id); specOk = res.ok;` no `!ok` incluir `reason` no warn `planner attempt produced no valid spec` e chamar `raiseGuardAlert(t.id, "validateSpec", res.reason)`. No sucesso: `clearGuardRejections(t.id, "validateSpec")`. O return terminal (`pipeline.ts:1479`) passa a incluir a última razão: `` `planner did not produce a valid ${specFile} after 2 attempt(s) — last: ${reason}` ``.
3. **Razão do guard de findings** (`pipeline.ts:1755-1764`): quando `secAllDropped || qualAllDropped`, montar `reason` = para cada reviewer all-dropped `` `${name}: ${dropped.length}/${dropped.length} finding(s) dropped (${até 2 razões distintas de verified.reasons})` `` unidos por `"; "` e chamar `raiseGuardAlert(t.id, "verifyFindings", reason)` (1 vez por round). Quando nenhum reviewer está all-dropped: `clearGuardRejections(t.id, "verifyFindings")`. Não mexer em `needsEscalation`, `reviewerOk` nem nos caminhos fail-closed de P1-073/P1-103 (lição: preservar).
4. **Evento `alert`** (`apps/pilot/src/events.ts:10`): adicionar `"alert"` à union de `type`. Consumidores checados: `countFailSteps` (`metrics.ts:86`) filtra `type==="phase"`; `pilotforensic.ts:151` trata `type` como string; `/api/pilot-events` (`apps/daemon/src/index.ts:2219`) repassa o tail sem filtrar.
5. **Dashboards** (o daemon serve os dois arquivos, `apps/daemon/src/index.ts:1928-1930`; o desktop embute o mesmo `dashboard.html`/`dashboard-v3.html`):
   - `apps/pilot/dashboard/mission-v3.html` — em `apply(e, quiet)`, antes de `if (e.type !== "phase") return;` (linha 404): `if (e.type === "alert") { const s = shipFor(e); if (s) { tremor(s, 1); s.color = COL.red; tag(s, \`GUARD ${(e.phase || "").toUpperCase()}\`, COL.red, 6); if (!quiet) burstAt(s.x, s.y, COL.red, 18, 0.8); } return; }`. HUD cap (749-752) e feed (763-764) já pintam `ok:false` em vermelho. ## Edge cases
- Contador é por processo (memória): restart do pilot zera, igual à streak tier-B de P2-114 — documentar. Attempts diferentes da mesma task no mesmo processo CONTAM (é exatamente o caso "4 attempts em 2 tasks").
- "Seguidas": qualquer sucesso do mesmo guard na task zera o contador; rejeição de `validateSpec` não influencia o contador de `verifyFindings`.
- `emitEvent`/`notify` nunca derrubam o pipeline (try/catch + `.catch(() => {})`); `notify` sem `supervisorSession` devolve `false` silenciosamente (já é assim).
- `reason` pode conter texto de LLM (finding): cortar em 160 chars, sem newline (`replace(/\s+/g, " ")`); nunca incluir conteúdo de spec além dos nomes de seção/marker.
- `specRejectReason` para marker de controle cita apenas o nome do marker e a linha — o texto do spec não vai pro feed.
- Escalação tier-B com todos os findings dropped NÃO conta como rejeição (fora do escopo; só `sec`/`qual`).
- `git diff --name-only` falhando em `commitSpecWithReason` → `"branch diff not spec-only: <git error tail>"` (fail-closed, como hoje).
- Dashboards: evento `alert` sem `task` (não deve acontecer) não quebra `apply` (`shipFor` devolve null → só `return`).

- `npm run typecheck && npm run build --silent && npm run test:unit` verdes; `npm run lint` sem novos erros.
- `scripts/unit.test.ts` — checks novos, todos `OK`:

  - `countFailSteps([{ ts, type: "alert", task: "T", phase: "validateSpec", ok: false, detail: "d" }])` → `[]` (alertas não poluem o breakdown de gate-fail).
