## Problem

`mergeTask` (`apps/pilot/src/pipeline.ts:2338-2432`) roda os passos `gh` com
`allowFail` e devolve `boolean`. Qualquer falha vira `false` (linhas 2366 e
2373), que o caller converte no detail genérico `gate green but the PR merge
failed — the next cycle retries the PR` (`apps/pilot/src/pipeline.ts:1914`),
sem `infra`. Consequências reais:

1. **A razão do `gh` some.** O output de `pr create` / `pr list` / `pr merge`
   nunca entra no detail, no evento `phase: merge` nem nas failure lessons — o
   operador só vê o tail do gate (que estava verde).
2. **A falha é tratada como mérito.** `resultInfraKind` (`apps/pilot/src/audit.ts:75`)
   devolve `null` porque `infra` está ausente, então `runSlot`
   (`apps/pilot/src/index.ts:477-487`) chama `recordCycle` + `tripCircuitBreaker`:
   incrementa `taskAttempts` e bloqueia a task em 4 tentativas sem nenhum
   finding de código. P2-117 e P2-123 morreram assim (8 attempts perdidos).
3. **Sem confirmação.** `gh pr merge --auto` sob branch protection retorna erro
   ou apenas *arma* o squash; hoje o pipeline nunca poll a o estado final,
   diferente de `armMetaPr` (`apps/pilot/src/metapush.ts:151-179`), que só
   reporta sucesso com `state === MERGED && headRefOid === pushedSha`.

## Approach

Tudo em `apps/pilot/src/pipeline.ts`, no espírito de `metapush.ts` (IO
injetável ⇒ testável sem rede):

1. Exportar `PrMergeIo { exec(cmd): {ok,output}; sleep(ms): Promise<void> }`,
   `PrMergeOutcome { ok: boolean; detail: string; infra?: InfraFailureKind }`,
   as constantes `PR_MERGE_CONFIRM_POLLS = 60` / `PR_MERGE_CONFIRM_DELAY_MS = 5_000`
   (~5 min, mesmo orçamento de `MERGE_CONFIRM_POLLS`) e
   `mergePrForTask(io, { branch, title, body, pushedSha }): Promise<PrMergeOutcome>`.
2. `mergePrForTask` executa e **captura o output** de cada passo:
   - `gh pr create --head <branch> --title … --body …`;
   - `gh pr list --head <branch> --state all --json number --jq '.[0].number'`
     para resolver o número do PR (funciona também quando o create falhou por PR
     já aberto, e continua válido depois do `--delete-branch`);
   - `gh pr merge <n> --squash --delete-branch --auto || gh pr merge <n> --squash --delete-branch`
     — **não** retorna cedo quando falha.
   Sem número de PR resolvível ⇒ `{ ok:false, infra:"network", detail:"pr create failed: …| pr list: …" }`
   com os últimos 300 chars de cada output.
3. Confirmação fail-closed: até `PR_MERGE_CONFIRM_POLLS` iterações (sleep de
   `PR_MERGE_CONFIRM_DELAY_MS` entre polls, nunca antes do primeiro)
   `gh pr view <n> --json state,headRefOid`;
   - `state === "MERGED" && headRefOid === pushedSha` ⇒ `{ ok:true }` **mesmo que
     o exec do merge tenha retornado erro** (auto-merge armado sob branch protection);
   - `state === "MERGED"` com `headRefOid` diferente ⇒ falha imediata (nosso sha
     não foi o mergeado);
   - view indeterminável (gh fora, JSON inválido) ⇒ continua polling;
   - orçamento esgotado ⇒ `{ ok:false, infra:"timeout", detail:"merge unconfirmed after ~5min: <tail do gh merge>" }`.
4. `mergeTask` passa a devolver `PrMergeOutcome` (não `boolean`): mantém o
   `git push -q origin pilot/<id>` e o `preMergeHead`, chama `mergePrForTask`
   com `{ exec: (c) => exec(c, { cwd: ws, allowFail: true }), sleep }`, e só
   segue para `checkout/pull main`, o registro P2-058 e o `landMetaCommit`
   quando `ok`.
5. Caller (`apps/pilot/src/pipeline.ts:1891-1914`):
   `emit("phase", { task, phase: "merge", ok, detail })` com o detail real, e no
   caminho de falha `return { ok:false, detail: \`gate green but the PR merge failed: ${outcome.detail}\`, infra: outcome.infra, ...roundMeta() }`
   — `resultInfraKind` passa a classificar como infra: soma em `infraFails`,
   não incrementa `taskAttempts`, não alimenta a janela de febre, task
   re-agendada no ciclo seguinte.
6. **Nada de deploy afrouxa**: o bloco P2-058 (`postMergeHead !== preMergeHead &&
   isTaskMergeSha(...)` ⇒ `recordVerifiedMerge`, warn caso contrário) fica
   idêntico, e a regra P1-076 (sem fallback de merge local / push direto em
   main) continua — o commit deve dizer isso explicitamente.
7. Documentar em `docs/PILOT.md`: parágrafo novo na seção de infra (~linha 595,
   junto de P1-074/P1-104) e nota na seção de merge/PR (~linhas 55-72).

## Edge cases

- `gh pr merge` retorna erro **e** o PR acaba MERGED com nosso sha ⇒ sucesso
  (o caso P2-117/P2-123).
- `gh pr create` falha porque o PR já existe ⇒ `pr list --state all` resolve o
  número e o fluxo continua.
- `--delete-branch` apaga a branch: o poll usa o **número** do PR, nunca
  `gh pr view <branch>`.
- `gh pr view` com JSON inválido/`gh` fora ⇒ nunca conta como sucesso; continua
  polling e no fim é infra (fail-closed).
- `emit` trunca `detail` em 220 chars (`apps/pilot/src/events.ts:26`) — o detail
  do `PipelineResult` carrega 300; nenhum dos dois pode conter secrets do output.
- Poll não pode dormir antes da primeira leitura (merge imediato sem proteção
  confirma no poll 0, sem 5s de latência artificial).
- Falha de infra no merge **não** chama `recordGateFail`/`tripCircuitBreaker`.

## Acceptance criteria

- `npx tsc -p tsconfig.base.json --noEmit` (ou `npm run typecheck`), `npm run build`
  e `npm run test:unit` verdes, com output real colado no bloco EVIDENCE.
- Blocos novos em `scripts/unit.test.ts` com `PrMergeIo` falso (zero rede),
  pinando pelo menos:
  - `P2-125: merge exec falhou mas o PR confirma MERGED ⇒ sucesso` (`ok === true`);
  - `P2-125: MERGED com headRefOid de outro sha ⇒ falha, nunca sucesso`;
  - `P2-125: merge nunca confirmado ⇒ ok=false com infra ("timeout") e zero attempts`
    — rodando `resultInfraKind` no resultado e checando
    `Object.keys(st.taskAttempts).length === 0` após `recordInfraFailure`;
  - `P2-125: detail carrega a razão do gh` (o tail do output do `gh pr merge`/
    `pr create` aparece no `detail`, ≤ 300 chars);
  - `P2-125: PR resolvido por número, nunca por branch` (nenhum comando
    `gh pr view pilot/` nas chamadas registradas);
  - pin de wiring por leitura de `apps/pilot/src/pipeline.ts`: a linha de falha
    do merge propaga `infra:` e não existe mais o detail sem razão.
- `PR_MERGE_CONFIRM_POLLS * PR_MERGE_CONFIRM_DELAY_MS === 300_000` (5 min).
- `grep -n "recordVerifiedMerge\|isTaskMergeSha" apps/pilot/src/pipeline.ts`
  mostra o bloco P2-058 inalterado; nenhum `git push origin main` novo.
- Mensagem do commit declara explicitamente que o guard de sha verificado
  (P2-058) e a regra P1-076 (nunca empurrar direto em main) continuam idênticos.
- `docs/PILOT.md` descreve a confirmação por poll e a classificação infra.

## Out of scope

- Mexer em `scripts/invariants.ts`, `deploy/` ou no fluxo de deploy/quarentena.
- Alterar `landMetaCommit`/`armMetaPr` ou a branch `pilot/meta`.
- Mudar limites do circuit breaker, da janela de febre ou o `INFRA_DOCTOR_EVERY`.
- Reabilitar merge local / push direto em `main` como fallback.
- Retry automático do merge dentro do mesmo ciclo (o scheduler re-agenda).
