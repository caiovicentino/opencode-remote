# P1-021 — Deploy rápido: pular npm ci quando lockfile não muda

## Problem
- Cada deploy roda `npm ci` (wipe + reinstall de ~2GB): 10-20min de ciclo, gargalo dominante.
- Hoje existe um skip *intra-deploy* (apps/pilot/src/deploy.ts:277-287, commit d301cf0): compara o
  hash do lock do HEAD anterior com o do novo SHA e, se iguais, **não roda instalação nenhuma**.
  Buracos: (1) node_modules com drift (wipe manual, ci interrompido, crash pós-wipe) não é
  reparado — o build falha e o deploy cai em rollback de 10-20min; (2) não há registro em disco
  do último install bem-sucedido, então nada distingue "lock igual e node_modules sadio" de
  "lock igual mas árvore podre"; (3) binários electron/ffmpeg não têm cache local configurado.

## Approach
1. **Estado do último install** (apps/pilot/src/deployguard.ts — mesmo padrão tolerante do
   módulo, fs-only): `defaultLastInstallFile()` → `~/.opencode-remote/pilot/last-install.json`;
   `readLastInstall(file): { sha256: string; at: string } | null` (JSON corrupto/parcial → null,
   hash vazio ou fora de `^[0-9a-f]{64}$` → null); `writeLastInstall(file, sha256, at): boolean`
   via `writeAll` (deployguard.ts:110).
2. **Decisão pura** (deployguard.ts): `installModeFor(currentHash: string, saved): "ci" | "fast"`
   — `fast` só quando `saved` existe e `sha256 === currentHash`; caso contrário `ci`
   (fail-closed para correção).
3. **Wiring no deploy()** (apps/pilot/src/deploy.ts:276-294):
   - Remover a comparação intra-deploy `prevLock`/`newLock` (linhas 277, 282-287); manter um
     único cálculo de hash pós-reset: `git show HEAD:package-lock.json | shasum -a 256 | cut -d' ' -f1`
     (allowFail). Hash vazio → `ci`.
   - `installModeFor(hash, readLastInstall(...)) === "fast"` → rodar
     `FAST_INSTALL_CMD` (deploy.ts, exportada p/ bateria):
     `ELECTRON_CACHE="$HOME/.cache/electron" npm install --prefer-offline --no-audit --no-fund --ignore-scripts --loglevel=error`
     com `timeoutMin: 5`. **Manter `--ignore-scripts` (lição P1-057, supply chain) — o texto do
     backlog omite, mas é requisito constitucional de segurança, não opcional.**
   - `"ci"` → `npmInstall(cfg)` (deploy.ts:371) com o prefixo
     `ELECTRON_CACHE="$HOME/.cache/electron"` adicionado aos dois `npm ci`; em caso de sucesso,
     `writeLastInstall` com o hash novo.
   - Escada de auto-reparo: fast install falhou → logar warn e cair para `npmInstall(cfg)`
     (ci completo, que já tem retry interno); ci falhou → caminho de erro/rollback existente.
   - Emitir evento observável: `emitEvent("deploy", { phase: "install", ok, detail: "fast-install (lock unchanged) in Xs" | "npm ci in Xs" })`.
4. **Rollback honesto** (deploy.ts:435-447): após o `npm ci` do rollback (linha 438) com ok,
   recalcular o hash do lock do HEAD revertido e regravar `last-install.json` — mantém o
   invariante "hash persistido == lock do node_modules em disco". Se o ci do rollback falhar
   (allowFail), NÃO regravar.
5. **Docs**: docs/PILOT.md linha 22 e ~156 ("reset SHA → npm ci → build → kickstart") passam a
   descrever: lock inalterado → `npm install --prefer-offline` (fast path), lock alterado → ci
   completo, cache de binários em `~/.cache/electron`.

## Touched files
- apps/pilot/src/deploy.ts — decisão fast/ci, `FAST_INSTALL_CMD`, ELECTRON_CACHE nos ci, evento
  `install`, refresh do hash no rollback; remove comparação intra-deploy obsoleta
- apps/pilot/src/deployguard.ts — `defaultLastInstallFile`, `readLastInstall`,
  `writeLastInstall`, `installModeFor` (puros, fs-only)
- scripts/unit.test.ts — novos checks da bateria (seção deploy, ~linha 1889)
- docs/PILOT.md — fluxo de install do deploy documentado

## Edge cases
- `last-install.json` ausente/corrupto/hash inválido → `ci` (comportamento de hoje), grava no
  sucesso. Primeiro deploy pós-merge faz um ci completo (cold start) e depois acelera.
- Lock inalterado mas node_modules apagado/danificado: fast install repara (instala a partir do
  lock + cache npm) em segundos — sem rollback dispendioso.
- Fast install falha → um fallback para ci completo antes de declarar erro (mesmo espírito do
  retry que `npmInstall` já faz, deploy.ts:372-375).
- Rollback: ci do rollback falhou → hash não é regravado (pode ficar defasado; o fast install do
  próximo deploy repara ou a escada cai pro ci).
- Lockfile inexistente no HEAD (hash vazio) → nunca é "igual" ao persistido → `ci`.
- Deploys são seriais (P1-006) → nenhuma corrida de escrita no arquivo; write único como `saveState`.
- `npm install` (fast) NÃO usa wipe — serviços continuam de pé durante a instalação; mesmo
  comportamento de boot que o skip atual já preserva.

## Acceptance criteria
1. `npm run typecheck` verde; `npm run test:unit` verde com NOVOS checks:
   - `installModeFor(h, { sha256: h }) === "fast"`, `installModeFor(h2, { sha256: h }) === "ci"`,
     `installModeFor(h, null) === "ci"`;
   - roundtrip `writeLastInstall`/`readLastInstall` em tmpdir; JSON corrupto → `null`;
     hash com chars fora de `[0-9a-f]` → `null`;
   - `FAST_INSTALL_CMD` contém `--prefer-offline`, `--no-audit`, `--ignore-scripts` e o prefixo
     `ELECTRON_CACHE`; os comandos `npm ci` de deploy.ts:372/375 também contêm ELECTRON_CACHE e
     `--ignore-scripts` (pinado por string exata no teste).
2. `grep -n "npm ci" apps/pilot/src/deploy.ts` → apenas no caminho de lock alterado e no
   rollback; nenhum `npm ci` no caminho fast (pinned pelo teste 1).
3. Evento `install` emitido em todo deploy com `detail` trazendo modo (`fast-install`/`npm ci`)
   e segundos decorridos — verificável em `~/.opencode-remote/pilot/events.jsonl`.
4. Evidência de tempo (bloco EVIDENCE): rodar no checkout de produção
   `time npm install --prefer-offline --no-audit --no-fund --ignore-scripts --loglevel=error`
   → completa em < 30s com lock inalterado; `npm run build --silent` verde em seguida.
5. Critério-chave: com lock inalterado, o intervalo entre os eventos `deploy start` e o primeiro
   `soak` de um deploy real (próximo ciclo) é < 300s (colar trecho do events.jsonl no EVIDENCE);
   com lock alterado o evento `install` reporta `npm ci`.
6. docs/PILOT.md descreve o fast path e o cache (constituição regra 5).

## Out of scope
- `deploy/` e `scripts/invariants.ts` (safety-critical, constituição) — não tocar.
- `npm ci` do slot (apps/pilot/src/index.ts:662) e o `lock-sync` do gate
  (apps/pilot/src/pipeline.ts:1630) — fora do caminho de deploy.
- Troca de gerenciador de pacotes, tuning de cache npm, mudanças no soak/disk guard/rollback.
- Qualquer mudança de UI/dashboard; o chip de deploy existente já mostra fases.
