# P1-053 — Daemon-down não pode desistir: reconnect infinito com degradação honesta

## Problem

`apps/desktop/src/daemon.ts:30-34` limita o respawn do sidecar a 3 tentativas
(5s/15s/45s) e entra em `gaveUp` **terminal**. Com deploys dando `kickstart` no
daemon a cada merge, o app desktop morre na tela de pairing várias vezes ao dia
(aconteceu de verdade). Hoje o mesmo orçamento curto vale para daemon **adotado**
(reuso, ex. launchd em :8792), onde não há filho algum para respawnar — e o
banner atual só diz "reabra o app".

## Approach

Três estados honestos no banner: reconectando (amarelo, ativo) / daemon-down
(vermelho, terminal-hosted, com ação) / ok (sem banner). Toda a lógica nova é
**aditiva**: o orçamento de 3 tentativas do modo hosted fica intacto.

1. **`apps/desktop/src/daemon.ts`**:
   - `reconnectDelayMs(n)` pura e exportada: `min(30_000, schedule[min(n-1,len-1)] × 2^max(0,n-len))`.
     Produção: 5s → 15s → 30s → 30s… (cap 30s). `OCR_DAEMON_RESPAWN_DELAYS` continua
     encurtando em testes ("200,200,200" → 200ms sempre, pois 200×2^k < cap).
   - Watchdog de reuso: quando um daemon externo é adotado (`sidecar.reused`,
     `startDaemonSidecar`/`respawn`/`restartDaemon`), iniciar timer que sonda
     `healthOnce(port, token)` em backoff infinito (delay acima). Perda de saúde:
     `reconnecting=true`, `reconnectAttempts++`; recuperação: reset dos dois.
     **Nunca** seta `gaveUp` e **nunca** spawna filho (nada de brigar pela porta
     com o launchd). Timer guardado e limpo em `stopDaemonSidecar`.
   - Modo hosted (`sidecar.spawned`): comportamento atual (3 tentativas → `gaveUp`)
     inalterado; `gaveUp` só é alcançável nesse modo.
   - Novos exports: `reconnectState(): { reconnecting: boolean; attempts: number }`
     (hatch `OCR_DAEMON_FORCE_RECONNECTING=1`, mesmo padrão do FORCE_DOWN existente)
     e `reconnectDelayMs`. Manter `respawnState()` como está (eval battery usa).
2. **`apps/desktop/src/main.ts`**: `refreshPairingState()` no caminho de falha:
   `isDaemonDown()` → `daemonDownState()` (hoje) **+** `reconnectState().reconnecting` →
   `{ uri:null, qrDataUrl:null, devices:0, phonePaired:false, reconnecting:true, reconnectAttempts:n }`.
   Handler IPC `app:reconnectDaemon` → `restartDaemon()` (lógica P3-017 reusada).
3. **`apps/desktop/src/preload.ts` + `apps/desktop/src/pairing.ts` + `App.tsx`**:
   `PairingState` ganha `reconnecting?: boolean; reconnectAttempts?: number` (3
   cópias sincronizadas) e bridge `reconnectDaemon()`. `App.tsx`: banner amarelo
   `role="status"` "Reconectando… (n tentativas)" (classe `.daemon-reconnecting`,
   variante amarela do `.daemon-down` em `apps/web/src/index.css`); banner vermelho
   `daemonDown` ganha botão **"Reconectar agora"** → `bridge.reconnectDaemon()`.
   Extração do auto-pair de montagem (App.tsx:298-349) em `tryAutoPair()` e
   re-execução quando a saúde volta com `phase==="unpaired"` e `!loadState()` —
   é isso que mata a tela de pairing eterna.
4. **`apps/web/src/lib/i18n.ts`**: chaves novas `reconnecting` ("Reconectando ao daemon… ({n})") e
   `reconnectNow` ("Reconectar agora"), EN + pt-BR; reescrever `daemonDown`
   (i18n.ts:147/243) para apontar ao botão, não a "reabra o app". Ajustar
   `NOTIFY_DOWN_BODY` em `apps/desktop/src/notify.ts` na mesma direção.
5. **Testes**: ver critérios.

## Edge cases

- Watchdog de reuso **não** spawna filho: pid-file/`child` nunca mudam no modo reuso.
- Squatter 200-anywhere na porta durante o reconnect: `healthOnce` (challenge 401)
  já rejeita; nenhum token novo é emitido.
- `stopDaemonSidecar`/`restartDaemon` limpam timer pendente e estado `reconnecting`
  (nenhum probe pós-quit; `restartDaemon` reseta attempts).
- Daemon externo volta durante `gaveUp` hosted: `respawn()` já re-adota — manter.
- App web fora do shell (sem bridge): banners/regex de bridge inexistentes — sem mudança.
- `scripts/invariants.ts` (regexes sobre daemon.ts) precisa continuar verde — mudança aditiva.
- Hatches `OCR_DAEMON_FORCE_*` nunca setados em produção (policy dos comentarios em daemon.ts).
- `phonePaired:false` no estado reconnecting nunca abre overlay de QR (`uri` é null).

## Acceptance criteria

1. `npx tsx scripts/desktop-sidecar.test.ts` verde, incluindo:
   - `reconnectDelayMs(1)=5000`, `(2)=15000`, `(3)=30000`, `(4)=30000`;
     soma dos 10 primeiros delays ≤ 300s (outage de 5min ⇒ ≥10 probes).
   - Modo reuso: fixture server morto por outage comprimida (env 200ms) →
     `reconnectState()` reporta `reconnecting=true` com `attempts > 3` e
     `isDaemonDown()===false` o tempo todo; server volta → `reconnecting=false`,
     `attempts===0`, health 200 em ≤ 2s, nenhum spawn (pid único).
   - Modo hosted: testes de give-up existentes continuam passando sem mudança.
2. `npx tsx scripts/desktop-flow.test.ts` verde, gravando shot 1440x900 do estado
   "reconectando…" em `~/.opencode-remote/pilot/shots/builder/P1-053-reconnecting.png`
   e afirmando o botão "Reconectar agora" no banner `daemonDown` (FORCE_DOWN).
3. `npm run test:unit && npm run typecheck && npm run lint` verdes.
4. Sem re-pairing: após ciclo kill→recovery no teste do item 1, o `daemon.json`
   (0600, fixture) não é reescrito pelo desktop e nenhuma nova entrada de
   allowlist é criada; no `desktop-flow`, o overlay de QR não aparece no estado reconectando.
5. READMEs descrevem os 3 estados (reconectando infinito em reuso / botão em hosted / recuperação sem re-pair).

## Out of scope

- Mudar relay (`apps/relay`), handshake, allowlist, replay (seq-in-AAD) ou o formato
  do state 0600 — intocados (constituição 1, 2).
- `scripts/invariants.ts` e `deploy/` (constituição 3).
- Backoff do `OcrClient` (relay) em `apps/web/src/lib/client.ts` — já tem reconexão própria.
- Spawn de daemon substituto pelo desktop quando o launchd morre (tray "Restart daemon" cobre).
- Novos fluxos no gate desktop-flow (1 shot + 1 assertion bastam).
