# P1-061 — Modo local direto: app fala com o daemon sem relay

## Problem

O app desktop no mesmo Mac que o daemon roteia cada frame via relay loopback
(wss + crypto + relay): `OcrClient` sempre diala `pairing.relay`
(apps/web/src/lib/client.ts:585) e o daemon conecta OUT no relay
(apps/daemon/src/index.ts:1419). Deploys do pilot kickstartam relay+daemon 41x/dia
(apps/pilot/src/deploy.ts:72-73) e derrubam o WS no meio do stream — caso real
21:01, agent construindo, app cego. O loopback tem a mesma máquina nas duas
pontas: o relay é salto desnecessário e um ponto de falha extra.

## Approach

1. **WS local no daemon** (apps/daemon/src/index.ts): `startMetricsServer`
   retorna o `http.Server` do loopback 127.0.0.1:8792 (apps/daemon/src/metrics.ts:83).
   No daemon, anexar `WebSocketServer({ noServer: true })` de `ws` via
   `apiServer.on("upgrade")`: só path `/ws`, checagem de defesa `remoteAddress`
   loopback e `?token=` igual a `apiToken()` (daemon.json, 0600; gerado
   preguiçosamente pela própria função). Upgrade rejeitado ⇒ `socket.destroy()`,
   sem logar a URL (token na query). Conexão aceita alimenta o
   **mesmo** `handleMessage(data, ws)` (index.ts:1293): protocolo `RelayFrame`
   idêntico ao do relay, handshake E2E, allowlist fresh-read e replay guard
   (seq-in-AAD) intocados — nenhuma rota plaintext nova. Gauge
   `ocr_local_ws_sessions`. Shutdown: sessões locais já estão em `sessions`
   (index.ts:867), o drain do P2-020 as cobre.
2. **Transporte no cliente** (apps/web/src/lib/client.ts): `OcrClient.connect`
   recebe opcionalmente `local?: { url }`. Se presente, diala
   `ws://127.0.0.1:8792/ws?token=…` com timeout curto (3s) para o confirm do
   handshake; sucesso ⇒ `transport = "local"`; falha ⇒ cai no relay de sempre.
   Reconexão (`reconnect`, client.ts:336) fica *sticky* no último transporte
   bom e faz failover após 2 falhas consecutivas. Handshake, sealing, heartbeat,
   replay de ops pendentes: zero mudança (o client já tem `pairing.k`).
3. **Token no renderer** (apps/desktop): novo IPC `app:localLink` em
   main.ts/preload.ts devolve `{ port, token }` lido do daemon.json a cada
   chamada. Relaxa de propósito a regra "o renderer nunca vê o apiToken"
   (main.ts:130-133): o renderer é processo same-user, o token só vale no
   loopback, e o client E2E já fala com o daemon como par autorizado.
   Documentar a troca no security.md.
4. **Resync de stream** (apps/web/src/components/ChatView.tsx): efeito sobre
   `connStatus` — na transição `connecting→paired` após uma queda (ref
   `hadDrop`), reexecutar `loadHistory()` (substitui `bubbles` inteiro,
   ChatView.tsx:351) e limpar o tail de streaming (`liveText`, watermark
   `lastEventId` resetada) antes do fetch. Histórico é a fonte da verdade:
   mensagens produzidas durante a lacuna aparecem sem reenvio, eventos pós-
   reconexão continuam pelo watermark existente.

## Edge cases

- PWA/phone (sem bridge): sem `local` ⇒ fluxo relay exato de hoje, zero diff de comportamento.
- Electron nunca carrega a UI por https (loadFile/loadFile dev http) — sem mixed content no `ws://`.
- daemon.json sem apiToken ainda: upgrade responde destruição do socket; o health poll do sidecar gera o token antes de qualquer dial local.
- Kickstart do daemon: WS local cai (processo morreu), client rediala com backoff, daemon sobe, "reconnect" control-frame/re-handshake rodam como hoje (allowlist fresh-read); resync cobre a lacuna. Kickstart do relay NÃO afeta o app local.
- Failover local→relay: mesmo `from` re-hello substitui a sessão no Map (sessions.set) — socket velho nunca recebe broadcast.
- Token na query: proibido logar no daemon e no client (logger só recebe URL sem query).
- Resync não pode duplicar bolhas: `loadHistory` substitui o estado; eventos já processados ficam atrás do watermark; race fetch×evento novo é resolvido ordenando clear-tail → fetch → eventos.

## Acceptance criteria

1. `npm run typecheck --silent`, `npm run test:unit --silent`,
   `npm run test:e2e --silent` e `npm run build --silent` verdes;
   `scripts/localws.test.ts` prova: token errado ⇒ upgrade destruído; token
   certo ⇒ hello→confirm + 1 op sealed ida-e-volta contra o daemon real.
2. Unit pinam: builder da URL local (`ws://127.0.0.1:<port>/ws?token=…`);
   predicado de failover (2 falhas ⇒ troca de transporte; 1 falha ⇒ sticky);
   nenhum log contém `token=`.
3. Campo (local): app desktop com sessão aberta em stream —
   `launchctl kickstart -k gui/$(id -u)/com.ocr.relay` ⇒ dot verde inalterado
   (nenhuma reconexão); `launchctl kickstart -k gui/$(id -u)/com.ocr.daemon` ⇒
   dot amarelo→verde em ≤15s e as mensagens do agent produzidas na lacuna
   aparecem sozinhas, sem reenvio do usuário.
4. Relay intacto: `scripts/smoke.ts` e `scripts/reconnect.test.ts` verdes;
   nenhum frame plaintext no relay (invariants existentes passam sem mudança).
5. Settings mostra o transporte atual; screenshots 1440x900 e 390px via
   `tools/browse.mjs` citados no EVIDENCE.

## Out of scope

- Acesso direto do PWA/phone em rede local (exigiria CORS/mTLS) — remote continua no relay.
- Qualquer mudança em cripto E2E, allowlist, replay guard, `deploy/` ou `scripts/invariants.ts`.
- Buffer de replay de eventos no daemon (resync é refetch de histórico).
- Rate-limit/mTLS no WS local (loopback + token já delimitam).
- Múltiplas janelas/instâncias do app desktop.
