# P1-078 — Cache affinity entre slots: prefixo byte-idêntico e escalonamento cache-aware

## Problem

P1-077 tornou o prefixo dos 4 templates principais byte-idêntico por slot, mas o cache de
prefixo do provider é **por conta/organização**: os 2 slots batem no mesmo provider e podem
herdar cache um do outro — porém hoje isso não acontece e não é medido:

1. **Prefixo entre slots quebra dentro do próprio opencode**: cada spawn headless roda em cwd
   distinto (`~/.opencode-remote/pilot/repo-<slot>`, `ensureSlotWorkspace` em
   `apps/pilot/src/index.ts:762`) e o opencode 1.18.25 injeta `Working directory: ${cwd}` +
   header absoluto do AGENTS.md no system prompt (bloco `<env>` do `SystemPrompt.environment`,
   verificado no binário instalado). O pilot não controla esses bytes — herança cross-slot só é
   provável **dentro do mesmo slot** (cwd constante), nunca entre slots simultâneos.
2. **Prompts auxiliares ainda intercalam variável antes do estável**: `runStrategist`
   (index.ts:604-646) põe `lessonsBlock`/`failureBlock` no meio; `forensicPrompt`
   (forensic.ts:81), `researcher.ts` e `explorer.ts` idem. O mesmo padrão do P1-077 não foi
   aplicado a eles.
3. **O scheduler ignora cache**: `pickBatch`/`pickTasks` (apps/pilot/src/scheduler.ts) atribuem
   slots por ordem de fila; uma task de shape similar (mesma `area`) cai no slot que nunca
   viu aquele prefixo em vez de herdar o cache do slot que acabou de rodar task similar
   (TTL ~5-10min). Starts simultâneos de 2 slots no mesmo ciclo disputam o cache-write.
4. **Zero medição por slot**: P1-077/P2-028 foldam `input/cacheRead/cacheWrite` por task
   (costs.ts `applySessionCosts`), sem dimensão slot — impossível provar o efeito.

## Approach

1. **(a) Normalização** — o pilot controla só o texto que monta: manter a regra "estável
   primeiro, variável por último" nos prompts auxiliares: em `runStrategist`, mover
   `lessonsBlock(lessons)`+`failureBlock` para depois das regras estáveis (perto do contrato
   AUX-TASKS); em `forensicPrompt`/researcher/explorer, blocos de dados (lessons, fontes,
   diffs) por último. Unit test pin: nenhum template interpola caminho de slot (`repo-1`,
   `OCR_PILOT_REPO`, `cfg.workspace`) no prefixo estável — os builders de prompt não recebem
   `ws` hoje (ordem já garantida por construção); o pin impede regressão.
2. **(b) Affinity no scheduler** (`apps/pilot/src/scheduler.ts`): `AFFINITY_TTL_MS = 10min`;
   tipo `SlotAffinity { slot, area, at }`; nova função pura
   `assignSlots(picks, freeSlots, busy, affinity, now, ttl?)` → `Map<taskId, slot>`: task
   prefere o slot livre cujo último task teve o mesmo `areaKey` dentro do TTL (mais recente
   vence), senão o slot livre de menor número. `runSlot` grava a affinity em memória no
   `finally` (índice por slot, só substitui). Invariante P1-006 intacta: `pickBatch` continua
   dedupando áreas — affinity só escolhe ENTRE slots livres.
3. **(c) Starts escalonados**: `SLOT_START_STAGGER_MS = 20_000`; helper puro
   `startDelayMs(index) = index * SLOT_START_STAGGER_MS`. `fillFreeSlots` (index.ts:96) reserva
   o slot em `running` imediatamente e só o primeiro pick começa já; pick i>0 espera
   `startDelayMs(i)` e o timer re-checa `frozen()`/audit/budget antes de spawnar.
4. **(d) Medição por slot**: no ponto da reconciliação (`runSlot`, index.ts:357), além do log
   `task cache`, emitir `msg:"slot cache"` com `{slot, task, input, cacheRead, cacheWrite,
   ratio}` e acumular em `state.slotCache: Record<number, {input, cacheRead, cacheWrite}>`
   (substituição pelo valor da task, janela viva). `ratio` = `cacheHitRatio` (0 com
   denominador 0). Normalizar em `loadState` e `normalizePilotState` (backfill `{}`).
5. **Documentação**: parágrafo em docs/PILOT.md (affinity, stagger, `slot cache`, limitação
   do bloco `<env>` do opencode — cross-slot o prefixo diverge fora do controle do pilot) e
   uma linha no AGENTS.md sobre affinity/stagger.

## Touched files

- `apps/pilot/src/scheduler.ts` — `AFFINITY_TTL_MS`, `SLOT_START_STAGGER_MS`, `SlotAffinity`,
  `assignSlots`, `startDelayMs` (puros, testáveis).
- `apps/pilot/src/index.ts` — `fillFreeSlots` usa `assignSlots` + start escalonado;
  `runSlot` registra affinity no `finally` e loga/folda `slot cache`.
- `apps/pilot/src/state.ts` — `slotCache?` opcional + normalização em `loadState`.
- `apps/pilot/src/doctor.ts` — backfill em `normalizePilotState`.
- `apps/pilot/src/forensic.ts`, `apps/pilot/src/researcher.ts`, `apps/pilot/src/explorer.ts`,
  `apps/pilot/src/index.ts` (strategist) — reordenação estável→variável.
- `scripts/unit.test.ts` — pins novos (ver AC 2-4), estendendo o bloco P1-077 (~:1633).
- `docs/PILOT.md`, `AGENTS.md` — documentação.

## Edge cases

- `--once` (bateria de eval): só o loop escolhe e 1 task — stagger não pode causar
  double-pick nem segunda pipeline; timer não spawna se `once`.
- Frozen/audit ativados durante a janela de 20s: timer re-checa antes de spawnar e descarta.
- Processo morre no stagger: slot já reservado em `running` no mesmo tick — sem dupla
  atribuição; estado de affinity é in-memory e se perde no restart (TTL de minutos, aceitável).
- Task sem área (`solo`) nunca ganha affinity (key `solo` é serial por P1-006).
- `state.slotCache` ausente/corrompido em state.json legado → `{}` (loadState/doctor).
- DB/sqlite3 indisponível: fold de slot é best-effort igual ao de task (não bloqueia ciclo).
- Mudança de data (`Today's date` no `<env>`) quebra cache à meia-noite — aceito.
- Tier-B: prompts reordenados valem para fallback tier A/B automaticamente; runner intocado.

## Acceptance criteria

1. `npm run typecheck && npm run build && npm run test:unit` → exit 0 (gate re-executa).
2. Unit (scheduler): `assignSlots` — task de área X prefere o slot livre que rodou X dentro do
   TTL; affinity expirada (`now - at > 10min`) → slot de menor número; área busy nunca
   atribuída; `startDelayMs(0)===0`, `startDelayMs(1)===20000`, `startDelayMs(2)===40000`.
3. Unit (normalização, estende bloco P1-077): para duas tasks quaisquer,
   `builderPrompt`/`plannerPrompt` continuam byte-idênticos até a linha TASK; novo pin:
   `!/repo-\d/.test(prompt)` e `!prompt.includes(process.env.OCR_PILOT_REPO ?? "")` para todos
   os templates (incl. strategist/forensic/researcher/explorer); no strategist, os blocos
   variáveis ("EXPERIENCE —"/"FAILURE LESSONS") vêm depois das regras estáveis ("SECURITY
   RULE"); no forensic, depois do contrato de seções ("## Recommendations").
4. Unit (métricas): fold de slot agrega `{input, cacheRead, cacheWrite}` por slot e `ratio`
   0 com denominador 0; `loadState`/`normalizePilotState` backfillam `slotCache: {}`.
5. Live (pós-merge, janela de 10 ciclos): pilot.log contém linhas `msg:"slot cache"` por slot;
   no opencode.db, o primeiro builder da task B no MESMO slot dentro do TTL de uma task A
   similar mostra `tokens_cache_read > 0` (herança de prefixo; A e B não rodam simultâneos —
   P1-006) — critério "cache.read > 0 no segundo" provado no par de affinity.
6. docs/PILOT.md documenta os três mecanismos e a limitação do `<env>` cross-slot.

## Out of scope

- Igualar paths de slot (impossível com cwds concorrentes) ou alterar o binário/config do
  opencode que injeta `Working directory` no system prompt.
- Dashboard/UI para `slotCache` (só log + state.json).
- Mudar a regra de paralelismo por área (P1-006), budgets, `scripts/invariants.ts`, `deploy/`,
  cripto E2E ou CONSTITUTION.
- Persistir affinity across restarts ou afinidade por shape além de `areaKey`.
- Resume de sessão (`-s`, P2-013) — caching de contexto ortogonal, intocado.
