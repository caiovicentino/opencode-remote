# P3-348 — desktop-package-win: o boot smoke imprime OK e trava até o timeout de 10min

## Problem
Nos runs `34280931249` (P3-343) e `34283357299` (P3-344) o passo `Smoke-boot the packaged app`
do job `desktop-package-win` loga o veredito bom
(`packaged-boot: OK D:\a\...\win-unpacked` + `app empacotado abriu, montou a interface e o console está limpo`)
e depois fica 10 minutos parado até `The action 'Smoke-boot the packaged app' has timed out after 10 minutes`
— o main fica vermelho a cada PR que toca desktop.

Causa: `apps/desktop/scripts/packaged-boot.mjs` nunca encerra o processo node de forma determinística.
`finish()` (linha 128) só define `process.exitCode`, e no `finally` (linha 274) o `closeApp()` faz
`electronApp.close()` com SIGKILL apenas no **processo pai** após `CLOSE_DEADLINE_MS`; no win32 a árvore
de processos do Electron / o pipe do Playwright ficam vivos e seguram o event loop, então o node nunca sai.
O `watchdog` de `BOOT_TIMEOUT_MS` (linha 194) é limpo dentro de `finish()`, ou seja só cobre o caminho
**antes** do veredito. A P3-343 mexeu só na descoberta do `.exe` e não consertou isto (o próprio run do
merge dela falhou no mesmo passo). O timeout de 12s do `OCR_PACKAGED_BOOT_SHOT` (`boot shot unavailable`)
é ruído fail-open correlato, não a causa.

## Approach
1. **Módulo puro novo** `apps/desktop/scripts/packaged-boot-exit.mjs` (mesma regra dos helpers P2-194/P2-208:
   zero `node:fs|os|path|net|http|child_process`, zero I/O, importável pela bateria):
   - `exitPlan({ platform, exitCode, pid, childAlive })` → plano ordenado e fechado:
     `[{ kind: "kill-tree", pid }]` apenas quando `platform === "win32" && childAlive === true && Number.isInteger(pid) && pid > 0`,
     seguido **sempre** de `{ kind: "exit", code }` com `code = Number.isInteger(exitCode) ? exitCode : 1`
     (undefined/null/NaN → 1, nunca um "sucesso" acidental).
   - `runExitPlan(plan, { kill, exit })` → executa na ordem; `kill(pid)` dentro de try/catch (best-effort,
     nunca muda o código) e por fim `exit(code)`. As dependências são **injetadas** — o módulo continua puro
     e o teste prova o caminho de saída sem tocar no SO.
2. **`packaged-boot.mjs`** (único ponto que toca processo/SO):
   - importa `node:child_process` (`spawnSync`) e o módulo acima;
   - guarda o pid logo após o launch (`const launchedPid = electronApp.process()?.pid ?? null`) porque depois
     do `close()` o handle pode não expor mais nada;
   - no `finally` do `main()`, **depois** de `await closeApp(electronApp)`, executa
     `runExitPlan(exitPlan({ platform: process.platform, exitCode: process.exitCode, pid: launchedPid, childAlive: <processo ainda vivo> }), { kill, exit: process.exit })`,
     onde `kill` faz `spawnSync("taskkill", ["/T", "/F", "/PID", String(pid)], { stdio: "ignore", timeout: 5_000 })`
     (árvore inteira, não só o pai) e loga uma linha `packaged-boot: kill-tree pid=<pid>`;
   - `childAlive` = `electronApp?.process?.()` existe e `exitCode === null` (try/catch → `false`).
3. **Watchdog** deixa de ser desarmado por `finish()`: `finish()` não chama mais `clearTimeout(watchdog)`;
   o timer é `unref()`-ado logo após ser criado (para ele mesmo nunca ser o handle que segura o loop) e o
   callback passa a logar `packaged-boot: FAIL — travou após o veredito` e chamar `process.exit(1)` também
   no caminho pós-veredito. Continua matando `activeApp` antes de sair.
4. **`.github/workflows/ci.yml`**: no passo `Smoke-boot the packaged app` do job **`desktop-package-win`**
   troca `timeout-minutes: 10` → `timeout-minutes: 4` (boot real ~15s; travamento vira vermelho em 4min).
   `shell: bash`, `env: OCR_PACKAGED_BOOT_SHOT` e o `run:` ficam idênticos. **Não** mexer no passo mac nem
   nos passos de `release.yml`.
5. **Captura do shot** continua exatamente como está (fail-open, uma linha `boot shot unavailable: …`) — já
   atende o item 3 da tarefa; nada a mudar.
6. **Docs**: uma frase em `docs/PILOT.md` (parágrafo do boot smoke, ~linha 170) e em `README.md`
   (~linha 756, bloco do `OCR_PACKAGED_BOOT_SHOT`) registrando a saída determinística pós-veredito e o
   teto de 4min do passo win no ci.

## Edge cases
- **Veredito FAIL**: `exitPlan` devolve `code: 1` e o `exit` continua sendo a última etapa — o kill-tree
  falhando (taskkill ausente, pid já morto, acesso negado) nunca engole o código.
- **`process.exitCode` indefinido** (exceção antes de `finish()`): plano sai com `1`, nunca `0`.
- **Não-win32** (`darwin`/`linux`): plano tem **apenas** o passo `exit` — nenhum `taskkill`, nenhum spawn.
- **Caminhos de retorno antecipado** de `main()` (sem argv, bundle inexistente, playwright ausente,
  `binary-missing`): continuam usando `process.exitCode` + `return`; não há handle vivo ali e o comportamento
  observável (exit 1 / fail-closed) não muda.
- **`electronApp.process()` lançando** depois do `close()`: try/catch → `childAlive: false`, plano só com `exit`.
- **Watchdog pós-veredito**: só dispara se o `finally` inteiro travar >`BOOT_TIMEOUT_MS`; é backstop, e como
  o timer é `unref()`-ado ele nunca é a causa do processo continuar vivo.
- **`bootsmokeparity.ts`** só exige `timeout-minutes` presente (`!== null`) e `shell: bash` — `4` passa; não
  alterar o gate.
- Nenhuma linha nova imprime path de usuário, sessão, token ou conteúdo de frame (constituição §1/§4).

## Acceptance criteria
1. `npx tsx scripts/unit.test.ts` passa, com novos checks no bloco `P3-348`:
   - `exitPlan({ platform: "win32", exitCode: 0, pid: 4242, childAlive: true })` → exatamente
     `[{ kind: "kill-tree", pid: 4242 }, { kind: "exit", code: 0 }]`;
   - `platform: "darwin"` (mesmos demais fatos) → exatamente `[{ kind: "exit", code: 0 }]`;
   - `childAlive: false` ou `pid: null`/`0`/`-1` no win32 → sem `kill-tree`;
   - `exitCode: undefined` → `{ kind: "exit", code: 1 }`; `exitCode: 1` → `code: 1`;
   - `runExitPlan` com `kill`/`exit` falsos: **prova que `exit` é chamado uma única vez com o código do
     veredito** (0 no OK, 1 no FAIL) e que um `kill` que lança não impede o `exit`;
   - fonte: `packaged-boot-exit.mjs` sem `node:(fs|os|path|net|http|child_process)`;
   - fonte: `packaged-boot.mjs` contém `runExitPlan(` dentro do `finally`, `taskkill` com `"/T"` e `"/F"`,
     e `finish()` **não** contém mais `clearTimeout(watchdog)`.
2. `npx tsx scripts/bootsmokeparity.ts` (ou o check equivalente em `unit.test.ts`) sem problemas novos;
   `npx tsx scripts/check-job-timeouts.ts` continua verde.
3. `.github/workflows/ci.yml`: o passo `Smoke-boot the packaged app` de `desktop-package-win` tem
   `timeout-minutes: 4`; o de `desktop-package` (mac) segue `10`.
4. `npm run test:unit` verde localmente.
5. `gh run list --branch main --workflow ci.yml` com **3 pushes seguidos verdes** em `desktop-package-win`,
   e o job terminando em **<5min** (passo de boot em ~15–60s, sem `has timed out`).
6. `docs/PILOT.md` e `README.md` descrevem a saída determinística e o teto de 4min.
